① 三大闭环关系总图与定位

1.1 全景图：三个领域不是平级，是"飞轮 + 底座 + 追赶者"

三个领域在公开讨论里经常被并排罗列，但读者最容易踩的坑是把它们当三个独立技术栈去学。它们真实的关系是层级嵌套：自动驾驶数据闭环是上层"飞轮"，数据基建栈是横跨两个领域的"底座"，具身智能数据闭环是没有车队红利、被迫激进创新的"追赶者"——而它正在反过来倒逼自动驾驶重审假设。

1.3 为什么"放在一起学"是 ROI 最高的姿势

三个领域公开讨论各自孤立——AD 团队读 arXiv 2401.12888，具身团队读 Open X-Embodiment，数据基建团队读 DDIA——但所有 Function Owner 级判断都发生在三者交界处。一个典型问题："我们要不要从 ES 迁到 lakehouse？" 这个决策需要同时懂：（1）AD 数据闭环里的"价值单位是 frame 还是 clip"；（2）具身的 OXE schema 归一化教训；（3）lakehouse 表格式 Iceberg vs Hudi 的写入模式差异。三块缺一块，决策都会偏。

"放在一起学"的存在理由是判断力在交界处产生。单学一个领域的人能拆解问题，但不能在不确定性里拍板——拍板需要跨界对照（"具身那边怎么做的，他们的代价是什么"）。这是 PM 跨到 Function Owner 的关键认知跃迁。反事实：若分开学，会出现"数据闭环 PM 不懂 lakehouse 物理设计"，被平台方主导决策（这正是读者校准报告里"治理结构定义权让渡给平台方"的根因）。
三个领域一句话定位：AD 数据闭环是"被量产车队红利推着走的成熟飞轮"；数据基建栈是"决定飞轮转速上限与方向正确性的横向底座"；具身智能数据闭环是"没有车队红利的追赶者，正在用合成优先 + 遥操作硬件激进创新反过来倒逼 AD 重审假设"。读者学这本教材的目标不是记住三个领域的事实清单，而是在脑里把这张关系图变成"判断任何数据相关问题时先在图上定位"的本能。

② 自动驾驶数据闭环：七段飞轮 + 物理不变量

自动驾驶数据闭环已迭代到第 3 代（生成式 + 世界模型 + 主动误差挖掘），是三个领域里成熟度最高的。学术心智模型来自 arXiv 2401.12888《Data-Centric Evolution in AD》（来源），给出 7 组件架构。本节按"采集→标注→挖掘→训练→仿真评测→部署回流→物理不变量"七段展开，每段给标杆公司做法、关键数字、能力定级。

2.1 采集段：量产车队 = 天然被动飞轮，已解决冷启动

AD 采集段的核心范式是shadow mode + trigger classifier：车上同时跑生产模型和影子模型，两者分歧或触发器命中时回传 engineering clip。这是 Tesla 开创、小鹏/理想复用的成熟范式，本质是一个"永不疲倦的差异采样器"。

  • Tesla：8 相机 × 36fps，1000 车 1h ≈ 10 亿帧；标注 ROI 提升 100x；去雷达项目 1 周内自动标 1 万 clips（Tesla AI Day 2021 拆解）。
  • 小鹏：300+ 触发器，影子模式 + 定向触发；上传 22x、带宽 15x、集群利用率 >90%、云端 10 EFLOPS、训练规模从 1M → 200M Clips、自研图灵芯片（1024 科技日）。
  • 理想：87 万车影子模式 + 云端世界模型 + 主流水线内嵌脱敏；云端 4.5 EFLOPS；VLA 依赖"数百万辆车构建的数据闭环"（东方财富研报）。
  • Waymo：单车日产 ~25TB；200 TFLOPS 边缘计算。
shadow mode 是 AD 数据闭环的"飞轮启动器"——它把"何时回传"从无穷多手写规则收敛到"两个模型分歧"一个统一信号。它的本质是差异采样：只采对未来训练有信息量的样本。Cruise 用误差、Tesla 用 shadow 分歧、小鹏用 300+ 触发器，看似不同，本质都是差异采样器（trigger classifier 拆解）。反事实：若没有差异采样，全量回传会让带宽和标注成本爆炸，飞轮转不动。
读者要从"shadow mode 是个技术名词"升级到"trigger classifier 是产品功能，值得作为独立子模块立项设计"。这意味着它有 PRD、有状态机、有评测指标（命中率、误触发率、覆盖长尾分布）、有版本化。读者自家业务里这块如果还散落在各团队代码里，是第一个该收口的产品机会。

2.2 标注段：offboard 精标 + "未来=真值"自监督

AD 标注段有两条并行路线，分别对应检测类任务和预测/规划类任务：

  • Offboard 3D 精标（检测类）：用多车多趟 LiDAR 序列联合优化，在 4D vector-space 重建出比单帧更精确的标注。代表：Waymo Offboard 3D Auto-Labeling（CVPR 2021，object-centric 分治，论文）；Tesla 4D NeRF 重建；Uber Auto4D（4D 空间 3D + 时间 1D，object size branch + motion path branch）。
  • 未来=真值自监督（预测/规划类）：用未来感知结果作为"伪真值"标注过去的预测。Cruise Continuous Learning Machine（CLM）是范式开山（Sean Harris 2020），核心洞察："旧金山市区挑战场景频率是郊区 46 倍；U-turn 出现频率 <0.1%"——量化了长尾问题。

两条路线的存在理由是任务的"可自监督不变量"不同。检测类任务的不变量是"同一物体在多帧多车视角下是同一物理实体"——所以可以跨帧聚合精标。预测/规划类任务的不变量是"未来必然发生"——所以未来帧可以做过去的真值。先找到你任务的不变量，再选标注路线。反事实：检测类硬套"未来=真值"无效（物体没动）；预测类硬套"多帧聚合"无效（预测的是行为不是物体）。
这是读者最该吃透的范式："可自监督的物理不变量"决定自动化天花板。Cruise CLM 的"未来=真值"和 Waymo Offboard 的"跨帧聚合"是两种不变量的两个范式解。Function Owner 评审自监督方案时，第一句问的是"你的不变量是什么、为什么它成立"。回答不出 = 方案不可信。读者校准报告显示这块是 can-decide（doc04 数据质量治理按错误码归因，96% 可规避论证），但要把这个能力迁移到"自监督不变量论证"上。

2.3 挖掘段：误差驱动 + 主动学习 + VLM/LLM 自动化

标注解决"已有数据怎么变可用"，挖掘解决"哪些数据值得采"。三条递进路线：

  1. 规则挖掘：写触发器（"急刹 + 横向加速度 > X"），是早期路线，覆盖窄、维护成本高。
  2. 误差驱动挖掘：模型预测和真实分歧显著 → 自动入库。Cruise CLM 是开山，小鹏"算法-人分歧自动上传（无人工）"是量产版。
  3. VLM/LLM 自动化数据引擎：用 foundation model 替代手写规则和人工标注。AIDE（NEC Lab，CVPR 2024，论文）是前沿基线，被引 57+，把 active learning + self/semi-supervised labeling + error mining 拼成 pipeline。这是数据闭环平台下一代架构的 RFP。
三路线递进的存在理由是维护成本和信息覆盖率的权衡。规则维护成本高但解释性强，适合安全关键场景；误差驱动覆盖率好但需要"未来真值"基础设施；VLM 自动化最前沿但黑盒、需要兜底。一个成熟数据闭环团队应该三路线并存而非替换——规则兜底、误差驱动做主力、VLM 探边界。反事实：若全押 VLM，遇到 VLM 自己也不认识的新长尾会盲飞；若全押规则，永远追不上长尾增速。

2.4 训练段：从单模型到端到端 VLA 范式

训练段在 AD 里正在经历感知-预测-规划三段式 → 端到端的范式切换。这块和具身侧的 VLA（Vision-Language-Action）深度交叉：

  • 传统三段式：感知出检测结果 → 预测他车轨迹 → 规划自车动作，三段各有 loss、各有数据集。
  • 端到端：直接从原始传感器输入到动作输出。Momenta "飞轮大模型"、华为 WEWA（World Engine + World Action）都在这条线上。
  • 连续化输出：端到端轨迹/规划输出在离散化 vs 连续化间取舍。具身侧 π0 flow matching + action chunk=50（~1 秒，论文）证明连续表达在高频控制上更优，AD 端到端值得评估。
训练段是 AD 数据闭环里读者最容易"只当用户不当负责人"的环节。读者校准显示这块 practiced（跟过完整闭环但没深入）。Function Owner 必修的是训练调度：理解 Determined AI 的实验/checkpoint 模型、Gang scheduling 防分布式死锁、vGPU 分配、checkpoint 续训——这些是 JoyDrive-Infra 的训练子系统核心（见教材 B）。读者当前盲区是"自家集群拓扑/容量水位仍是灰盒"（doc07 自述"数据预热，不太清楚当前几个集群"）。

2.5 仿真评测段：log replay + re-simulation + 世界模型（详见第 3 章）

仿真评测段决定"飞轮转得对不对"，是闭环里最被低估的高杠杆子系统。本节只给位置，详细的世界模型路线、log replay vs re-simulation、场景库+测评指标见第 3 章。关键数字先记：华为 25 万场景库 + 500+ 类功能场景 + 200+ 测评指标；百度 PB 级场景库；Waymo Waymax + Sim Agents Challenge ~57.5 万场景。

2.6 部署回流段：OTA 是飞轮"闭"点

部署回流是飞轮真正"闭"的点——模型上车后，真实运行数据回灌到下一轮采集/挖掘。两个关键设计：

  • 商业架构 > 技术架构：Momenta 的"Mpilot 量产喂数据 / MSD L4 吃红利"（来源）、理想的"87 万车影子模式 + OTA 回灌"，都是用低成本量产场景养高价值算法资产的双产品线互馈。做数据闭环 PM 不能只看技术，要先看商业架构是否支撑飞轮转动。
  • 脱敏/合规前置嵌入：规模化下唯一可行的合规姿势是前置嵌入而非事后补丁。理想把脱敏放在"采集→脱敏→训练→OTA"链路里。这是量产车企做数据闭环的硬约束。
"OTA 是飞轮闭点"的存在理由是没有 OTA 回灌的飞轮是开环。开环飞轮靠人工补数据，永远追不上长尾增速；闭环飞轮靠真实运行数据自动找问题。Momenta 的"闭环自动化五环（发现/记录/标注/训练/验证）"可以直接落地为数据平台五个产品模块。反事实：若没有 OTA 回灌，部署的模型在真实场景里的失败不会被自动捕获，下一版模型不会变好。

③ 仿真·场景库·世界模型·长尾挖掘

仿真评测段是 AD 数据闭环里被严重低估的高杠杆子系统。它决定"飞轮转得对不对"，而不只是"转得快不快"。本节按"两种仿真范式 → 世界模型两条技术路线 → 场景库+测评指标体系 → 生成式造难例"展开。

3.1 log replay vs re-simulation：两种仿真范式不是对立是分工

仿真段最容易被新手混淆的概念是log replay（回放）和re-simulation（重仿真）。两者不是对立而是分工（Applied Intuition 解析）：

范式原理适合局限
log replay（开环/半闭环）把真实 log 回放，模型输出不反馈到环境感知/预测回归、量化模型在某段真实数据上的表现无法测试"模型动作改变后他车如何反应"
re-simulation（闭环）用世界模型/Sim Agents 响应模型动作，闭环演化规划/控制任务、测试对抗场景、长尾边界仿真保真度依赖世界模型质量
双层回归log replay + re-simulation 叠加量产回归套件（既能测感知又能测规划）工程复杂度高，需要统一评测框架
两种范式分工的存在理由是任务类型决定仿真方式。感知模型输出不影响环境（你识别错了一个车，那车不会因为你识别错就改变轨迹），所以 log replay 够用。规划模型输出会改变环境（你变道了，他车会避让），所以必须 re-simulation。Function Owner 设计评测套件时按任务类型分配两种范式比例。反事实：规划任务只用 log replay，会得到"模型在真实数据上表现好"的虚假结论，因为没测试它动作改变后他车的反应。
读者校准显示评测闭环是 introduced 盲区（doc22 HIL 是性能观测平台，作为数据闭环评测段自己写"Q2-Q3 才纳入"）。这是从 PM 跨到 Function Owner 必须补的硬技能。建议直接对标 JoyDrive-Infra 的 evaluation-data-service（"行云缺陷 → 评测准入 → 自动触发推理流水线 → 状态回填"），它是当前读者能接触到的最近距离的运行中评测闭环实现。精读 doc/evaluation-data-service.md。

"渲染层 vs 决策层"是读者判断世界模型相关论文/产品的元地图。看到任一世界模型先问"它在哪一层"，立刻能判断它的训练数据需求、算力成本、用途边界。这是仿真段 can-decide 级判断的入场券。

3.3 场景库 + 测评指标体系：被低估的高杠杆子系统

场景库 + 测评指标决定"飞轮转得对不对"。它是独立产品线，不是附属工具。标杆：

  • 华为 ADS 4.0：25 万场景库 + 500+ 类功能场景 + 200+ 测评指标；云端 7.5 EFLOPS；日行 3500 万公里；模型 5 天迭代；6 亿公里仿真（官方）。
  • 百度 Apollo：PB 级场景库（真实 + 虚拟）；文心大模型数据智能搜索引擎 + 数据中台 PaaS 化。
  • Waymo：Waymax + Sim Agents Challenge ~57.5 万场景；Waymo Open Dataset。
  • Mobileye Meteor + Genario（博客）：Diagnosing the Long Tail——把边缘 case 系统化变成定向训练数据。
场景库+测评指标独立立项的存在理由是它防的是"飞轮空转"。没有它，团队可能狂采数据、狂标数据、狂训练，但模型在关键场景上的表现反而下降（因为评测不准、回归不全面）。华为的 200+ 测评指标本质上是"我们承诺这 200 个场景上模型必须过"的契约，不是 KPI。建议把"场景库 + 测评指标体系"作为独立产品线立项，配合 ASAM OpenSCENARIO 2.0 做可互换防工具锁定（标准）。反事实：场景库附属在仿真工具下，工具一换场景全丢，多年积累归零。
读者校准显示"验收格多处空缺、能力间依赖/冲突仲裁未定义"——这恰好是场景库+测评指标体系的核心要素。把测评指标设计成"契约"（200 个场景必须过、不过不能交付），就是 JoyDrive-Infra 那种"血缘校验作为交付前置门禁"在评测段的同构。建议读者下一步把"测评指标 = 契约"这件事写成治理型 PRD。

④ 数据基建栈：六层横向底座

数据基建栈是横跨 AD 与具身的底座，决定上层飞轮的转速上限和方向是否正确。它有六个独立关注点，共识是"OpenLineage 当标准 + DataHub/OpenMetadata 当平台"——不要让一个工具扛所有职责（参考 TheDataGuy 2025 对比）。本节按"表格式 → 版本化 → 血缘 → 质量 → 元数据 → feature store"六层展开。

4.2 数据版本化：lakeFS / DVC / Pachyderm 按对象类型选

版本化不是单一技术，是三个对象类型对应三个工具：

  • lakeFS（2025-11 收购 DVC）：服务端、PB 级 Git 语义、零拷贝 branch。版本化对象存储数据湖表。
  • DVC：客户端、ML 数据集 + 代码。版本化 ML 数据集 + 模型 + pipeline，保持开源。
  • Pachyderm：pipeline-centric。需要内建血缘 + 容器化。
三个工具按对象类型分工的存在理由是"版本"在不同对象上的语义不同。数据湖表的版本是"快照"（不可变、可 branch、可 zero-copy clone），所以 lakeFS 用 Git 语义。ML 数据集的版本是"训练输入"（要 pin 死、要和模型绑定），所以 DVC 把数据集 hash 进 commit。Pipeline 的版本是"加工逻辑"（要重跑、要追溯），所以 Pachyderm 把血缘内建。反事实：用 DVC 管数据湖表，会发现没有 server 端一致性、跨团队 branch 协作困难。
读者校准重要修正："版本机制不弱、血缘是真的弱"。doc03 的 snapshot/不可变/clone/准入三件套 + run_id↔dataset_version_id 映射，与 JoyDrive DataArtifact 同构，是 practiced。读者之前笼统说"数据版本与血缘是弱项"是错的，要分开精进——版本机制重点是落地（doc03 功能 7 训练追溯先做掉、给出存储拓扑设计），血缘是 introduced 真盲区。

DataHub 的 MCP Server 杀手特性的存在理由是它把元数据从"给人看"升级为"给 Agent 调用"。DataHub MCP Server 让 AD Agent 能编程化查"这版模型用了哪些数据、质量分多少、owner 是谁"——这是 LLM 时代元数据平台的核心价值。OpenMetadata 没有等价能力但部署快、内置质量。团队按"是否在 AI Agent 战略"二选一。反事实：用 Atlas/Amundsen，未来想做"Agent 自助查元数据"会卡在生态缺失。

4.6 feature store：point-in-time 正确性是底线、归属是谈判地

feature store 是负责人绕不开的跨团队接口。两个硬知识点：

(1) point-in-time 正确性是时序 ML 的底线。feature store 的核心价值不是缓存，是"训练时只拿事件时间之前的特征值"。AD 感知/预测模型的 label 都是未来帧，没有这个保证，训练集会"偷看未来"导致 AUC 虚高且无法复现（Tecton 选型指南）。

(2) feature store 是数据平台与 ML 平台的谈判地。归属（基础设施 vs 特征定义）、在线/离线一致性 SLA、发现机制三件事必须提前写死。Uber Palette 按实体组织、Pinterest 两工程师逐步标准化——都可迁移（Uber Palette 博客）。

方案定位适合
Feast开源自管算法栈强 + 成本敏感
Tecton托管，声明式 transformation要托管 + 流式 + point-in-time 保证
Hopsworkspoint-in-time 一致性强对一致性最敏感的场景
Databricks / SageMaker云绑定已在云栈内的团队
"feature store 是谈判地"的存在理由是它同时被数据平台和 ML 平台觊觎。数据平台认为"特征是数据资产，归我"；ML 平台认为"特征是训练输入，归我"。如果不提前写死归属，会出现两个团队各搞一套、特征口径分裂、训练和生产特征不一致的灾难。point-in-time 正确性是硬底线，没有它训练 AUC 虚高且无法复现。反事实：feature store 归属不写死，离线 batch 标注特征和车端在线推理特征对不齐，模型上车后效果大幅下降。
"feature store 是谈判地"这条洞察对读者最重要。读者校准显示"数研冲突已暴露"、"治理结构定义权让渡给平台方"——这正是 feature store 归属谈判失败的典型症状。读者下个阶段要练的就是"在跨团队谈判（feature store 归属、SLA、发现机制）上代表平台方拍板"。这不是技术问题，是治理结构问题。把归属、SLA、发现机制写进治理型 PRD（第 8 章给模板），把谈判从"听产品的"变成"听流程的"。
数据基建六层：表格式（按写入模式选，Iceberg/Delta/Hudi/Paimon）→ 版本化（按对象类型选，lakeFS/DVC/Pachyderm；版本≠血缘）→ 血缘（OpenLineage 标准先行 + DataHub/OpenMetadata 消费）→ 质量（WAP 模式前置门禁 + 质量分作为血缘一等属性）→ 元数据（DataHub/OpenMetadata 二选一，AI Agent 战略选 DataHub MCP Server）→ feature store（point-in-time 是底线 + 归属是谈判地）。读者关键修正：版本机制 practiced、血缘 introduced，不要打包成同一弱项。

⑤ 流处理 · OLAP · 编排 · MLOps

这是支撑数据闭环飞轮"实时性 + 多维查询 + 任务调度 + ML 全生命周期"的横向能力层。本节给四块的选型逻辑和 AD 场景结合点。

5.1 流处理：Flink 几乎是 AD 唯一选择

AD 流处理的核心需求是多传感器对齐、去重、窗口聚合——这些都刚需 stateful processing + watermark + exactly-once。Apache Flink 是首选：

  • Flink（官方概念）：stateful + exactly-once + watermark + 流批一体。AD 多传感器对齐/去重/窗口聚合刚需 stateful；watermark 处理车端乱序。
  • Spark Structured Streaming：micro-batch，延迟不如 Flink。
  • Kafka Streams：嵌入式，规模受限。
  • Flink Serverless：托管版。

工业标杆：理想汽车 Hologres+Flink 万亿级车联网（案例）：150 万 RPS、10 秒增量 ETL 框架、端到端延迟 <2s、冷热比从 2:1 → 5:1、计算成本 -40%。还有蔚来 Flink 实时计算平台（FFA 2021）。

Flink 是 AD 唯一选择的存在理由是stateful + watermark + exactly-once 三件套在车端场景不可替代。车端多传感器（相机/LiDAR/Radar）数据时序错位、网络回传乱序，没有 watermark 就无法定义"何时算迟到"；没有 exactly-once，故障恢复会重复或丢数据；没有 stateful，跨传感器对齐要自己造状态机。反事实：用 Kafka Streams 做多传感器对齐，状态管理会让代码复杂度爆炸。

5.4 ML 训练编排：Kubeflow 管 DAG + Ray 管算力分层

最务实的姿势是把 K8s 做成"Invisible Infrastructure"（KubeRay/Kubeflow SDK 抽象），算法团队不碰 YAML：

  • Ray（分布式训练 + Ray Serve + RL）：步间延迟关键、端到端大模型/RL。
  • Kubeflow（端到端 MLOps + KServe）：标准化多模型生命周期 + 多团队，治理强。
  • Metaflow：devex 优先，治理弱。
  • KubeRay：让 Ray 和 Kubeflow 同集群共存。

推荐组合：Kubeflow 管 DAG + Ray 管算力（ayedo.de 对比）。这是大团队最务实的分层。

分层组合的存在理由是Kubeflow 和 Ray 各自的强项不重叠。Kubeflow 强在 DAG 编排和治理（多团队、多模型、多环境），Ray 强在算力调度（分布式训练、RL、步间延迟）。让 Kubeflow 管"做什么"（DAG）、Ray 管"怎么跑"（算力），各司其职。反事实：让 Kubeflow 跑 RL，步间延迟会拖慢整个训练；让 Ray 管 DAG，治理能力不够，多团队协作会混乱。
这是读者训练调度盲区的关键。JoyDrive-Infra 用 Determined AI 做训练调度（精读 doc/det-cli-integration.md）——Determined 是另一个选择，强在实验/checkpoint 模型。读者要建立的判断力是"Kubeflow vs Ray vs Determined vs Metaflow"选型评审能拍板。判断维度：是端到端大模型/RL（Ray）还是标准化多模型生命周期（Kubeflow）还是实验/checkpoint 治理强（Determined）。
横向支撑四块：流处理（Flink 几乎是 AD 唯一选择，stateful+watermark+exactly-once 三件套；理想 Hologres+Flink 万亿级 150 万 RPS）→ OLAP（按场景分：评测段 Doris/StarRocks、采集监控 Druid、日志聚合 ClickHouse）→ 编排（task-centric vs data-centric 分水岭，AD 推荐 Argo/Dagster 而非 Airflow）→ ML 训练编排（Kubeflow 管 DAG + Ray 管算力分层最务实）。读者差异化优势：argo+k8s+flink+clickhouse 数仓 + onboard 监测 can-decide。

⑥ 具身智能数据闭环：追赶者范式

具身智能数据闭环是"没有车队红利的追赶者"，被迫在合成数据、遥操作硬件、real-to-sim-to-real 上做激进创新，反过来正在倒逼 AD 重审"真实数据为王"的默认假设。本节按"冷启动悖论 → 遥操作+OXE → 合成优先 → AD↔具身可迁移/不可迁移"展开。

6.1 冷启动悖论：没有车队红利，被迫 bootstrap

AD 的冷启动靠量产车队天然飞轮（已解决），具身没有车队红利，被迫用仿真 + 人工遥操作 bootstrap。Tesla Optimus 复制 AD 车队飞轮思路，但没有车队红利——公开招 Data Collection Operator，投入 >$200 万，这是"被动车队飞轮 → 主动人工采集"的退化。

冷启动悖论的存在理由是机器人的物理形态决定了没有"廉价差异采样器"。AD 的车就是天然的数据采集器（每跑一公里都在采），机器人的关节运动需要人遥操作或专门的采集设备（ALOHA 2 $27k 双臂、UMI $400 手持 GoPro 夹爪）。所以具身被迫走"合成优先 + 主动采集"路线。反事实：等机器人量产了再采数据，永远走不出实验室。

6.2 遥操作硬件产品化 + 跨本体 schema 归一化（OXE）

具身侧两个关键创新：

(1) 采集硬件产品化、可分发：

  • UMI（项目）：$400 手持 GoPro 夹爪，采集成本降一个数量级。
  • ALOHA 2（项目）：$27k 双臂，diffusion policy 部署真机。
  • Mobile ALOHA：移动版双臂。
  • DROID（数据集）：50 采集员跨三洲，76k 轨迹、350h、564 场景、86 任务。

(2) 跨本体 schema 归一化（OXE 范本）：Open X-Embodiment（项目）把 22 种机器人本体统一成一套 schema，1M+ 轨迹、21 机构、527 技能/约 16 万任务。这是具身侧"跨本体数据归一化"的范本，对 AD 直接同构可迁移。

OXE schema 的存在理由是跨本体训练的前提是 schema 统一。不同机器人本体关节数、动作空间、传感器配置不同，硬拼训练不出通用策略。OXE 定义了统一字段（observation/action/reward/...），让 22 种本体的数据能共训。这和 AD 的"多车型/多传感器归一化"是同构问题。反事实：不统一 schema，每家机器人公司各搞一套数据格式，跨本体训练永远不可能。
OXE 是读者最该从具身侧借鉴到 AD 的东西。AD 多车型/多传感器/多区域车队的"数据格式归一化"是同构问题，OXE schema 设计可直接迁移。读者自家业务如果还在为"每个车型一套数据格式"头疼，去读 OXE 论文（arXiv 2310.08864），把"跨本体字段标准化"做成 AD 数据闭环的第一个产品模块。读者校准显示这块对应"产品方案结构化（场景矩阵+共性能力）" practiced，要升级到 can-decide。

模板六段详解

  1. 边界句三段：In Scope（这个产品管什么）、Out of Scope（这个产品不管什么但相关）、Non-Goals（明确不做的事）。这是治理型 PRD 的第一道防越界。JoyDrive organization-prd 范例："组织管人/项目/角色/配额；资源管资源对象/调度；监控管运行状态"——一句话定义清楚谁管什么，技术想越界都难。
  2. 状态转移表：每个对象的状态用 mermaid stateDiagram-v2 + 跳转矩阵显式定义。每个跳转要写：from→to、trigger（什么触发）、guard（前置条件）、side-effect（副作用/副作用是否同事务）。doc17 范例：Hook 触发时机 + 状态锁/车辆锁/时间锁三把锁 + Orphan/Conflict Edge Cases。读者 doc02 当前是"状态清单"而非"状态机"——升级到状态机要补"跳转条件 + 副作用"。
  3. 变更单 schema：高危且不可逆的操作（负责人变更、角色调整、GPU 配额、Namespace 绑定）必须走 Draft→PendingApproval→Approved→Executing→Succeeded/Failed/Cancelled。审批人≠申请人、失败整单回滚不在原单重试（复制为新单带 retry_parent_id）。
  4. 审计字段契约：双层审计——AuditRecord（业务动作）+ OpsAuditRecord（平台动作）。字段含变更前值/变更后值 JSON 快照、影响项目、影响责任人、关联变更单 ID。只追加不修改，导出动作本身也写一条审计。
  5. SLA 数值：不是"快"是"<2s P99"。不是"高可用"是"99.9% monthly availability"。SLA 必须有数值才能监控、告警、对账。
  6. 失败模式矩阵：每个外部依赖/API/状态跳转都要列：降级（依赖挂了怎么办）、限流（流量尖峰怎么办）、重试（瞬时错误怎么自愈）、幂等（重复请求怎么处理）、补偿（业务事务失败怎么补）、回滚（变更出错怎么回）。
治理型 PRD 模板的存在理由是把"业务描述"升级为"治理结构"——这是读者校准显示的最大短板（治理结构 introduced）和最大高估（影响力 practiced）的统一解药。读者校准原话："你的设计是'业务描述'而非'治理结构'。doc02/05/10 你提了状态机、血缘追溯、规则版本化的概念，但都标为'平台待完善项：黄子晋(Rickroll)'——你把治理结构的定义权让渡给了平台方。" 用这套模板重写设计，反对声一来技术执行的是流程不是"听产品的"。反事实：不写治理结构，下次数研负责人抵触，你还是回到人治拉锯。
这是本教材最重要的实操模板。立刻做（本周）：挑一个正在推的设计（建议数据资产管理 doc12），强制用六段模板重写。对照 JoyDrive doc/organization-prd.md 逐节抄结构。本月做：把这份模板文档化成可复用模板，每次写新 PRD 都套用。关键认知：治理结构能力不是"口才"，是"用流程把协同变成系统强制"的工程能力。这是读者从 PM 跨到 Function Owner 唯一不能跳过的一步。
