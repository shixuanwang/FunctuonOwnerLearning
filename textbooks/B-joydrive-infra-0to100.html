① 一句话定位与它解决什么

JoyDrive-Infra 是一套自动驾驶"数据 → 实验 → 训练 → 评测 → 交付"的可复现、可审计闭环平台，建在 K8s + PostgreSQL + Determined 之上，跨越京东云控制面与郑州隔离 GPU 网。它解决的不是"如何训一个模型"，而是"半年后这版模型上了车出事，能不能反查出当时用了哪批数据、哪段代码、谁批的交付"。

系统强制把每一跳的产物都固化为"不可变引用 + 血缘边"，把"可交付"定义为"通过血缘校验"。一切设计——状态机、变更单、审计、Outbox、对账 Reconciler——都是为了让这条因果链在 6 个月后依然可信可查。

下面从 0（产品骨架）走到 100（GPU 节点的 DiskPressure 怎么处理），按"先因果后术语、先模型后实现"的顺序展开。

② 产品视角：8 工作区 / 主旅程 / 状态机 / RBAC / 变更单 / 审计

2.1 用「事实归属 + 权限边界」而非「页面」切分 8 个工作区

JoyDrive 不按页面切，而是先确定每个工作区"拥有哪些不可变事实、谁能写、归哪个领域服务"，再倒推主导航。业务侧 5 个（工作台/数据/实验/评测/交付）回答"我的产出怎么推进"；平台侧 3 个（组织/资源/监控）回答"谁能在什么项目用多少 GPU、配额和告警"。资产血缘不是一级工作区——它只是从既有对象的关系投影"下钻"进入的关联视图。

  • doc/domain-model.html：工作区到领域对象逐区列出事实归属（数据区拥有 DataProductionJob/DatasetVersion/QualityReport；实验区拥有 Experiment/TrainingJob/Artifact；交付区拥有 DeliveryRequest/Deployment）。
  • doc/architecture-design.html：Portal 入口页 + 8 工作区；组织/资源/监控拆为三个平台侧边界，避免"一个运维后台承载所有职责"。
  • doc/ui-interaction-design.html：导航只承载稳定工作区；资产血缘作为跨工作区上下文页，不进一级导航。
按页面切会让"实验页"和"数据页"都来写 TrainingJob 摘要，事实归属一旦发散，血缘回溯必然断裂。按事实归属切则强制每个对象只有一个权威写入服务，血缘校验才能成立。反事实：若血缘做成一级工作区，会出现"血缘页改对象状态"的越权写入。
"事实归属"是抽象杠杆。看到任一按钮先问"这一写落到哪个服务的哪张表、谁是权威源"，而不是"这个按钮在哪个页面"。血缘是只读投影这一点最反直觉——它看似是"资产关系的家园"，实则无写权限。

2.2 主旅程闭环：数据 → 实验 → 训练 → 评测 → 交付

主线是单向推进的可复现闭环：生产/挖掘数据 → 发布 DatasetVersion（不可变训练输入）→ 创建 Experiment（冻结 commit/镜像/超参/数据快照）→ 提交 TrainingJob 训练 → 登记 ModelPackage/Checkpoint/MetricReport 资产 → 用 EvalSet 跑评测出 EvaluationReport → 模型对比标候选 → 发起 DeliveryRequest → 负责人确认 → Deployment 执行交付。每一跳都把上一跳产物作为"不可变引用"固化，从而任一交付版本能反查全部上游。

  • doc/ui-interaction-design.html：PRD 业务流程主线（实验创建→选数据版本→训练→产物登记→评测→结果对比→交付）与支线（数据生产/挖掘→样本复核→质检→发布→DatasetVersion）。
  • doc/prototype/experiment.html：实验详情标签固定为 配置/训练状态/日志/指标/资源/输出资产/评测/审计；按钮区含 终止/克隆/重跑/发起评测/申请交付/查看资产血缘。
  • doc/prototype/delivery.html：交付记录固化链路 申请提交→血缘校验→等待补充→交付信息确认→Delivering/Delivered，每步带操作者和时间。
  • doc/architecture-design.html：主写入数据流五段——dataset 创建 DataProductionJob→Outbox→workflow；metadata 创建 Experiment 快照→cluster 提交 TrainingJob；eval 写 EvaluationReport；deploy 调 metadata 做血缘校验。

这套闭环的存在理由是自动驾驶交付的"可复现 + 可审计"强约束。把每一步产物固化为不可变引用，就是为反查留链路。反事实：若 Experiment 允许提交后改超参，TrainingJob 的结果就和"记录的实验配置"脱钩，复现失败时无法定位是代码问题还是配置被篡改。
关键区分：Experiment = 不可变配置快照（What you intend），TrainingJob = 一次执行实例（What you ran）。一次 Experiment 可派生多个 TrainingJob（重跑/克隆），但 Experiment 本身冻结。这是"复现"概念在数据结构上的落地。

2.3 状态机：状态决定按钮、风险提示、是否需要审批

JoyDrive 的状态不是展示标签，而是"决定这个状态下哪些按钮可点、风险提示显示什么、是否需要审批"的控制变量。每类对象有显式状态枚举和允许动作矩阵。

  • DeliveryRequest：Draft 可编辑/提交；Submitted 可撤回/补充/确认/取消；Delivering 只能查看执行；Canceled 只能归档（doc/prototype/delivery.html 把六态画成状态轨迹条）。
  • Experiment 是极端情况——无 Draft 态（草稿在 ExperimentDraft 层处理），创建即不可变，所有状态下都禁止编辑字段，要变更只能克隆派生新 Experiment（doc/ui-interaction-design.html）。
  • TrainingJob 8 态含 Paused（用户主动暂停）和 Preempted（被高优任务抢占，Determined 自动从最近 checkpoint 续训，仅查看不可手动操作）。
  • ChangeRequest：doc/organization-prd.md §7.5 完整状态机 Draft→PendingApproval→Approved→Executing→Succeeded/Failed/Cancelled。

状态机前置定义的好处是按钮规则一处确定，前后端不漂移：前端按状态渲染按钮，后端按状态校验合法性，双重保险。反事实：若状态是"软标签"，会出现 Submitted 态还能改候选模型、Delivering 态还能撤回这种破坏血缘的操作，交付审计链断裂。
Preempted 态是难点：它不是失败而是"被抢占后自动续训中"，所以页面禁止手动操作（不能强制重试也不能取消），只让 Determined 调度器续训。状态机不只编码业务流转，也编码"系统自治 vs 人工干预"的边界。

2.4 RBAC：全局角色 + 项目内角色二级 + 权限快照克隆

权限模型分两层。第一层 GlobalRole 是固定枚举（Admin/SRE/ProjectOwner/Researcher），不可由用户新建；第二层用户"加入某项目"时，按其 GlobalRole 对应的 PermissionTemplate克隆出 ProjectMember.permissions 字符串数组快照。这样后续可通过 ChangeRequest 单独增删某条权限，不影响全局模板。权限字符串格式 <domain>:<action>（如 experiment:create），不允许通配符。MVP 砍掉 Team 实体（D6），用户↔项目走多对多，一个用户可在 A 项目当 Owner、B 项目当 Researcher。

  • doc/organization-prd.md §0.2 D1：全局角色是固定枚举；用户加入项目时按模板克隆生成 ProjectMember.permissions 快照，后续可通过 ChangeRequest 单独增删某条权限。
  • doc/organization-prd.md §6.1：权限字符串词表 experiment:create/read/approve、template:*、quota:read、audit:read/export；不允许通配符。
  • doc/organization-prd.md §5：角色权限矩阵——SRE 默认全局只读（D4）；项目负责人只读本项目成员/配额/队列授权；算法工程师只看所属项目。
"模板克隆成快照"是为了解耦：项目内权限可个性化调整而不污染全局模板，全局模板升级也不反向覆盖已个性化项目。禁通配符是为了审计可枚举——审计日志能精确说出哪条权限被授予/撤销。砍 Team 避免部门/二级组织树这类半成品标签带来归属二义性。反事实：若用通配符 experiment:*，审计时无法区分 create 还是 approve 被滥用。
"权限快照克隆"反直觉——直觉是"运行时查模板"。但快照的意义是时间冻结：审计能还原"当时这个人当时拥有哪些权限"，即使模板后来改了。这和审计只追加不修改是同一设计哲学。

2.5 ChangeRequest 变更单：申请-审批-执行-回滚四段式

组织域的关键操作（负责人变更、项目内角色调整、GPU 总配额调整、资源池/队列授权、Namespace 绑定）不能直接改库，必须先生成 ChangeRequest：Draft→PendingApproval→Approved→Executing→Succeeded/Failed/Cancelled。审批人≠申请人（D3，统一由平台管理员审批）。执行原子保证，失败整单回滚到 Failed；不在原单重试，必须"复制为新单"并带 retry_parent_id 指向旧单（保留审计血缘）。

  • doc/organization-prd.md §0.1：MVP-1 以"直接生效 + 强审计 + 关键操作走变更单"为原则。
  • doc/organization-prd.md §8.6：失败与重试——执行失败时整单回滚；不在原单上重试；用户基于失败单"复制为新单"，新单 retry_parent_id 指向旧单，便于审计血缘。
  • doc/organization-prd.md §4.2：创建项目时 Namespace 绑定、初始 GPU 配额、初始池/队列授权与项目创建在同一事务内生成首批 ChangeRequest 并自动审批通过，避免冷启动死锁。
把"高危且不可逆"的操作纳入审批和回滚，避免单人误操作毁掉整个项目的训练能力。retry_parent_id 保证失败重试不丢审计血缘。创建项目首批变更单自动审批通过是个反例设计：若死守审批流程，新项目冷启动会卡死（没配额就没法跑实验）。反事实：若允许原单重试，审计会看到同一单多次执行结果，无法判断哪次成功。
"不在原单重试，复制为新单"对习惯"重试同一个请求"的读者很反直觉。审计要求每条记录代表一次确定性的执行尝试。原单 Failed 已是终态事实，重试是"另一次尝试"，必须是新记录。这和 Experiment 不可变、克隆派生新 Experiment 是同一思想。

2.6 双层审计：AuditRecord（业务）vs OpsAuditRecord（平台）+ 只追加不修改

审计分两类：AuditRecord 记业务动作（实验创建/终止、数据发布/废弃、评测发起、交付提交/确认/取消）；OpsAuditRecord 记平台动作（成员变更、配额授权、队列授权、节点处置、平台 Job 终止/重试、告警规则变更、告警处置、审计导出本身）。两类都只追加不修改，导出动作本身也写一条审计（防导出泄密无据可查）。项目负责人只看本项目审计，平台管理员和 SRE 看全量，只有平台管理员可导出。

  • doc/architecture-design.html：业务动作写 AuditRecord，平台动作写 OpsAuditRecord，审计记录只追加不修改，导出动作也写审计。
  • doc/organization-prd.md §6.2：OpsAuditRecord 字段含变更前值/变更后值 JSON 快照、影响项目、影响责任人、关联变更单 ID、关联资源/监控 URL、最近导出时间/批次 ID。
  • doc/organization-prd.md §9.3：项目负责人只能看本项目相关审计；平台管理员和 SRE 看完整记录；只有平台管理员可导出。
双层审计的存在理由是"业务事实"和"平台治理"分离：业务审计回答"这版模型怎么来的"，平台审计回答"谁给了这个项目 256 卡时"。只追加不修改是审计可信的根基——一旦可改，审计就失去证据效力。导出动作也写审计是闭环：否则有人批量导出敏感审计后无据可查。
"只追加不修改"和 Event Sourcing、不可变 Experiment、变更单不重试是一脉相承的——系统状态是"事件序列的折叠"，任何修改都是新事件而非覆盖。这条贯穿全平台，是理解 JoyDrive 的认知钥匙。

2.7 边界约束：血缘校验是交付的强制门禁 + 平台不让用户绕过

交付前 deploy-service 必须调 metadata-service 做血缘校验：候选模型能否反查到训练数据版本、评测数据版本、代码 commit、TrainingJob、评测报告，缺一不可提交 DeliveryRequest。同时平台封堵绕过路径——用户不能绕过 Portal/API 直接创建训练 Pod 或任意 kubectl；外部系统（Determined/K8S）状态不作为唯一事实，必须同步回平台并对账。

  • doc/architecture-design.html：metadata 负责血缘校验，交付前必须能反查数据、代码、参数、训练任务、模型包和评测报告；用户不能绕过 Portal / API 直接创建训练 Pod 或任意 kubectl；外部系统状态不作为 Portal 唯一事实，必须同步回平台服务并对账。
  • doc/ui-interaction-design.html：缺少 Ready 评测报告、候选模型被 Blocked、权限不足、目标环境或风险说明缺失时禁止提交（交付申请异常）。
  • 资源页 K8S 安全封装：只展示平台任务相关对象，支持查看事件/日志/资源申请/调度原因/终止/重试平台 Job，不开放任意 kubectl 操作。
  • 项目审计辅助视图的业务风险记录含：疑似绕过平台登记、血缘缺失、使用废弃资产、交付材料缺失——把绕过行为纳入风险监测。
血缘校验门禁是"可交付"的硬定义：没通过校验的模型不允许出车端。封堵绕过是为了"平台是唯一事实源"——若允许 kubectl 直接建训练 Pod，就会出现没有 Experiment 记录的孤儿训练，血缘账本失效。对账机制同理：Determined 状态漂移必须同步回 cluster-service，否则平台显示 Succeeded 但实际已 Failed，决策错误。
"平台是唯一事实源"是个需内化的原则：外部系统（K8S/Determined/Rancher）只是执行底座，平台不把它们的态当事实，而是定期对账拉回。这解释了为什么架构里有大量"对账任务"——cluster 对账 Determined/K8S Job、dataset 对账文件 URI、deploy 对账 DeliveryRequest 状态。

2.8 跨页跳转的「上下文契约」

所有跨工作区跳转必须通过 URL Query 携带白名单参数（project_id / change_request_id / pool_id / queue_id / namespace / audit_id / user_id / from），前后端用同一白名单。业务任务→组织页必须带 project_id+from；组织页→资源/监控必须带 project_id；审计详情可由 audit_id 单参直达。原型 doc/prototype/js/app.js 用 jumpMap 集中管理 11 个工作区跳转，确保入口收敛（doc/organization-prd.md §8.11）。

这是"契约先于实现"的范例：跳转协议在 PRD 层定义为白名单表，前端 jumpMap、后端路由、审计 URL 生成全部消费同一契约。改协议等于改 PRD，不是改代码。

③ 工程视角：13 entrypoint / 服务拓扑 / BFF 读写分离 / 调用链

3.1 服务拓扑与端口约定

系统由一组同命名空间微服务组成，每个服务一个 cmd entrypoint。关键服务及其监听端口：

  • cmd/web-service：BFF（:8080），唯一对 Portal 暴露的入口，做鉴权 + 读聚合 + 写转发。
  • cmd/identity-service：身份/会话/RBAC。
  • cmd/metadata-service：血缘账本与对象摘要（Artifact/Checkpoint/ModelPackage/MetricReport/EvaluationReport），交付前血缘校验执行方。
  • cmd/data-service：数据工作区（artifact/package/frame 三级 + 三位置同步），独占独立 PG 实例。
  • cmd/workflow-service：消费 ExperimentCreated 事件→向 cluster 请求 TrainingJob。
  • cmd/cluster-service：对接 Determined，提交/对账训练任务。

3.2 BFF 的读写分离与外部代理原则

BFF（web-service）既是读聚合层（合并多服务返回给前端），也是写鉴权层（注入身份头转发到权威服务）。关键原则：

  • 外部系统状态不作为 BFF 唯一事实，必须同步回平台服务并对账。
  • 对 data-service 等带 Push Token 的无认证代理：BFF 注入 system 身份（带 Push Token），再转发（doc/data-artifact-push-guide.md）。
  • 对评测推理链，BFF 注入 X-Inference-User 头透传调用者身份（services/web-service/evaluation_data.go L64-86）。

④ 训练：Determined / 提交 / 回调 / Agent Gateway

4.1 Determined 是实验调度层，不跨集群调度 Pod

Determined Master 部署在 local 集群（rancher-02 上一个 K8s Pod），通过同一隧道代理调度训练 Pod 到郑州的 default namespace，按节点标签 joydrive.jd.com/gpu-type=h20|h800 + pool=formal|debug 选择节点（doc/k8s-cluster.md L88-104）。Determined 不跨集群调度——它在每个 Rancher 集群内部用节点标签做资源池映射。

4.2 提交训练任务：从 ExperimentCreated 到 TrainingJob

  1. 用户创建 Experiment → metadata-service 在业务事务里写 experiments 表 + outbox_events（migrations/0001_init.sql L173-182）。
  2. AFTER INSERT 触发器在 commit 后调 pg_notify('platform_outbox', row_id)（migrations/0001_init.sql L281-292）。
  3. workflow-service 持有专用连接 LISTEN 'platform_outbox'，收到通知 SELECT outbox 行、按 topic 过滤 ExperimentCreated、转发到本地 platform.Bus（internal/platform/eventbus/listener.go）。
  4. workflow-service 消费 ExperimentCreated → 调 cluster-service 请求 TrainingJob（services/workflow-service/server.go L23-52）。
  5. cluster-service 提交到 Determined，并周期对账 Determined/K8S Job 状态（设计契约；当前实现是纯事件驱动 + UNIQUE(experiment_id) 防重，migrations/0001_init.sql L296-299）。
核心权衡是"NOTIFY 在 commit 后才发"——这把"业务事务原子性"和"事件通知"绑在一起。读者容易误以为 trigger 在 INSERT 时立即 NOTIFY（实际是 commit 时），这恰恰是 transactional outbox 模式的精髓。重放机制是"at-least-once"语义的兜底——消费方必须幂等。

4.3 训练回调：从 Determined 状态到平台血缘

训练完成时，cluster-service 把 Checkpoint/Artifact 摘要和血缘边回写到 metadata-service（doc/architecture-design.html L547-563 主写入数据流第三段"产物登记"）。这条血缘边就是后续交付校验的反查依据。状态机：TrainingJob 8 态——Queued/Scheduled/Running/Paused/Preempted/Succeeded/Failed/Canceled。其中 Preempted 由 Determined 自动从最近 checkpoint 续训，平台仅展示不可手动操作。

4.4 Agent Gateway：Zero Trust 设计 vs 落地度 0%

doc/determined-agent-gateway.md 设计了 Zero Trust 架构：agent↔proxy(mTLS, Hop2 本地)↔gateway(mTLS, Hop1 公网)↔master(DET_SESSION_TOKEN, Hop3 端到端)，3 跳凭证制 + OPA ext_authz 基于 SPIFFE 证书 SAN 做 agent_id+resource_pool+route 三级授权。

但 doc/k8s-security.md 实测：这套设计落地度约 6%——Envoy+OPA 未部署（NotFound）、4 个设计 Secret 全不存在、agent 无客户端证书 volume、CATTLE_INSECURE=true 跳过校验、:2000 全程 HTTP 明文，mTLS Total Implementation: 0%（doc/k8s-security.md L224-234）。当前生产环境接受这个风险（内网+CDN 网络层防护），但 P0 风险真问题：doc/k8s-security.md L39-47 列出 P0-1 Rancher 引导弱密码 admin、P0-3 DB 密码硬编码 postgres、P0-7 Det /info 无认证公网泄露、P0-8 Det login 公网暴力破解面。

最有价值的是"设计文档 ≠ 实际状态"的认知。读者做架构判断时分清三层：设计意图（doc/）→ 部署清单（manifests/）→ 运行时实际（kubectl get/ss/openssl）。审计方法是"从运行时反推"，而非"从文档正推"。这是 Function Owner 必备的判断力。

⑤ 评测：行云缺陷 → 自动触发推理 → 状态回填

5.1 闭环总览：从缺陷到推理结果的一条自动链路

评测数据服务（evaluation-data-service，:8087）把 QA 在行云缺陷平台登的缺陷单，自动变成 Prefect 推理流水线的输入。机制是：行云缺陷先被定时同步落库，QA 在 Portal 勾选已回传的 mcap 文件做"准入"，准入只把数据行打个"待触发"标记，真正的推理触发和状态回填由后台 goroutine 异步完成。这样用户点完"准入"立刻返回，不用等几十秒的 Prefect 调用（doc/evaluation-data-service.md L8-15）。

5.2 准入的事务边界：advisory lock + 首写优先 + 评论回写非阻断

准入要做三件事且必须原子：写 defect_records、为每个 mcap 写一行 eval_data、回写行云评论。两个 QA 可能同时点同一缺陷。解法：事务里 SELECT pg_advisory_xact_lock(hashtext(defect_id)) 串行化；再用 (defect_code, data_package) 唯一约束 + ON CONFLICT DO NOTHING 实现"首写优先"——后到的 import 跳过、不重复写评论。评论回写放在事务外，失败只记 comment_error，绝不回滚准入（services/evaluation-data-service/repository.go L300-391；services/evaluation-data-service/handlers.go L735-772）。

pg_advisory_xact_lock 是 PG 特有：锁的不是某行数据，而是一个整数 key（这里用 hashtext(defect_id) 把字符串压成整数）。事务结束自动释放，不会泄漏。这是"我只想串行化一段逻辑、又不想加一张锁表"的惯用法。比 FOR UPDATE 行锁更关键，因为缺陷可能尚未落库，FOR UPDATE 锁不住不存在的行。

5.3 后台 worker 的节流：per-tick 上限 + 抢占式 claim + 重试退避

后台 worker 每 15s 一个 tick，先触发后回填。节流三层：(1) 每 tick 最多触发 5 个、最多回填 20 个；(2) 两次提交间隔 500ms；(3) 同一行触发用"条件更新"抢占——UPDATE ... WHERE pipeline_status='PENDING_TRIGGER'，看 tag.RowsAffected()==1 才算抢到。提交失败不立刻判死，retry_count++ 后退回 PENDING_TRIGGER，最多 3 次才落 TRIGGER_FAILED，一次网络抖动能自愈（services/evaluation-data-service/pipeline_worker.go L11-19、L38-72；services/evaluation-data-service/pipeline_repo.go L181-223）。

"抢占式 claim = 条件 UPDATE + 看 RowsAffected"是无分布式锁去重的核心模式。记住口诀：任何"我想确保一段副作用只执行一次"的场景，都先想能不能用一条带 WHERE 的 UPDATE 来做。比 SELECT FOR UPDATE 轻，比分布式锁简单。

5.4 两级状态语义：顶层 state vs progress.stage（避免过早显示"已完成"）

Prefect 的 onboard 主 flow 一跑完，顶层 state 就翻 COMPLETED，但 onboard 只是整条链（onboard → offboard → download）的第一段。如果直接用顶层 state 当 UI 状态，评测数据会过早显示"已完成"。GetStatus 优先取 progress.stage：只有当 download 也 COMPLETED 才报 COMPLETED。stage 是 0/3、1/3、2/3、3/3 的进度串，由调度服务沿子 flow 链逐级探测得到（services/evaluation-data-service/prefect.go L131-138；services/prefect-scheduler/client.go L386-429、L518-531）。

关键认知：UI 状态要映射到"用户关心的事件"（整链完成），而不是"系统内部的事件"（某一段 flow 完成）。progress.stage 就是为这个映射专门设计的二级字段。

5.5 状态回填的容错：瞬时错误保留原值、未知状态不覆盖

worker 回填时对 prefect GET /api/status 调用失败直接 continue，保留当前 pipeline_status 不动，下个 tick 再试。prefect 返回的状态串经 normalizePipelineState 映射成 SCHEDULED/RUNNING/COMPLETED/FAILED；映射不出（空串）的也跳过，避免把缓存的好状态用未知值覆盖。ListActivePipelines 只捞非终态行，终态行不再轮询，省 Prefect API 调用（services/evaluation-data-service/pipeline_worker.go L74-95；services/evaluation-data-service/pipeline_repo.go L231-251）。

5.6 专用自动触发路径 /api/eval/submit：与手动提交解耦、带 defect 溯源

prefect-scheduler 给 eval-data-service 开了专用接口 POST /api/eval/submit，不复用面向用户的 /api/submit。区别：(1) 只收单个 mcap key；(2) 必带 defect_code 作为 source，让这次触发在"提交历史"里能溯源到具体缺陷；(3) 同步返回 flow_run_id + batch_id。手动批量提交走 /api/submit 的异步队列（5 worker、200 容量、满返回 503）。自动触发走同步路径，因为 worker 自己已做节流和重试（services/prefect-scheduler/handlers.go L225-293；services/evaluation-data-service/prefect.go L41-98）。

"同一类操作（提交推理）开两个接口"不是冗余，是"调用方语义不同"。手动要异步（用户不等）、要批量；自动要同步（worker 需要 id 回填）、要单条。接口分离让两边的容错策略（重试、限流）各自演化，不互相污染。

5.7 部署踩坑：xauto-discovery / Prefect PG 独立 / Ingress 僵尸 Pod

Prefect 流水线在生产里踩过三个工程坑并固化成设计（doc/prefect_deployment.md）：

  1. xauto-discovery.jd.com 解析到两个内网 IP，K8s 集群只通其中一个且要 Host 头，用 hostAliases 把域名钉死到可通 IP（L14-31）。
  2. Prefect Server 和主业务共享 PG 导致 CPU 打满超时，给 Prefect 部署独立 PG（L33-42）。
  3. Ingress Controller 出现僵尸 Pod（containerd 丢状态），单副本扛全站流量间歇性不响应，强制清理并扩到 2 副本（L44-63）。
这类"部署踩坑文档"是判断一个系统成熟度的金矿。读法是看"根因"一栏——共享资源打满、僵尸 Pod、编译时 vs 运行时配置，这些是分布式系统的经典反模式，会跨项目复现。

⑥ 数据闭环：artifact 三级 / 血缘 / Outbox 三件套

6.1 三级对象模型 Artifact → Package → Frame

为了让外部数据管线能用最小动作上报又能在前端浏览到帧级，把一个"数据版本"拆成三层：最外层 Artifact（一个版本，全局唯一版本号即主键值 artifact_id）、中间 Package（按场景打包的目录，一个 artifact 几十万包）、最里层 Frame（一包里几千个 .zst 帧文件，全表可达数亿行）。包级做"拥有/未拥有"判定和差异对比，帧级做精确索引。migrations/data/0002_data_artifacts.sql L4-59 三表 + frames 按 package_id HASH 分 32 区。

HASH 分区按 package_id 散列，让"某包的帧"物理上聚在一个分区，写入和查询都只动一片，正是 CopyFrom 批量写和按包浏览能扛住数亿帧的关键。反事实：若按 artifact_id 分区，同一 artifact 的所有帧挤在 1 个分区，热点直接打爆。联合主键 PK(frame_id, package_id) 不是冗余，是 PG 分区表硬性要求——分区键 package_id 必须出现在主键里。

6.2 固定三位置同步模型：location × package 矩阵 + CFS/S3 非对称上报

同一份数据落在三个固定位置（北京 CFS=源、郑州 CFS=跨地域、S3 训练桶=整包）。系统维护 (location_id, package_id) 矩阵表 artifact_location_packages：行存在=该位置拥有该包。CFS 位置上报每包实际帧数 frame_count，S3 位置只上报整包大小 frame_count=0；同一包在两个 CFS 位置的帧数不一致，前端标红告警。total_synced_packages 是这张矩阵的 COUNT 缓存，专门给前端进度条做 O(1) 渲染（doc/data-artifact-registry-design.md L111-148；migrations/data/0002_data_artifacts.sql L65-88）。

读者常困惑"frame_count=0 到底算同步了吗"。答：行存在即代表同步，frame_count 只承载"一致性强弱"，S3 故意记 0 让前端显示"-"而非误报缺帧。(xmax = 0) 是 PG 技巧——INSERT...ON CONFLICT...RETURNING 时 xmax=0 表示真 INSERT（新行），用来区分"新增同步"还是"刷新已有"，避免 total_synced_packages 重复自增。

6.3 两接口幂等推送：管线只调"注册版本"+"推送包"

外部管线接入只需两个 HTTP：POST /api/data-artifacts/（注册版本 + 声明一个 location）和 POST /api/data-artifacts/{version}/packages（推送一个包）。注册可对同一 version 多次调用，每次追加位置（幂等）；推包时同 package_name 重复推送是"追加帧"而非报错，frame_index 用 MAX(frame_index)+1 自动续号（doc/data-artifact-push-guide.md L4-5、L237-238；services/data-service/repository/data_artifacts.go L557-604）。

6.5 Outbox + pg_notify + LISTEN/Replay：可靠事件分发的实现骨架

跨服务推进（实验创建→训练提交、训练完成→评测、评测完成→交付）不能靠 RPC 直连。做法：业务事务里把业务表和 outbox_events 表一起提交；提交时一个 AFTER INSERT 触发器调 pg_notify('platform_outbox', row_id) 把行 ID 推给所有 LISTEN 的连接。每个消费服务起一个 eventbus.Listener，独占一条连接 LISTEN，收到通知回查 outbox 行、按 topic 过滤、发到进程内 platform.Bus。LISTEN/NOTIFY 是 at-most-once（断线期间的通知会丢），所以每次重连都先 replay outbox WHERE created_at > last_seen，冷启动 floor=now()-5min（migrations/0001_init.sql L173-294；internal/platform/eventbus/listener.go）。

模型先行读者常误以为"消息队列"就是 Kafka/RabbitMQ。这里的关键认知：PostgreSQL 的 LISTEN/NOTIFY + 一张 outbox 表，就是一个进程内的"事务性消息队列"，省掉了一个独立中间件。三层抽象：(1) 触发器在事务里写 notify（notify 只在 commit 后才发）；(2) Listener 收到 notify 后回查 row 拿 payload；(3) replay 弥补断线窗口。三层缺一不可。

6.6 Reconciler 对账 + 幂等键：闭环的"最终一致"兜底

两层兜底：(1) 幂等——每个 POST 写接口要求 idempotency_key，目标服务按 event_id 和 business_key 去重。data-service 推包用 ON CONFLICT、training_jobs 用 UNIQUE(experiment_id) 防重（migrations/0001_init.sql L184-193、L296-299）。(2) Reconciler——cluster 对账 Determined/K8S Job，dataset 对账文件 URI/checksum，deploy 对账 DeliveryRequest 状态，metadata 扫描悬挂血缘引用，超过重试次数进 dead_letter 表并告警。注意：当前 workflow-service 实现是纯事件驱动 bus 消费，尚未落地周期 ticker Reconciler——这是设计 vs 实现的真实缺口（services/workflow-service/server.go L23-52）。

读者要警惕"文档说了就算实现"的陷阱。doc/architecture-design.html L578-596 描述的 Reconciler/dead_letter 是目标架构，但 workflow-service 当前实现只有事件消费没有 ticker。这种"设计先行、实现追赶"是大型平台常态，正是 Function Owner 要会读的"契约 vs 交付"差距。

6.7 DB 物理隔离：data-service 独占 PG 实例

为不让数据生产那种"数亿帧、HASH 分区、高频 CopyFrom"的写入压力污染平台主库，把 data workspace 所有表放进独立 PostgreSQL 实例（data-db namespace），由 data-service 独占连接。平台主 repository 保持单 pool repository.New(pool)，绝不 import data sqlc 或 data repository；platform.Store 接口不含任何 data workspace 方法。迁移用单进程双 URL：DATABASE_URL→migrations/，DATA_DATABASE_URL→migrations/data/（doc/data-service-db-isolation-plan.md L5-22、L32-53；migrations/data/0001_data_workspace.sql L1-2）。

7.1 三端点 webhook + 四阶段 CI/CD

一个仓库同时承载 release/devel/test 三条线。做法：暴露三个独立 ingress 路径（VALID_PATHS = {三个端点}），每个路径对 payload 校验不同——release 仅接受 devel→release 的 merge_request 且 action=merge；devel 接受任意→devel 的 merge；test 仅接受 push 且最新 commit 必须带 [cicd] 标记。webhook-server.py 的 if/elif 分支把请求转译成一个 batch/v1 Job（manifests/cicd.yaml L120、L187-243）。Job 跑五阶段：STAGE1 checkout+setup → STAGE2 db migrate → STAGE3 go vet+build → STAGE4 docker build+push → STAGE5 deploy（manifests/cicd/pipeline.sh L241/564/627/708/727）。

per-branch 去抖：dedupe_key = path + ':' + branch 做 3s 窗口去抖，避免两个 test 分支同时 push 互相抑制；LAST_TRIGGERS 还有 60s 清理（manifests/cicd.yaml L245-265）。STAGE5 部署目标：release→joydrive ns（Fleet CD）、devel→joydrive-devel、test→joydrive-{br} ns + 24H TTL。

7.2 脚本分层：frozen bootstrap + branch-traveling pipeline

CI 脚本本身要能迭代，但又必须能跑通 CI（鸡生蛋）。切成两层：bootstrap.sh 极薄且冻结在 ci-script ConfigMap（改它需要 merge），只做三件事——每 job 独立 clone、checkout 目标分支、exec 仓库内 pipeline.sh；真正的五阶段逻辑随分支走（manifests/cicd/pipeline.sh 注释 'travels with branch'），新功能只改 pipeline.sh 就能在该分支生效，不必动 ConfigMap（manifests/cicd.yaml L19-94；doc/k8s-lessons.md L78 自更新段）。

7.3 并行 Job 隔离：mktemp 独立 clone + git --reference 共享对象库

多个 CI Job 同时跑会抢同一份 checkout。解法：BUILD_DIR=$(mktemp -d /src/.ci-${CI_MODE}-XXXXXX) 每 job 独立 + git clone --reference '$POD_SRC' 共享 git objects 接近 instant；stale-dir cleanup 60min 后清旧目录（manifests/cicd.yaml L31-58）。不能 fallback 到 host，注释明确 'would corrupt git state'。早期 bug：旧设计按 CI_MODE 共用 1 个 clone 目录，作者被迫让 Go build 读宿主机代码——结果宿主机 stale 时新 tag 镜像里是旧 binary（doc/k8s-lessons.md L244-280）。验证手段：kubectl exec ... strings /usr/local/bin/web-service | grep <feature> 直接验镜像内 binary 内容。

7.4 AI coding 纵深防御：绝对禁令 + 2 步预检 tag + bash wrapper

  1. 语义层——AGENTS.md 顶部 ABSOLUTE PROHIBITIONS 列出 6 条铁律（rm -rf、pull 公网镜像、killall -9、systemctl restart rke2/docker stop unknown、kubectl delete --force 无备份、git commit、改生产 config/iptables/network/system），声明 override 所有其他指令。

7.8 GPU 多集群管理：三集群拓扑 + remotedialer WSS + 按标签调度

训练 GPU 在郑州隔离网（10.24.60.x，GFW 阻断 443），Rancher 控制面在京东云。拓扑：local 集群（Rancher Server）+ gpu-cluster-00（L40S）+ gpu-cluster-zhengzhou（H20+H800 一体化 37 节点 288 GPU）。managed cluster 上的 cattle-cluster-agent 主动发起 remotedialer WebSocket（wss://，agent 源码硬编码，CATTLE_INSECURE=true 跳过证书校验）出站到 CDN :2001（TCP Stream 模式）→ Envoy → Rancher（doc/k8s-cluster.md L62-66、L82、L152-161）。

Determined Master 在 local 集群，通过同一隧道代理调度训练 Pod 到郑州 default namespace，按节点标签 joydrive.jd.com/gpu-type=h20|h800 + pool=formal|debug 选择节点（doc/k8s-cluster.md L88-104）。

核心心智模型是"隧道方向反转"——服务器（Rancher）想管理客户端（GPU 节点），但客户端在隔离网，所以让客户端主动出站建立 WSS，服务器把 K8s API 调用 multiplex 到这条隧道上。这是 NAT 穿透的工业实现。读者要分清：RKE2 是节点本地的 K8s，Rancher 是多集群管理层（不管 Pod 调度），Determined 是实验调度层（跨集群只通过资源池抽象）。

7.9 GPU 节点接入：CA 注入 + hostAliases + CATTLE_INSECURE 三件套

三件套：hostAliases 把 jdx-infra-rancher.jdl.cn 钉到 CDN 出口 IP；initContainer 从 tls-ca Secret 复制 CA 证书到 /etc/kubernetes/ssl/certs/serverca；CATTLE_INSECURE=true 跳过 HTTP 客户端 TLS 校验（这只作用于 HTTP 客户端，不作用于 remotedialer 的 TLS dialer，所以仍需 CA 注入）。Envoy 用 tcp_proxy 而非 TLS termination，让 Rancher 自己终结 TLS（doc/k8s-lessons.md L1241-1265；doc/k8s-security.md L165-173）。失败方案表（L1076-1090）总结了 F-K 共 6 条失败方案。

最难的是分清"tcp_proxy 透传 vs TLS termination"。前者 Envoy 不解密，只看 SNI 转发字节；后者 Envoy 解密后再加密到上游。选错会导致信任链断裂。读者应记住：agent 用 wss 直连 Rancher，中间任何"解密"都会破坏端到端信任。

7.10 RKE2/Rancher 配置路径：托管 vs 手动，别手动改托管节点

RKE2 节点配置两类：手动 rke2 server 启动的（config.yaml 可直接编辑 + systemctl restart），和 Rancher UI 创建/导入的（config.yaml.d/50-rancher.yaml 不可手改，Rancher controller 会持续回滚）。50 的含义：RKE2 按文件名字母序合并，数字越大优先级越高；Rancher 用 50 压过默认值，给用户留 51-99 做本地覆盖。JoyDrive 纪律：Rancher 托管节点配置异常时不手动改不重启，经 Rancher UI 重新注册或下发证书（doc/k8s-lessons.md L291-302）。

核心认知是"谁是 source of truth"——Rancher 托管节点的 SoT 是 Rancher controller 的内存状态，不是节点本地文件。手动改本地文件是"对抗声明式系统"，必输。正确做法是改 Rancher 的期望状态（UI/CRD），让 controller 把状态收敛到节点。

7.12 离线镜像铁律 + containerd/Docker 镜像库分裂

GPU 节点无外网（hub.jdcloud.com、PyPI、GitHub 全被 GFW/DPI 阻断），任何 docker pull/ctr pull 必超时挂起。铁律：所有镜像走 NFS 缓存逐节点 ctr -n k8s.io import 预导入，禁止公网拉取（doc/k8s-deploy.md L124-157）。两个分裂陷阱：(1) containerd 有独立 CRI 镜像数据库，ctr import 不入 CRI 库（ctr image ls 能看到但 crictl images 看不到）；(2) 磁盘 ≥85% 时 containerd GC 无差别删镜像，包括手动 import 的——必须用本地 registry (:5000) 或推到 Docker volume 抗 GC（doc/k8s-lessons.md L600-635）。

"TCP 握手成功 ≠ HTTP 能用"是 DPI 教训——不能靠 ping/curl 测连通性下结论，要测到应用层。Det entrypoint pip install 连 PyPI → DPI 拦截 → 永久挂起；解法是 PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/（L1117-1125）。

7.13 DiskPressure 三层故障 + kubelet 状态锁死

GPU 节点磁盘小（183G）+ 训练临时数据大，磁盘 ≥85% 触发 containerd GC，GC 失败时 kubelet 进入 FreeDiskSpaceFailed 锁死状态。三层故障模型（doc/k8s-lessons.md L331-348）：Layer1 磁盘满 → Layer2 kubelet GC 失败锁 DiskPressure → Layer3 critical pod 被驱逐（cattle-agent 被 evicted → Rancher Unavailable）。关键认知：即使清出空间，DiskPressure 仍不解除——只有重启 kubelet（systemctl restart rke2-server）才能强制重设。根治是迁移 kubelet/containerd 数据到 NVMe 大盘（bind-mount + rsync -aHAX --numeric-ids），并给 cattle-agent 加 DiskPressure toleration（L351-403）。

核心心智是"kubelet 状态机有粘性"——DiskPressure 一旦进入 FreeDiskSpaceFailed 就不会自动恢复，必须外部强制重设。这违背"声明式系统会自愈"的直觉。迁移后旧 root-disk 副本保留为 rollback anchors（/var/lib/rancher/rke2.pre-nvme-*），多次成功实验 + 显式变更窗口后才删——这是变更纪律。

7.14 运行时配置同步：MF 三处一致 + TTL 双标签

新增运行时配置（env/Secret/CM key）时，代码改了但 CI 部署的 Secret 没同步 → 前端 503（如 DATA_SERVICE_URL 漏注入，doc/k8s-lessons.md L104-105）。纪律（AGENTS.md L68）：新配置必须同步到三处——mfs/web-svc.yaml（运行时 Secret 模板）、mfs/cicd.yaml 的三个 web-service-env block（AUTO_SETUP + main + STAGE5 部署时）、CI 脚本。STAGE5 部署时的 sync 会覆盖 Secret，所以只改初始化路径会被刷掉，三处必须一致。TTL 标签也有双标签问题：CI 每次 push 重新部署后 TTL 仍从首次创建 ns 时间倒数——STAGE5 必须同时更新 joydrive.io/ttl-hours 和 joydrive.io/created 两个标签（L69-75）。

⑨' 训练与评测的本质总结

9.1 训练的本质：把意图冻结成不可变引用

训练系统不是"跑一个模型"，而是"把'我打算用 A 数据 + B 代码 + C 超参跑一次训练'冻结成 Experiment 这条不可变记录"。TrainingJob 只是这条记录的执行实例，可重跑可克隆，但 Experiment 本身永不改。所有血缘回写、checkpoint 摘要、metric 上报都是"挂"在 Experiment 上的——交付时反查的是 Experiment，不是 TrainingJob。

这把"训练"从"一次 GPU 计算"升格为"一次可复现、可审计的事实声明"。半年后这版模型上事故，团队能回答"用哪批数据、哪段代码、谁批的"——这是 JoyDrive 训练子系统的唯一存在理由。

9.2 评测的本质：把缺陷变成可触发、可回填、可溯源的自动事件

评测系统的核心张力是"用户期望立即反馈 vs 外部推理流水线需要几十秒"。JoyDrive 的解法是解耦：

  • 准入是同步的标记动作（DB 写一行 PENDING_TRIGGER，advisory lock 保证幂等）。
  • 触发是异步的副作用（后台 worker 每 15s 捞 5 个，抢占式 claim 去重）。
  • 回填是宽容的最终一致（瞬时错误保留原值、未知状态不覆盖、最多 15s 延迟）。
  • 状态是消费者视角（progress.stage 优先于顶层 state，避免过早"已完成"）。

同时每次推理触发都带 defect_code 作为 source，把"评测数据"和"推理执行"两条线缝起来——一次推理跑完，能反查它是为了验证哪个缺陷。这是评测系统的闭环价值。

9.3 闭环的本质：让 6 个月后的反查可信

训练 + 评测 + 数据 + 交付四条线最终汇聚到一份不可变的血缘账本。每个事实的产生（数据发布、实验创建、训练完成、评测完成、交付确认）都在同一事务里同时写业务表和 outbox_events；每个跨服务推进都靠事件 + 对账兜底而非 RPC；每个权威写入服务都只有一个；每条审计都只追加不修改。

这套设计的唯一存在理由是：让"半年后这版模型出事故，能否反查根因"这个问题有肯定答案。所有工程复杂度——状态机、变更单、advisory lock、抢占式 claim、Outbox 三件套、Reconciler 对账、独立 PG、同命名空间短名——都是为这个目标服务的。

"只追加不修改"是贯穿全平台的设计哲学：Event Sourcing、不可变 Experiment、变更单不重试、审计只追加、权限快照克隆——都是同一思想的不同投影。系统状态是"事件序列的折叠"，任何修改都是新事件而非覆盖。这条认知是理解 JoyDrive 的钥匙，也是判断力领先于实现熟练度的 Function Owner 的真正杠杆。
