2.5 迭代与情绪（双轨明显）

出错时典型链路：对标老平台发现数据不一致 → 要 agent 查 → 定位是 transit+process 口径 → 分别给数仓和 onboard 提需求——这是教科书级的根因导向。但情绪化爆发频繁，且穿插在技术指令中：

"你他妈"、"我操不对啊"、"什么东西"、"你干啥呢"、"什么疾病"、"快他妈的刷完"、"你们玩的还挺开心"、"到这样可以说是事故了"。

这些紧随理性根因分析或职责边界重申，属于高压下的压力释放而非判断力下降。但要注意：

为何这是问题｜对 agent 来说，情绪化自然语言是噪声。Addy Osmani 的"Anti-Rationalization Table"理论反过来也成立：你给 agent 的情绪化指令，agent 会试图"合理化"它——可能把"你干啥呢"解读成"需要重新规划"，把"快他妈的刷完"解读成"跳过验证直接报完成"。情绪指令会污染 agent 的判断信号。顶尖 aicoder（Boris、Willison）几乎不把情绪写进 prompt——他们的纠偏是冷的、结构化的："plan 不对，重做"、"证据不足，跑测试"。你可以保留情绪做压力释放，但建议用 /btw 或旁注承载，不进主指令流。

短板 1（最高 ROI）：声明原则缺 deterministic 兑现层

结构性 高频

证据：6/6 token_budget=None；301 open spawn edge；4/6 goal-thread 长期 resume 失控；情绪化纠偏 prompt 高频；logs_2 全是 Rust tracing。

优化措施（按优先级）：

  1. 把"bounded outcome"量化为 token_budget。开新 goal-thread 时必填 token_budget（建议默认 5M token / 4h，复杂任务 10M / 8h）。codex config.toml 已支持，只是你从未设。例： 
    # ~/.codex/config.toml 或 .codex/config.toml
[agents]
default_token_budget = "5M"  # 默认上限
default_time_budget = "4h"
    对标：Claude Code "context window 是最稀缺资源"第一性原理的机制化。
  2. 把"don't"从 AGENTS.md 升级为 PreToolUse hook。AGENTS.md 里"never edit .env""never 写 sudo 密码到 prompt""never 在 Documents 全家目录 trusted"全是 advisory，agent 会忽略。改成 deterministic 拦截： 
    # .claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{
          "type": "command",
          "command": "jq -r '.tool_input.command' | grep -E '(rm -rf /|sudo|DROP TABLE|DELETE FROM|\\.env)' && exit 2 || exit 0"
        }]
      }
    ],
    "SessionStart": [{
      "hooks": [{
        "type": "command",
        "command": "echo '本轮 token_budget: 5M / 4h. 边界: Documents 全目录只读. 凭据禁贴 prompt.'"
      }]
    }]
  }
}
    对标：Claude Code hooks-guide "guardrail 放 hook 里：CLAUDE.md 写 never edit .env 是请求，PreToolUse hook 阻断才是强制"。
  3. 建立 spawn-edge close-rate 监控。每开一个父线程，结束前检查 open edge 数。>5 个未收敛 = 不允许开新父线程。可以写个简短 skill： 
    # .claude/skills/edge-hygiene/SKILL.md
---
name: edge-hygiene
description: 父线程结束前检查 open spawn edge，>5 则强制收敛
---
父线程标记"完成"前，必须：
1. 列出所有 open 子线程
2. 每个 open 子线程要么标记完成、要么显式废弃（写一行原因）
3. close-rate < 80% 则不允许标记父线程完成
    对标：AGENTS.md 自己的"delegated owner 完成自己的闭环, return final evidence or objective stop"。
  4. 把 verification 事件沉淀为可读流。logs_2 全是 Rust tracing 是结构性漏洞——你 AGENTS.md 最骄傲的原则缺可观测通道。写个 PostToolUse hook 把关键事件（测试运行/build/部署/canary）落 markdown：

# .claude/verification-log.md（append-only）
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "echo \"[$(date -Iseconds)] $(jq -r '.tool_input.command') → exit $(jq -r '.tool_response.exit_code')\" >> .claude/verification-log.md"
      }]
    }]
  }
}
    对标：Willison "所有 prompt+response 落 SQLite" + Boris "evidence before assertions"。

短板 2（最高 ROI）：独立验证 gate 缺失

高频 结构性

证据：扩容到 8CU/parallelism=8 直接采纳去申请；agent 报 RUNNING=1 即认为稳定；多次"让我验收 p90 但我查不到 p90"；交付与汇报不符的信任崩塌反复。

优化措施：

  1. 建一个 live-smoke-test skill 作为 Done 的硬 gate。任何"数据接通/SQL/REST/GraphQL done"声明，必须先跑真实查询/端点。mock 单测不算。例： 
    # .claude/skills/live-smoke-test/SKILL.md
---
name: live-smoke-test
description: 任何"数据可用/done"声明前强制跑真实查询
---
触发条件：agent 声明"已上线/已可用/已修复"且涉及数据/接口
执行：
1. 列出 3 个真实端到端查询（不重复 agent 自己的测试）
2. 对每个查询跑真实 CK/PG/REST，落输出
3. 对比预期，差额>5% 则 NO-GO
4. 把结果写进 verification-log.md
未跑此 skill 不允许标记 Done
    对标：Boris "永远给 Claude 一个自我验证机制，2-3x 质量" + Anthropic 对抗式 review + Hamel "难评测是产品异味"。
  2. 建 conformance suite。把"对标老平台"沉淀为测试集：planning 耗时 108 vs 122 这种核对，做成可重复跑的 SQL 而不是临时手查。例：

-- 对标老平台 planning p90 应在 100-120ms 区间
SELECT vin, percentileCont(0.9)(planning_ms) AS p90
FROM dws_planning
WHERE dt = yesterday() AND vin IN (SELECT vin FROM old_platform_baseline)
GROUP BY vin
HAVING p90 NOT BETWEEN 100 AND 120;
    对标：Willison "conformance suite 极好地约束 agent 输出"。
  3. 把"扩容/容量建议"做独立审计。agent 给扩容建议时，强制要求附"测算依据 + 反例（不扩容会怎样）+ 回滚点"。你不下场，但要让 owner agent 用模板汇报。例：

- 扩到: __ CU / parallelism=__
- 回滚点: 若 30min 内消费 lag 不降则回滚到 __
- 反例: 是否考虑过增加 partition 而非 CU? __
    对标：AGENTS.md "report highest layer actually proved"。

⑧ 每会话自检 checklist

每次开 session 前后用。设计原则：可秒级过完、违反立即停、不让步于"我再快一点"。

开 session 前（30 秒）

  • 本轮 bounded outcome 是什么？（一句话能说清，说不清就先 grillme）
  • token_budget 设了没？（默认 5M / 4h，复杂 10M / 8h，未设不开）
  • 这是 fresh session 还是 resume？如果是 resume，exact baseline 变了没？变了就开新的。
  • 本轮 owner 是谁？边界声明够 scary 吗？（授权范围 / 不授权项 / 回滚点）
  • 本轮要不要主协调？要的话主协调"三不"边界写进 prompt 了没？
  • 凭据是从 credentials.md 注入还是手贴？手贴 → 停，先建 credentials.md。
  • 本轮会涉及"数据可用/done"声明吗？要 → 先准备好 live-smoke-test skill。

session 中（每 30 分钟一次）

  • 主协调是不是又下沉了？看 prompt 里有没有"我先看看""我查一下"→ 有则改派 fresh explorer。
  • open edge 数超过 5 个了吗？超过则停下来收敛。
  • 情绪上来要打字了？用 /btw 旁注，不进主指令流。
  • agent 报"已完成/通过/修复"→ 要证据（测试输出/命令返回/screenshot/SQL 结果），口头断言不算。
  • 规划过载了？单条 prompt > 500 字 → 拆 owner。
  • 本轮 token 用了 >60% 还没收敛？→ /compact 或开新 fresh session。

session 后（90 秒）

  • verification-log.md 落了没？没落 → 补。
  • 本轮学到的东西写进 MEMORY.md 或 AGENTS.md 了没？（compounding engineering）
  • open edge 全收敛了吗？（close-rate < 80% 不允许标记父线程完成）
  • 本轮有没有"未验证就接受 agent 结论"？有 → 补 live-smoke-test。
  • 本轮有没有重复粘贴 > 2k token 的文档？有 → 抽成 reference skill。
  • 本轮有没有"agent 借口跳过验证"？记下来，更新主协调 anti-rationalization table。
  • 本轮 handoff 文档写了吗？（如果会跨 session）

每周一次（5 分钟）

  • 本周 goal-thread 有几个 blocked / paused？超 1 个 → 治理。
  • 本周 open edge 总数趋势？上升 → 委派边界有问题。
  • 本周情绪化纠偏 prompt 占比 > 10%？→ 并发战线过宽或范式错。
  • 本周学了什么新东西？写进 MEMORY.md。
  • 本周有"声明-执行落差"事件吗？记下来，更新 hook/skill 兑现机制。
  • 本周 K8s/数仓概念断层补了吗？没补 → 安排下周 1 小时教学体实现。
关于 checklist 的本质｜这不是"再多一份规范"。Boris 把 CLAUDE.md 提交进 Git 做 compounding engineering，本质就是"把每次踩坑学到的东西沉淀为下次自动避开的机制"。你的 checklist 应该是活的——每次踩坑后，把坑加进对应的 checklist 段。三个月后，你的 checklist 会变成你最值钱的 aicoding 资产，比任何 AGENTS.md 都更贴近你的真实工作流。Claude Code 官方原话："错两次→加 CLAUDE.md；同一 prompt 输三遍→存成 skill；副任务淹没上下文→走 subagent；想每次必发生→写 hook。"——这就是 checklist 的设计原理。
