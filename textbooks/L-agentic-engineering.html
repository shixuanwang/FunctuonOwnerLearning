Agentic Engineering 深潜

① 定位：Agentic Engineering 是什么 / 为什么

把这一节当锚。后面所有名词（Firstmate / no-mistakes / Captain-Crew / Validator）都是同一句话的不同投影。

一句话定义。Agentic Engineering = 工程师从"写代码 + 逐行 review"迁移到"规划（plan）+ 自动化验证（validate）"，把实现层（implement）整体交给可被指令驱动、可被监督、可被门禁拦截的 agent 集群。瓶颈从"生成速度"上移到"决定做什么 + 讲清楚 + 把关质量"。

这里有三层认知必须先拆开，否则后面会糊在一起：

层是什么谁负责读者当前状态
Generation（生成）把意图变成 diff。已规模化，token 越来越便宜。agent（Claude Code / Codex 等）已掌握（教材 J 36 次 AGENTS.md）
Review（评审）判断 diff 是否真解决了问题。generation scaled, review did not——这是当前全行业的真瓶颈。独立 fresh-context 只读 reviewer（异构模型优先）缺失（J 中 adversarial 仅出现 1 次）
Decision（拍板）对模糊、影响产品方向、没有客观最优的判断负责。人类（不可委派）判断力领先但缺 deterministic 兑现层
manager-vs-implementer 边界。Kun Chen 把自己从 coder 改写成 "engineering manager directing a team of agents"——决定 build 什么 + 判断 good 与否。读者作为 PM 的"判断力领先"在此刻被工程化：你不再是"读 diff 的 reviewer"，而是"决定哪个 escalate 该进我脑子、哪个该自动修"的 EM。这条边界一旦模糊（自己上手实现、自己 review 自己的 session），agentic 的全部杠杆归零。[ByteByteGo]

为什么现在必须吃透

  • generation 已不是瓶颈：主流模型 diff 通量远超单人 review 速度。一条详细 plan 可以让 agent 自治几小时[ByteByteGo]。
  • review 通量才是真瓶颈：人类阅读速度天花板 ≈ 800 行/人·日[SudoAll]。没有自动化 gate，并行 agent 只是在加速制造待 review 的债务。
  • 判断力领先的人反而更需要 gate：你的判断力越强，越容易被"clear logical convincing LLM output"麻痹（可信度陷阱[Equal Experts]）。Function Owner 的核心风险不是不会写代码，而是"声明了原则却没 deterministic gate 兑现"——这正是教材 J 对你的诊断。

② L8 Principles 与 "always-on team 经理" 哲学

L8 = Meta 职级标尺中的 Principal 级 IC（Staff 级最高一档）。注意口径：L8 身份是 Kun Chen GitHub bio 的自述（"Former L8 engineer at Meta, Microsoft, Atlassian"[GitHub]），Atlassian 2026 Atlas Camp / Dev Day 活动页仍以 "Lead Principal Engineer at Atlassian, leads the development of Rovo Dev" 列他[SudoAll]。引用此标签时写"嘉宾自述 L8"而非既成事实，权威锚点应放在可核实的开源项目上（firstmate / no-mistakes / axi）。

2.1 核心隐喻：永不下班的团队的经理

"I have now stopped writing most of the code myself and started acting like an engineering manager directing a team of agents... I stay at the level of deciding what to build and whether it's good."
— Kun Chen，转引自 ByteByteGo
"You talk to a single agent – the first mate – and it runs the crew for you. You stay on decisions; the fleet stays on work."
— SudoAll

关键认知：把 agent 当直系下属（direct reports），而不是工具。Kun 明确指出"委托给 agent 与委托给人的失败模式相同"——要 outcome 而非 action、讲清楚 why、出错不要接管回控制权而是更新 memory 文件[Creator Economy]。

2.4 "40 PRs/day" 真相（口径校正）

来源数字口径

把"40 PRs/day"当营销标题，把"11 changes/day × 3 月、人工 review 上限 800 行"当真实基准。瓶颈不在写代码，而在"决定做什么 + 讲清楚"（planning）和"自动化验证"（gate）。[SudoAll]

2.5 高产出三腿（并行 + 输入 + 续命）

  • 并行：tmux 窗口 + tab title 显示每个 agent 状态（running/done/needs input）；treehouse 管 worktree 池（复用已装好依赖的空闲 worktree、自动 sync 最新 main）；同时管 5–10 任务[Creator Economy]。
  • 输入：OpenSuperWhisper（本地 Whisper large）做 voice primary input——"You talk a lot faster than you type"；WezTerm + Neovim + tmux 终端中心化[Creator Economy]。
  • 续命：Tailscale + SSH + mosh 让手机直达 Mac 上同一 tmux session——"perfect continuity across phone, laptop, and PC"[Creator Economy]。

token 经济：接口设计是系统工程，不是协议选择

SudoAll 引用 AXI 项目实测："MCP conditions average 185K tokens per task vs. 79K for AXI"——agent-first 紧凑 CLI 输出远胜 schema-heavy 的 MCP wrapper。原则："protocol choice matters less than interface ergonomics"[SudoAll]。更深的判断："A lot of SaaS from the last twenty years is a human UI glued to a database"——agent 要的是headless、stable、token-cheap control surface。

这对你直接相关：你走 bigmodel 网关按 token 计费，省 token = 省 context 长度 = 更深教材生成。

④ Firstmate（及 Hermes 误传）：解决什么 / 怎么上手

3.1 它是 distro，不是工具

Firstmate slogan："Talk to one agent. Ship with a crew."。它既不是模型、不是 MCP server、不是 CLI wrapper、也不是 SaaS——它是一个被克隆下来的目录（AGENTS.md + skills + scripts + 状态约定），让通用 coding agent（Claude Code / Codex / Pi / Grok / OpenCode）一启动就变成"船长 + 船员"协调器[GitHub]。

关键修正：'Hermes' 是误传。在 Kun Chen 的 stack 里没有 Hermes。
① Firstmate README 全文无 "Hermes" 字样；
② 它的 session backend 叫 Herdr（agent-aware multiplexer，给 tmux/zellij 加语义状态：working/idle/blocked-on-human）；
③ "Hermes" 实际指 Nous Research 的 Hermes Agent——一个独立的、自改进的开源 agent，与 Firstmate 完全无关。
David Ondrej 那期视频标题把 "firstmate compare to hermes" 当 hook，但该页 email gating，原始 transcript 未能核实。真正的对比维度是 Herdr vs tmux（语义状态 vs 哑会话后端）。[SudoAll]

3.2 三大痛点（何时该上）

痛点 1：上下文管理——tab-juggler 天花板

核心失败模式：人类维护 20–30 个并行 agent session 会耗尽 working memory，每次切换都要完整重载 intent——"Every context switch costs a full reload of intent. Agents keep running. Your attention does not."[SudoAll]

硬指标：你同时在跟几个 agent tab？>3 个且经常忘记哪个 tab 在跑失败测试 = 该上 Firstmate。

痛点 2：委托——可中断的 captain 才是好 captain

first mate 必须保持 interruptible。如果它自己吸收任务，就变成新瓶颈。crewmate 存在的唯一理由就是让 first mate 保持空闲接收新指令。委托遵循 durable preference rules（model / harness / reasoning effort 按 task class 预设，不临时选）。每个 crewmate 经 treehouse 拿独立 git worktree，杜绝并行 agent 撞同一 working tree[SudoAll]。

痛点 3：验证——no-mistakes 本地 git 代理是硬闸

"Generation scales, review does not." 若人类必须逐行 review 才能 merge，吞吐天花板就是人类阅读速度。no-mistakes 是本地 git proxy：从产出 agent 的 session 重构 intent → 跑对抗 review（常换不同 model family）→ 自动修机械 bug → 把触碰产品语义的变更 escalate 给人类 → 跑 tests / docs / lint 才放行[ByteByteGo]。

七条 Firstmate 原则

  1. One liaison, many workers——永远不要自己同时管 N 个 pane。
  2. Delegate by default——船长保持可中断靠"不亲自跑长任务"。
  3. Isolate parallel writes——永不两个 agent 同一 worktree。
  4. Gate the merge, not your eyeballs——无 gate 的生成 = scales slop（放大垃圾）。
  5. Route by task complexity——贵模型做设计、便宜路径做杂活。
  6. Invent tools only from real friction——避免 setup theatre。
  7. Protocol choice matters less than interface ergonomics——MCP/CLI/code-mode 都只是 transport。

3.4 怎么上手

最小路径不需要全栈。三步先上：①选 1 个 captain surface → ②隔离并行工作（worktree）→ ③装最小 merge gate。三者先上，再考虑 full Firstmate。

完整安装三行：

gh auth login
git clone https://github.com/kunchenguid/firstmate
cd firstmate && claude   # 或 grok --trust / pi / codex

三个项目模式：①no-mistakes（对抗审查兜底，推荐生产用）②direct-PR（信任 first mate 判断）③local-only（原型/实验）。可选 +yolo 自治标志（慎用，只在 throwaway 任务上）。

3.5 何时不该上（反 setup theatre）

SudoAll 明确警告四种不该上的情况[SudoAll]：

  1. 单一聚焦产品 + 一个 agent，review 量可控——Firstmate 是负担。
  2. 周末 demo / 一次性脚本——重管线不值。
  3. legacy monorepo——agent 帮但抹不掉协调债。
  4. 已有健康人工 review 流程——别用 shell 脚本替代。
"If your setup cannot point at a PR, a release, or a customer outcome this week, you are starring in setup theatre."
反事实：你装了 firstmate + treehouse + no-mistakes + lavish + axi 全套，但本周没有 PR 落地——你只是在大规模制造元工作（meta-work）。

社区硬风险（LinkedIn 评论区）：多 crewmate 撞同一共享模块时，合并冲突是语义级而非文本级，no-mistakes 的对抗 review 能否兜住是开放问题。给 first mate 设计任务划分时优先按模块边界切。

⑤ 对抗性审查 + 自动验证：让 AI 自证代码正确

这是教材 J 对你的核心诊断——"独立验证 gate 缺失"。下面这一节是补洞的核心。

4.1 Maker-Checker 分离：写代码的 agent 永不签字

Augment 官方指南原话："the agent that writes a change never certifies it."[Augment]。五维控制表：

维度Maker（生成者）Checker（检查者）
Context完整历史只 diff + criteria
System prompt实现导向怀疑式 checklist
Model任意显式 pin，最好跨家族
Tools全工具只读 Read / Grep / Glob（不给 Write / Edit / Bash）
Output自由形态结构化 verdict

Augment · Adversarial Code Review: Why the Maker Shouldn't Grade

4.2 Fresh-context 子代理：审查必须在独立 context 跑

"a fresh context improves code review because Claude avoids bias toward code it just wrote."
— Anthropic 官方，转引自 ByteByteGo

同会话自审 = 让人查自己刚交的作业，必然偏向"我刚写的肯定对"。Augment Cosmos 实现：a Deep Code Review agent runs in a fresh Session, isolated from the Session that produced the diff[Augment]。

你已有的武器：Claude Code 的 /code-review 就是 fresh-context 子代理——它是 "bundled skill that runs as a forked subagent"[Claude Code Skills]。缺的不是能力，是强制调用的规则。

4.3 跨家族审查暴露同家族盲区

Augment 引用 libfuse 战例："a Codex agent found bugs that Claude-family review missed."[Augment]。同家族模型 "share correlated blind spots and often end up confidently agreeing in the same places"。

MindStudio Verifier Pattern 三条[Creator Economy 旁证]：

  1. 独立 context——验证者只拿原始需求 + 产物。
  2. 跨模型家族——GPT-4o 生成、Claude 验证。
  3. 检测 generator-specific blind spots——模型错误是系统性聚类而非随机分布。

4.4 强制端到端证据（拒绝"单测过了"）

"I can often watch it test its own work in real time by driving the real app."
"every unit test passes, and the product is still buggy."
— Kun Chen，ByteByteGo

Claude Code 内置三件套（官方 Skills 文档）：

  • /run——真启动 app。
  • /verify——"Build and run your app to confirm a code change does what it should, without falling back to tests or type checks"。
  • /run-skill-generator——一次性记录"干净环境如何启动 app"（install/env/launch）存成 .claude/skills/run-<name>/。

v2.1.215 起 /verify 和 /code-review 只在用户主动调用时跑——所以必须把"显式触发"写进 AGENTS.md，否则会被 agent 跳过。

Augment："Authentication, authorization, secrets handling, and payment paths deserve verifier attention before broad refactors do.""A small permission change can be more dangerous than a large low-risk refactor."[Augment]。OpenAI 也只对 critical findings 设 merge gate，其余 advisory[OpenAI Alignment]。

4.6 三角色对抗：Primary + Challenger + Arbiter

Augment 把单 reviewer 扩成三方对抗[Augment]：

  • Primary reviewer——提发现。
  • Challenger——试图推翻发现并寻找遗漏。
  • Arbiter——裁决哪些阻断 merge。

OpenAI 用 "parallel reviewer agents score each issue for confidence"，只浮出高于阈值的发现[OpenAI]。

4.7 修复与审查解耦

Augment fixer loop："A separate fixer agent applies corrections" → "A new reviewer takes another pass" → 循环 → escalate 人。绝不让 reviewer 自己改——"A reviewer with merge authority breaks the checker boundary."[Augment]

4.8 渐进式门禁上线

  1. Advisory calibration——评论不阻断，先校准信任度/误报。
  2. Critical-findings gate——只对 critical 阻断 merge。
  3. Human-in-the-loop policy——"requires human approval before agents continue"。
  4. Permission-level scope——reviewer 不给 merge 权。
  5. Auditable session——"one replayable checker run per session"。

⑥ 用 agent 做复杂技术决策（judge panel / debate / ADR）

这是对你"判断力领先但缺 deterministic 兑现层"诊断的另一面——判断力领先的是拆解不是拍板。这一节讲清：什么能委派给 agent、什么不能。

5.1 关键反差：Kun / Firstmate 刻意不用 judge panel / debate

核实 ByteByteGo 与 SudoAll 两篇一手报道后确认：Kun 的决策模型里没有多 agent 独立设计 + 投票、没有 debate、没有正式权衡矩阵、没有 ADR 自动化。他的范式是分层问责[ByteByteGo][SudoAll]：

  1. 确定性步骤脚本化（bash / axi，零 reasoning token）；
  2. 代码质量用独立 context 的 reviewer agent 做 adversarial review，且刻意用不同模型家族；
  3. 模糊的、影响产品方向的决策明确升级人类——"Escalate ambiguous, product-changing decisions to the human"。

他自定位为 "engineering manager directing a team of agents"——决定 build 什么、是否够好。no-mistakes 管道是线性的（intent recovery → rebase → adversarial review → tests → docs → lint → PR → CI babysit），不是并行多方案竞争。

对读者最重要的校准：行业最前沿的实战派恰恰在"拍板"环节退回到人类，把 agent 限定在"拆解 + 执行 + 自检"。agent 越强，人类的拍板责任越被聚焦到少数高模糊决策上，而非被稀释——这正呼应"判断力领先的是拆解不是拍板"。
反事实：如果你试图用 judge panel/debate 投票决定"用 ClickHouse 还是 Druid 做数仓"——你把没有客观最优的架构权衡塞进了为客观参照设计的评估范式。结果只会得到"模型家族共识"，不是"上下文最优决策"。

5.2 Multi-Agent Verification（MAV）：学术范式

Lifshitz et al. 2025《Multi-Agent Verification》（arXiv 2502.20379）提出 test-time 组合多个 verifier 提升正确率，并给出"如何挑选要组合的 verifier"的方法。工程化最小形态不需要 debate 或 judge panel——主力模型生成 + 另一家族模型 fresh-context review 即可。

5.3 Judge panel / debate 的真主战场是"评估"而非"架构拍板"

2025 年 judge panel / debate 研究集中在 LLM-as-a-Judge 评估场景[NeurIPS 2025]：翻译质量、事实核查、对齐。这些系统的 judge/debate 用于"评估产出质量"，而不是用于"在两个架构方案里选一个并负责"。架构拍板的责任归属在这些论文里基本不讨论。

范式适合不适合
Judge panel / debate评估（对错有客观参照：翻译、事实、规范一致性）架构权衡（无客观最优，只有上下文最优）
Adversarial review (Maker-Checker)代码正确性验证—（这就是正确用法）
ADR 自动化 + judge prompt 批判草拟决策文档不替代人类对 alternatives 的事实核查

5.4 ADR 自动化：成熟范式，但人类始终在治理闭环里

Equal Experts 给出 metaprompting 方法[Equal Experts]：从一个 "decision kernel"（一句话决策核心）出发，让 LLM 扩展出 Background / Alternatives / Decision / Consequences，Alternatives 部分 prompt 要求 "think HARD" 并搜网获取最新替代方案。

四个陷阱：

  1. 幻觉——编造 API / 链接 / 产品功能。
  2. 理由错配——decision 与 alternatives 不对齐。
  3. 可信度陷阱——"clear logical convincing output" 让人放松审查。
  4. 瓶颈转移——文档快了但 stakeholder 协调变瓶颈。

Equal Experts 的解法：用另一个 "judge" prompt 批判生成的 ADR、加 guardrail（"References MUST exist"）、人工事实核查是核心环节。

5.5 AGENTS.md 作为"可执行 ADR"

SudoAll 报道 Firstmate 栈用 preference files（AGENTS.md）编码规则，captain agent 据此路由决策（"Route by preference files"）[SudoAll]。

社区论点 "AGENTS.md is the new ADR" 主张：传统 ADR 是给人类读的叙事文档，AGENTS.md 是给 agent 读的可执行约束——把"我们不用 X 框架""所有 SQL 必须带表前缀"这类决策编码为机器可读规则，agent 在生成代码时被迫遵守。这把"架构决策"从"事后记录"前移为"事前约束"。

advisory vs enforceable 的分界。ADR 是 advisory（建议性，靠人脑遵守）；AGENTS.md 在 hook / subagent / pre-push gate 联动时变成 enforceable（强制执行）。你的核心缺口不是"没写原则"，而是"写了原则但没有 deterministic 层去兑现它"——这正是把 AGENTS.md 从 advisory 升级为 enforceable 的过程：写一条 → 配一个 gate 验证它 → 违反时 gate 拦下。无 gate 的 AGENTS.md 仍是声明。

5.6 "拍板并负责" 的 agentic 模式

综合 Kun / Verifier Pattern / Equal Experts，可负责的 agentic 决策是三段式：

  1. 分层问责——脚本对确定性负责、对抗审查对代码质量负责、人类对产品方向负责。三层各有 owner，不混淆。
  2. 模糊性上交——Kun 明确 "escalate ambiguous product-changing decisions"，captain "delegate by default" 保持可中断，只在 ambiguous decisions 上花时间。
  3. 反馈进约束——每次人类拍板的决策，沉淀回 AGENTS.md / preference files，使下次同类决策不再需要人类。拍板次数随系统成熟度递减，因为决策被前置编码为约束。

(A) 任务分类

## Task classification

- **scout** = 只产 report，零代码改动。
  适用：数仓分片键 / TTL / 排序键 / 新表 schema 这类"建什么"不确定的探查。
  产物：data/<task-id>/report.md（含 pros/cons/推荐/引用）。
  升级：reader 审 report 后用 `bin/fm-promote.sh` 或人工 promote 成 ship。

- **ship** = 产出可 land 的变更（PR-ready）。
  适用：明确"改什么"的实现任务。
这一条直接回应"委托下沉不克制"。你的诊断之一是"声明原则缺 deterministic 兑现层"——把"建什么 vs 改什么"明确分类，把不确定的探查强制走 scout（零代码改动），能砍掉一半返工。委派给 agent 的不该是"改 DDL"，而应是"先调研三种分片方案的读写代价，产出 report"。

(B) Escalation 三级策略（搬自 firstmate AGENTS.md）

## Escalation policy

按权威分三级（不可越级）：

- **auto-fix（agent 自治）**：拼写 / lint / 格式化 / 类型 / 测试补全 / 缺失 import。
  原则：机械、可逆、不触及产品语义。

- **ask（必须问 reader）**：DDL 变更 / 数据契约 / 分片键 / 排序键 / TTL /
  触 `warehouse/` 或 `warehouse/dq` 或 `warehouse/contracts` 的任何修改 /
  新增外部依赖 / CI 凭证变更。
  原则：影响产品行为或不可逆。

- **never（硬规则，永不静默执行）**：删数仓表 / 改生产凭据 /
  force push master / 删 MEMORY.md / 关掉 pre-push gate / 改 AGENTS.md 自身。
  原则：破坏性或治理边界。

firstmate 的原始硬规则优先级（搬用参考）[firstmate AGENTS.md]：never write to projects / never merge without captain explicit word / never tear down unlanded work / crewmates never address captain directly / report faithfully including failure。

(C) 对抗审查硬规则（兑现"独立验证 gate"）

## Adversarial review gate (enforceable)

完成前 final gate（不可跳过）：

1. **intent recovery**：spawn fresh Task agent，
   prompt 第一段不是"找 bug"而是"重建声称完成的任务 → 列验收点 →
   逐条对照 diff 判断是否真实现"。结构化输出 verdict。

2. **fresh-context code review**：diff > 50 行 或 触 `warehouse/` / `flink-jobs/` /
   `warehouse/contracts/` 的变更，强制 spawn 另一个 fresh Task agent 跑
   superpowers code-review skill。结论带 文件:行号 回来前 **禁止 git push**。

3. **E2E evidence**：任何数据访问功能（ClickHouse/SQL/REST/GraphQL）
   完成前必须对 live DB 跑真实查询（配合 live-smoke-test-before-done skill）。
   mock 单测不算完成。/verify 不允许退回单测/类型检查。

4. **fixer 解耦**：reviewer 只输出 verdict（severity/confidence/file:line/evidence），
   修 bug 由另一个带写权限的 agent 或人执行，修完 spawn 新 fresh-context reviewer 复审。

5. **blast-radius 路由**：
   - auth / 支付 / secret / 权限 / 数据迁移 → 三角色（Primary+Challenger+Arbiter）
   - 纯格式化 / 低风险 refactor → 单 reviewer + 置信度阈值过滤
advisory vs enforceable 的兑现。仅写"应该 review"是 advisory——agent 可跳过。把它和 pre-push hook + fresh Task agent 联动，就变成 enforceable。这条规则把教材 J 的诊断"独立验证 gate 缺失"从声明变成机制。

第 4 步 · 加最小 merge gate（不依赖 no-mistakes）

#!/usr/bin/env bash
# 最小 merge gate：复刻 no-mistakes 的拦截语义，0 外部依赖
set -euo pipefail

# 读本次 push 涉及的 diff
range="$1...$2"  # ref1 ref2 from git
# 实际用 origin/master...HEAD 更稳：
range="origin/master...HEAD"

diffstat=$(git diff --stat "$range" 2>/dev/null | tail -1)
lines=$(git diff "$range" 2>/dev/null | wc -l)
touches_warehouse=$(git diff --name-only "$range" 2>/dev/null | grep -E '^(warehouse/|flink-jobs/|warehouse/contracts/)' | head -1)

if [[ "$lines" -gt 50 || -n "$touches_warehouse" ]]; then
  echo "─────────────────────────────────────────────"
  echo "BLOCK: 触发 fresh-context review"
  echo "  diff 行数: $lines"
  echo "  触敏感路径: ${touches_warehouse:-no}"
  echo "请在 Claude Code 里执行："
  echo "  1. /code-review   (fresh-context adversarial review)"
  echo "  2. /verify        (实跑 app，不允许退回单测)"
  echo "  3. 触 warehouse/ 的：跑 live-smoke-test-before-done skill"
  echo "─────────────────────────────────────────────"
  echo "确认完成后再 push。强制绕过: git push --no-verify (留有意识绕过的口子)"
  exit 1
fi

exit 0
chmod +x /home/cheche/Workspaces/Learning/HilPerformancePlatform/.git/hooks/pre-push

这条 hook 用 0 外部依赖复刻 no-mistakes 的 gate 语义。反事实：如果不加这个 gate，你的 AGENTS.md 里写的"必须 review"只是建议——agent 会在没有 review 的情况下直接 push，你的"独立验证 gate"诊断永不愈合。

⑨ 关键 rationale + 反事实

9.1 为什么"validator ≠ reviewer"

Reviewer 答"diff 有 bug 吗"，可基于 diff 推理；Validator 答"产品真的跑通了吗"，必须驱动真实 app 出证据。Unit test 全绿而产品有 bug 是常态——OpenAI 的 reviewer 给仓库读取 + 代码执行权限（不只看 diff）就是这个原因[OpenAI]。
反事实：如果你只装 reviewer（基于 diff 推理），SQL 别名碰撞、缺表前缀、IN 过滤错配、类型不匹配这些 bug 全部会过——它们只在真实 DB 上跑才暴露。Validator 必须独立于 reviewer 存在。

9.2 为什么 review 必须 fresh-context 且跨家族

Anthropic 原话："a fresh context improves code review because Claude avoids bias toward code it just wrote"[ByteByteGo]。同家族模型 share correlated blind spots——会"自信地在同样地方同意"[Augment]。libfuse 战例：Codex 抓到了 Claude-family review 漏掉的 bug。
反事实：你用 Claude 写、Claude 在同一 session 自审——等于让学生批改自己的作业。即使新开 session 但仍用同一家族，盲点是相关的，发现不了同一类问题。

9.3 为什么 "拍板" 不能委派给 agent

Judge panel / debate 范式为有客观参照的评估设计（翻译质量、事实对错）。架构决策没有客观最优，只有上下文最优——责任归属在这些论文里基本不讨论。Kun 在最模糊的决策上退回人类，正是对这条边界的尊重[ByteByteGo]。
反事实：用 judge panel 投票"ClickHouse vs Druid"——你得到的是"模型家族共识"，不是"上下文最优"。三个月后真实查询模式暴露的权衡，模型投票时根本没考虑过。agent 越强，拍板责任越被聚焦，而非被稀释。

9.4 为什么 AGENTS.md 必须联动 hook 才算 enforceable

仅写"应该 review"是 advisory——agent 可跳过。把它和 pre-push hook + fresh Task agent 联动，就变成 enforceable：违反时 gate 物理拦下。[SudoAll] 把确定性步骤留在 bash（零 reasoning token），agent 只在"打破预期"时介入——hook 是 bash、reviewer 是 agent，正好分工。
反事实：你的 AGENTS.md 写了 39 次"应该"但没有 gate——agent 在 95% 的情况下会跳过，因为"完成任务"的奖励信号压过"遵守原则"。Function Owner 的核心风险不是不会写原则，而是没有 deterministic 层兑现原则。

9.5 为什么 reader 应在第 3 档停下（不要跳级上 firstmate 全套）

SudoAll 给的迁移顺序：① captain surface → ② worktree 隔离 → ③ merge gate → ④ token 替换 → ⑤ tab 管不过来才上 firstmate 全套 → ⑥ 显式 escalation 规则。你当前在 (1) 已定 Claude Code、(2) 已用 worktree，正卡在 (3) merge gate 缺失。[SudoAll]
反事实：跳级上 firstmate 全套——你装了 captain+crew 编排但没有 gate。结果是并行地、加速地制造 slop。"Gate the merge, not your eyeballs" 不是口号：无 gate 的并行 = scales slop。

9.6 为什么"反馈进约束"是 agentic 决策可负责的根

每次人类拍板的决策应沉淀回 preference files，使同类决策下次不再需要人类——拍板次数随系统成熟度递减。Equal Experts 的"judge prompt 批判 ADR" + Kun 的"no-mistakes adversarial review"都是同一原则：在人类拍板前，先用独立 agent 把可机械验证的部分剥离掉[Equal Experts]。
反事实：你每次拍板后只改代码不改 AGENTS.md——下次同类问题还会 escalate 给你，拍板数量不收敛。三个月后你仍在为同一类问题拍板，agent 没有变得"更懂你的判断"。

9.7 为什么"可信度陷阱"对判断力领先的人更危险

Equal Experts：clear logical convincing LLM output 会让人放松审查[Equal Experts]。读者作为判断力领先的 PM，越容易被"听起来对"麻痹——你能更快看懂 LLM 的论证，但"看懂"不等于"核查"。
反事实：你读 agent 写的 ADR，alternatives 三条都很合理，decision 逻辑通顺——你拍板。三个月后发现 alternatives 漏掉了"用 Iceberg + Trino"这个真实存在过的选项（幻觉），decision 基于不全的权衡。judge prompt 批判 + references MUST exist guardrail + 人工事实核查是抗这个陷阱的三道防线。
分层的本质。读者作为 Function Owner 的核心能力，不是"写更聪明的 AGENTS.md"，而是分清哪一层该谁负责：脚本对确定性负责、对抗审查对代码质量负责、人类对产品方向负责。三层 owner 不混淆，是 agentic 决策可负责的前提。这一节 7 条 rationale 都是这条原则的不同投影——validator≠reviewer 是层（认知结构）、fresh-context 是层（context 隔离）、拍板不委派是层（责任归属）、AGENTS.md 联动 hook 是层（advisory→enforceable）、停在第 3 档是层（杠杆排序）、反馈进约束是层（决策收敛）、可信度陷阱是层（信任校准）。
