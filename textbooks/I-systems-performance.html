① 一句话定位：什么是"性能之巅"

"性能之巅"不是一本工具书，而是一套"如何决定看什么、怎么解读、按什么顺序下钻"的方法论骨架。Brendan Gregg 反复强调：方法先于工具——先用方法论决定看什么，再选工具，否则就是"先有锤子再到处找钉子"的反方法论（凭直觉乱试、甩锅、Google-Search 搜到啥试啥）。

性能问题不可解，根因往往是"看了错的东西"。USE/RED/60s/负载画像/延迟拆解本质都是"强制把你的注意力铺到对的切片上"——前者扫资源、后者扫服务、60s 扫高阶信号、画像扫负载形态、拆解扫延迟构成。每个方法论都是一种"避免盲区"的纪律。反事实：不学方法论直接上 perf record，90% 概率盯错热点，因为采样只覆盖了 on-CPU 时间，IO/锁/网络等待根本看不见。
对数据闭环 PM 的认知杠杆：你日常的"看仪表盘找瓶颈"本质就是性能分析。Gregg 把你直觉里的"系统化扫一遍再下钻"提炼成可复用模板——你能用它给一辆车、一条回流链路、一个训练任务秒出一份健康检查清单。这正是从执行型 PM 跨入架构师最稀缺的"抽象 + 迁移"能力。

下面按"方法论 → Linux 底层 → 工具栈 → eBPF → 无人车叠加层"五段展开，全程先因果后术语。

② 方法论：USE / RED / 60s / 负载画像 / 延迟拆解 / 性能箴言

2.1 USE Method：资源三态（Utilization / Saturation / Errors）

Gregg 亲自定义、可迁移性最强的方法论，一句话："For every resource, check Utilization, Saturation, and Errors."

  • Utilization（利用率） = 某时间区间内资源忙于服务工作的平均比例（%）。
  • Saturation（饱和度） = 资源有额外工作排队的程度，通常等于队列长度。
  • Errors（错误） = 错误事件计数（标量）。

策略：先列全部资源 → 对每个资源依次查 Errors（最快最确定）→ Utilization → Saturation → 发现问题即下钻。判读经验：

  • U=100% 多半是瓶颈；U>70% 因突发负载或不可中断资源也可能是瓶颈。
  • Saturation 任何非零都值得查（队列长度 > 0 就是排队）。
  • Errors 非零且持续增长必查。
CPU    U: vmstat 1 (us+sy+st) / mpstat -P ALL 1
CPU    S: vmstat 1（看 r 列 > CPU 数）
Mem    U: free -m / free -w -h
Mem    S: vmstat si/so + sar -B（pgscank/pgscand/%vmeff）
Mem    E: dmesg | grep -i oom / bcc oomkill
Net    U: sar -n DEV 1 / ip -s link / nicstat
Net    S: ifconfig 丢包 / netstat -s retrans
Net    E: ip -s link（接口错误计数）
Disk   U: iostat -xz 1（%util）
Disk   S: iostat avgqu-sz > 1 / await 高
Disk   E: smartctl / dmesg
FD     U: sar -v / /proc/sys/fs/file-nr
USE 的威力在"known-unknowns"练习：你强制把每一类资源都扫一遍，等于明确列出"我也测不到什么"。Gregg 自评用 5% 努力解决约 80% 服务器问题。反事实：跳过 USE 直接 perf record，会漏掉网卡静默丢包、磁盘软错误、FD 耗尽这些"利用率和 CPU 看不出来的"问题。
USE vs RED 的核心区分：USE 是资源/机器视角（这辆车/CPU/GPU/磁盘扛得住吗），RED 是服务/用户视角（这个请求/服务的用户体验爽吗）。AD 平台既有车端硬件资源又有云端请求驱动服务，两套必须合用——和嵌入式团队聊 USE，和 SRE 团队聊 RED。

2.2 RED Method：服务三态（Rate / Errors / Duration）

澄清归属：RED 由 Tom Wilkie（2015, Grafana）提出，不是 Gregg 原创，但被 Gregg 明确推荐为 USE 的服务侧补充。

  • Rate = 每秒请求数（吞吐）。
  • Errors = 失败请求数。
  • Duration = 请求耗时（延迟），必须看分布不只是均值。

与 Google 四黄金信号映射：Rate↔Traffic、Errors↔Errors、Duration↔Latency，缺 Saturation（RED 不含饱和度，四黄金信号补这一项）。典型实现用 Prometheus。

# Rate（每秒请求数）
rate(http_requests_total[1m])
# Errors（每秒失败数）
sum(rate(http_requests_total{status=~"5.."}[1m]))
# Duration P99
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))
数据回流 / 评测流水线 / 数据查询 API 是"请求驱动"的服务，USE 不直接适用——你不会说"这条回流链路的 CPU 利用率 80% 所以慢"，你会说"这条链路的失败率 5%、P99 800ms"。RED 给 PM 一组可向用户/SRE 报告的北极星：日活车辆回流量 (R)、回流失败率 (E)、回流端到端延迟 (D)。反事实：用 USE 监控服务会把注意力错放在机器上，而真实瓶颈可能是上游队列或慢 SQL。

2.3 60-Second Analysis：进场前 60 秒必跑的 10 条命令

《Linux Performance Analysis in 60,000 Milliseconds》：Netflix 实战提炼，目的是先扫高阶信号、定位方向再下钻。Gregg 自述"多数问题在到 top 之前已定位"。

#命令看什么症状

2dmesg | tail内核错误 / OOM / 硬件故障
3vmstat 1CPU 在 usr/sys/idle 哪段、si/so 换页、r>CPU 数
4mpstat -P ALL 1单核是否打满不均（CPU 亲和性问题）
5pidstat 1谁在吃 CPU
6iostat -xz 1磁盘 %util / await / avgqu-sz

60s 清单是"先广后深"纪律的体现：不一开始就钻 perf/flame graph，先把高阶信号（负载/内核/内存/磁盘/网络）扫一遍找疑点。AD PM 在路测卡顿、事故复盘、数仓慢查询现场，可把这套 10 命令改造成"AD 60s 清单"——车上：/proc 实时指标 + journalctl + 数据回流通路延迟；服务端：慢查询 Top5 + 队列长度 + 错误率。反事实：现场凭直觉"先 grep 日志找 error"，会浪费 20 分钟却错过根本没报错的调度抖动。

2.4 Workload Characterization：负载画像

回答"谁、为什么、什么类型、如何随时间变化"——把系统当前的负载描述清楚再优化。四维：

  • Source（PID / UID / IP——谁产生的）
  • Code path（哪段代码 / 调用栈）
  • IOPS / throughput（量级）
  • Time series（随时间模式）

常与 USE 配对：先用 Workload Characterization 描述"系统在干什么"，再用 USE 描述"资源扛得住吗"。盲目优化前先问清负载长什么样。

这条对数据闭环 PM 几乎是本职：闭环效率优化前必须画像"数据量级 / 来源（车 / 路 / 路测）/ 类型（感知 corner case vs 规控 failure）/ 时间分布（白天 / 黑夜 / 天气）"。这把 PM 的需求分析能力直接迁移到性能领域——"问题定义清楚 = 解决一半"在性能调优上同样成立。反事实：不画像就调参，会出现"优化了白天 throughput 但晚高峰 corner case 反而变慢"这类局部最优陷阱。

2.5 Time Division Method（延迟拆解）+ Drill-Down Analysis（下钻分析）

Time Division Method（原 Latency Analysis Method）四步：

  1. 测一次操作的总时间 / 延迟。
  2. 把时间拆成逻辑上的同步子组件。
  3. 继续往下拆直到定位延迟源头。
  4. 量化：估算"若修好这个问题能省多少时间"。

核心是"把一个端到端延迟不断二分成更小的时间片"，直到最大的那片被钉住。配合 process of elimination（分块排除法）：做能洗清多个未测组件的测试。

Drill-Down Analysis 三步循环：(1) 从最高层级看 → (2) 检查下一层细节 → (3) 选最有意思的维度继续下钻，重复直到问题定位。实践形态：top → 按 CPU 排序找进程 → 对该进程 perf record → 火焰图 → 定位函数。

AD 场景最痛的就是端到端延迟归因：从传感器数据 → 预处理 → 感知 → 融合 → 规控 → CAN 下发，一段一段拆时间才能定位哪一环拖后腿。Time Division 给 PM 一个"问题分解"的通用骨架，可直接套到数据回流链路延迟、模型评测流水线耗时、数据标注 SLA 的拆解上。反事实：只看总延迟"100ms 不达标"，永远定位不到是 H2D 拷贝 1.5ms 还是 NvJPEG 编码 4ms。

2.6 性能箴言七诀：优化方案的 brainstorming 框架

Static Performance Tuning 七诀（按优先级，越靠前越优先）：

  1. Don't do it（别做）——能不做就不做。
  2. Do it, but don't do it again（做一次但别再做）= 缓存。
  3. Do it less（少做）——降频率。
  4. Do it later（延后做）= 异步。
  5. Do it when they're not looking（趁没人注意做）= 预计算 / 批处理。
  6. Do it concurrently（并发）。
  7. Do it cheaper（更便宜地做）——换算法 / 换硬件。
七诀本身就是优化方案的 brainstorming 框架。PM 提需求时用它穷举改进方向：闭环数据能不能不回流（Don't do it）→ 能不能合并多车批量（Do it less）→ 能不能车端预标注（Do it when they're not looking）→ 能不能异步并发（Do it concurrently）→ 能不能下推到 ClickHouse 引擎（Do it cheaper）。避免直接跳到"加机器 / 加卡"这种最贵方案——这是架构师核心成本判断力。反事实：每次性能问题都默认"加机器"，运维成本爆炸且根本没解决软件层面的低效。

2.7 反方法论：必须避开的三个陷阱

  • Blame-Someone-Else（甩锅法）："是算法慢" / "是平台慢"——没有数据支撑的归因。
  • Ad-Hoc Method（凭直觉乱试法）：先有工具再到处试。
  • Google-Search Method（纯搜索法）：搜到啥试啥。
反方法论是真实项目里最常见的浪费。PM 把这套反方法学写进团队评审 checklist，能显著提升问题收敛速度——这与 ROVER5.0 MR 黄金路径同构：拒绝"凭感觉"，每个判断要有数据 / 方法学支撑。反事实：允许甩锅法，团队会在算法 vs 平台 vs 车端的互相指责里空耗数周，问题根因永远飘在中间地带。

③ Linux 系统性能底层：CPU / 内存 / IO / 网络 / 调度

3.1 CPU 与调度：CFS、rt、抢占、上下文切换

Linux 默认调度器是 CFS（Completely Fair Scheduler）——按红黑树维护任务虚拟运行时间，时间片轮转追求"公平"。内核 6.6+ 已被 EEVDF 取代（Earliest Eligible Virtual Deadline First，Zenkov et al. 2023 提出，Linux 6.6 合入；按"最早可调度时间（eligible）+ 虚拟截止期（virtual deadline）"排序，更细粒度响应延迟敏感任务。论文：hal.science/hal-03988543；LWN 报道：lwn.net/Articles/925371）。实时类用 SCHED_FIFO / SCHED_RR。

关键因果：CPU 性能问题分两类，方向完全不同——

  • involuntary context-switch 高 = CPU 不够 / 优先级问题（线程没跑够就被抢）。
  • voluntary context-switch 高 = IO / 锁阻塞（线程主动让出 / 睡）。
perf stat -e context-switches,cpu-migrations -a sleep 5  # 看 CS 频率
perf stat -e sched:sched_switch -a sleep 5               # 调度事件
perf sched record -- sleep 5; perf sched latency        # 调度时序分析
top -H / ps -L -o pid,policy,pri,nice,comm -p PID       # 线程策略与优先级
CFS vs rt 的核心区分：CFS 不区分实时线程——这是 ROS2 / 中间件实时性的根本短板。AV 控制链路常需 rt 优先级保障时序。看到一个 onboard 延迟 bug，先问"是 CFS/优先级问题还是模型 inference 慢"——而不是先让算法 team 改模型。这是 PM 转"机器人 / 具身"方向时的底层 OS 判断力。

CPU 分析工具梯度

  • uptime 看 loadavg（饱和度）。
  • vmstat 1 看 us/sy/id/wa/st 与 r 列（饱和度）。
  • mpstat -P ALL 1 看单核是否打满不均。
  • pidstat 1 看进程级 CPU。
  • perf stat 看 IPC、cache miss、cs 频率（宏观）。
  • perf record -F 99 -ag 抓栈（定位热点）。
  • 火焰图（下节详述）。

3.2 内存与 Page Cache：free 的可用内存不等于真用尽

核心因果：page cache 占的内存是可回收的，不是真用尽。free 显示的 used 含 cache，available 才是真可用。理解这条才能判断"是不是真内存不够" vs "只是缓存压力"——决定是扩内存还是调 IO。

free -w -h            # 分列显示 buffers/cache
vmstat -w 1           # 看 si/so（swap in/out）和 bi/bo（block IO）
sar -B 1              # 分页统计：pgscank/s（kswapd后台扫描）、pgscand/s（直接回收）、%vmeff
cachestat-bpfcc 1     # 每秒页缓存命中/未命中

关键判读：

  • pgscand/s 非零 = 直接回收路径被触发 = 内存压力已较重（应用被迫等回收）。
  • %vmeff = vmscan 效率（pgsteal/pgscan），< 20% 说明回收效率差。
  • majflt/s（主缺页）持续 > 0 = cache 未命中触发磁盘读。
AD 训练 / 标注 / 回放都是内存密集 + IO 密集混合负载。pgscand/s 上升 = 模型训练 epoch 间数据加载被回收拖慢。正确做法是改 readahead 或 mlock 热文件，而不是无脑加内存——这正是"先因果后动作"的范例。反事实：看到 free 内存少就扩内存，扩完发现还是慢，因为根因是 IO 路径而非容量。

3.3 OOM 全链路：从 PSI 到 cgroup OOM 到 kernel OOM

OOM 不是瞬时事件而是链式事件。现代 Linux（k≥4.20）诊断链：

  1. PSI（Pressure Stall Information）经 /proc/pressure/memory 报告 some（至少一个 task stall）和 full（所有 task stall）的 10/60/300 秒平均。
  2. memory cgroup v2 达到 limit。
  3. cgroup-scoped OOM kill（优先于 system-wide）。
  4. 否则 kernel OOM killer 根据 oom_score 选进程杀。
  5. systemd-oomd 是用户态 OOM 守护，可基于 PSI 阈值在 kernel OOM 前主动干预。
cat /proc/pressure/memory    # 看 some/full avg10/60/300
dmesg -T | grep -i kill      # 读 OOM kill 信息（victim/oom_score/内存快照）
journalctl -k | grep oom
sudo oomkill-bpfcc           # 实时跟踪 OOM 事件（BCC 工具）
无人车仿真集群 / 标注容器化部署几乎都用 cgroup，PSI 是判断"是被 throttle 拖慢还是真的 OOM"的金标准。车上边缘计算节点也会因多进程争内存触发 OOM——psitol 可做车端轻量监控，避免行驶中 OOM 导致进程重启的安全风险。这是 PM 能向车端团队提出的具体可落地方案。反事实：等 OOM 日志才响应，已经发生了一次重启；用 PSI 能提前 30 秒预警。

bpftrace biostacks.bt     # 按初始化栈分组的延迟直方图（回答"为什么慢"）
AD 数据通常是大文件（点云 / 图像包）+ 小文件（标注 json）混合。await 的平均值会掩盖长尾——biolatency 直方图 + biostacks 栈才能定位是哪条代码路径（如 fsync 慢）拖慢数据写入。这对"数据落盘是否赶上车端上传节奏"是核心问题。反事实：只看 iostat 的平均 await，会把 P99 = 200ms 的尾延迟误判为"磁盘平均 5ms 没问题"。

  • tcpaccept-bpfcc：被动 accept。

  • tcptop-bpfcc：按连接 top 吞吐。
  • tcptracer-bpfcc：连接建立 / 关闭事件。

99 Hz 而不是 100 Hz 的原因（采样频率锁定 lockstep）：用 99 / 199 / 997 这种奇数频率，是为了避免采样与某个周期性活动（定时器、轮询、GC）发生 lockstep（同频共振）而产出偏斜结果。100Hz 在 Gregg 的 DTrace 例子中被标注为 "a little coarse, and risking lockstep sampling"。采样频率不是越高越好——这条懂了，你就能判断别人采集的数据可信度。

采样开销的经验比例（rule of thumb）

  • ~100Hz 采样开销 "low to negligible（约 1% 或更低）"。
  • 1000Hz 约 10%。
  • 这是社区经验观察的近似，不是严格定理——不要当物理定律引用。
AD 车端 / 仿真常需要在不破坏时序的前提下采集（如实车 100Hz 决策回路）。懂开销比例 = 懂什么能在车上常开（~100Hz）、什么只能离线诊断时短开（1000Hz）。这是把性能工具落到 AD 工程实践的边界感。反事实：车端常驻 1000Hz perf，会把推理延迟本身拉高，导致采集的数据失真。

3.3 on-CPU vs off-CPU：只看一半的故事会漏掉 60%+ 的延迟

off-CPU 时间 = 线程不在 CPU 上跑的时段（阻塞于 syscall、involuntary 切换、mmap 磁盘 IO、调度延迟）。当它同步发生在请求路径上时"直接且按比例影响性能"。仅看 on-CPU 火焰图可能漏掉 60%+ 的请求延迟。on-CPU + off-CPU 一起 = 完整 wall-clock（墙上时间）画面。

Gregg 给的经验比例：off-CPU 分析能解决约 40% 问题，加上 wakeup 信息升到约 70%。

# 方法 A：perf 走 sched tracepoint（开销大，无奈之举）
perf record -e sched:sched_switch -a -g -- sleep 30
perf script --header > out.stacks
./stackcollapse-perf.pl < out.stacks | ./flamegraph.pl --title='Off-CPU' > off.svg

# 方法 B：bcc/eBPF offcputime（推荐，在上下文切换结束处一次性取 pid/stack）
/usr/share/bcc/tools/offcputime -df -p $(pgrep -nx mysqld) 30 > out.stacks
./flamegraph.pl --color=io --title='Off-CPU Time' --countname=us < out.stacks > off.svg

# 只看 TASK_UNINTERRUPTIBLE（D 态，磁盘 IO）
/usr/share/bcc/tools/offcputime -df -p PID --state=2 30 > out.stacks

wakeup / offwaketime：把睡和醒关联起来

off-CPU 只告诉你线程在睡，不告诉你被谁叫醒（唤醒者可能在别的 CPU / 进程）。wakeuptime 给出唤醒路径，offwaketime 把 off-CPU 栈 + 唤醒栈拼成一条 chain 图，定位"谁阻塞了关键路径上谁"。这是诊断跨进程延迟（生产者-消费者、调度延迟）的杀手锏。

/usr/share/bcc/tools/wakeuptime -f 30 > out.stacks
./flamegraph.pl --color=wakeup --title='Wakeup Time' --countname=us < out.stacks > w.svg
/usr/share/bcc/tools/offwaketime -f 30 > out.stacks
./flamegraph.pl --color=chain --title='Off-Wake Time' --countname=us < out.stacks > ow.svg
AD 数据闭环里大量是 IO / 锁 / 网络等待（回灌、序列加载、序列化、卡 GPU），on-CPU 看不到，必须 off-CPU。这条直接决定你能不能解释"为什么训练吞吐上不去但 GPU 利用率不高"——on-CPU 看模型计算，off-CPU 看 DataLoader / 锁 / 网络等待。offwaketime 是定位这类"CPU 不忙但端到端慢"的最终武器。反事实：只给 on-CPU 火焰图，永远看不到 DataLoader 阻塞 GPU 的真相。

⑤ eBPF 革命：bcc + bpftrace + 事件源

4.1 eBPF 是什么，以及为什么是性能分析革命

eBPF（extended BPF）是 Linux 内核 3.15+ 引入、4.1+ 普及的特性，把 BPF 从包过滤虚拟机扩展为可挂在多种事件上的内核态沙箱 VM。革命性体现在三点：

  1. 无需修改 / 重编译应用代码即可对任意内核函数或用户态函数插桩（kprobes / uprobes）。
  2. verifier 拒绝不安全代码（禁止循环、禁止反向分支），保证不崩溃、不挂起、不干扰内核，可以安全上生产。
  3. 全栈可见：内核态 + 用户态、CPU / 内存 / IO / 网络 / 调度全维度。

聚合计算全部在内核上下文完成（in-kernel sandboxed VM），减少上下文切换开销。

内核维护者 Ingo Molnár 原话：eBPF 允许 "user-defined instrumentation on a live kernel image that can never crash, hang or interfere with the kernel negatively."

eBPF 为何革命（与"又一个 tracing 工具"的区分）：传统 tracing（ftrace / strace）要么需要内核重编译、要么每事件一次用户态拷贝开销巨大；eBPF 在内核态沙箱内完成聚合，verifier 拦截不安全代码——这是它能上生产的根本。对 AD 平台而言，eBPF 是解决"线上推理卡顿 / scheduler 抖动 / IO 尾延迟难以复现"这类深层系统问题的唯一通用手段，是资深架构师必须掌握的"最后一公里可观测"。

4.4 bpftrace：AWK 风格的 one-liner 语言

bpftrace 受 awk / C / DTrace / SystemTap 启发，专为快速 one-liner 和短脚本设计，弥补 BCC 需写 Python 的笨重。语法核心：@[key]=aggfn() 建聚合 map，/predicate/ 过滤，hist() 出直方图。

# 按进程名统计 syscall 次数
bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'

# 追踪 openat 并打印进程名+文件名
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args.filename)); }'

# 块 IO 大小直方图
bpftrace -e 'tracepoint:block:block_rq_issue { @ = hist(args.bytes); }'

# on-CPU 火焰图（采样内核栈，99Hz）
bpftrace -e 'profile:hz:99 { @[kstack] = count(); }'

# off-CPU（调度切换时记录栈）
bpftrace -e 'tracepoint:sched:sched_switch { @[kstack] = count(); }'

# 内核函数 vfs_read 延迟直方图（按进程）
bpftrace -e 'kprobe:vfs_read { @start[tid]=nsecs; } kretprobe:vfs_read /@start[tid]/ { @ns[comm]=hist(nsecs-@start[tid]); delete(@start,tid); }'

# 仅追踪 pid=18644 的 read 返回字节数分布
bpftrace -e 'tracepoint:syscalls:sys_exit_read /pid==18644/ { @bytes=hist(args.ret); }'

# 列出所有 sys_enter_* probe
bpftrace -l 'tracepoint:syscalls:sys_enter_*'
bpftrace vs BCC 的边界：bpftrace 适合"一句话问一个问题"——按 PID 聚合、按直方图看分布、按 tracepoint 看事件；BCC 适合"长期跑的 daemon、复杂输出、需要 Python 处理"。PM 想验证"某个 ETL / 推理进程是不是真在等 X"，bpftrace 一行就能拿到直方图，比写代码快十倍——是"判断力先于实现"的典型杠杆。

4.5 四大事件源：决定可观测深度

eBPF 的能力边界由它挂载的事件源决定：

事件源类型特性
kprobes内核动态追踪任意内核函数入口/返回可插桩；跨内核版本可能失效
uprobes用户态动态追踪任意用户态函数（含 so 库）
tracepoints内核静态埋点稳定 ABI，跨版本可用；生产首选

事件源选型直接影响长期可维护性：生产稳定性建议优先用 tracepoints（ABI 稳定），kprobes 跨内核版本可能失效。车端内核版本固定、云端滚动升级，两条线的 BPF 工具维护成本完全不同——PM 在做跨端可观测方案时要把内核版本 / CO-RE 能力纳入架构约束。反事实：全用 kprobe 写监控，下次内核升级监控脚本集体失效，事故复盘反而没数据。

4.6 CO-RE + BTF：解耦内核版本

CO-RE（Compile Once, Run Everywhere）依赖内核 BTF（CONFIG_DEBUG_INFO_BTF=y，5.8+），解决 BPF 工具"换内核就坏"的历史痛点。Gregg 称未来靠 BTF + CO-RE 可做到 "install 100-Kbyte binary versions of the tools with no dependencies"。Netflix 实践：bpftrace 脚本集中存放、按需推到目标机。

grep CONFIG_DEBUG_INFO_BTF /boot/config-$(uname -r)   # 检查内核 BTF 是否开启
bpftool btf info                                       # 验证 BTF 可用
可观测 ≠ 安全（Gregg 2023 博文澄清）：eBPF 可观测工具为最低开销设计以便安全上生产，但这不等于它们是安全工具。verifier 保证程序本身安全（不崩溃），但不保证不会被恶意利用（root 权限才能加载 BPF）。AD 数据闭环涉及车规安全，需清晰区分"诊断可观测"与"功能安全 / 信息安全"两条独立线——别把诊断工具当安全防线。

⑥ 无人车系统性能：GPU / 感知延迟 / DDP / ROS2 / onboard

Brendan Gregg 方法论（USE / 火焰图 / 延迟分布）是普世方法论，但无人车场景需要叠加三层领域知识：GPU profiling（Nsight）、实时调度（PREEMPT_RT）、车载功耗约束（Orin TDP）。这三层恰好是 PM 转架构师时"系统观"的补全。

5.1 端到端 100ms：AD 性能的硬约束信仰

Berkeley EECS-2019-39 报告明确给出："AV 必须在 100ms 内做出端到端处理"。关键事实：

  • 这个 100ms 是感知 → 规划 → 控制的整条链预算，不是单一环节。
  • 高速公路上额外 100ms 延迟会让刹车距离增加 3 米。
  • 人类在最佳情况下对新信号的反应时间是 100-150ms——这是参考基准。
  • 这是 hard RTES（类飞机控制），不是 soft / firm。

Apollo 实测（同报告）：感知组件应该 125ms 一帧（8 FPS），但常常超过 250ms 才输出（掉帧）；控制组件均值 10ms，但偶尔 1s+ 不输出。模型推理时间方差极大：同一环境不同帧差 50%，不同环境差 10%，换模型差 100%。

100ms 是 AD 数据闭环 PM 的"底层信仰"：为什么 onboard 上掉帧就是 P0 事故——3 米刹车距离在城市道路意味着撞人。每加一个 head、每加一层 transformer，都要在评审里回答"这多花了多少 ms，撞没撞 100ms 预算"——PM 用这个 100ms 当否决门槛。反事实：把延迟预算留给感知 80ms、规划 15ms、控制 5ms，最后发现感知偶尔飙到 150ms，整条链崩了——预算分配必须看最坏情况不是均值。

5.7 ROS2 实时性：CFS 默认配置的痛与三套解法

ROS2 / ROS 默认走 Linux best-effort CFS（完全公平调度，红黑树按时间片轮转），不区分实时线程——这是 ROS2 实时性的根本短板。三套主流解法：

  1. PREEMPT_RT 内核补丁：让内核可抢占，最大幅降低抖动，是 AV / 机器人基础设施。
  2. SCHED_FIFO / SCHED_RR 实时调度策略 + CPU affinity 绑核：把关键 ROS callback 绑到隔离核（isolcpus），调高优先级。
  3. ROS-Llama（MPI-SWS 2021，被引 101）自动延迟管理器：动态给关键 cause-effect chain（如激光 → 建图 → 避障）分配线程、调优先级、超载时 graceful degradation。例子：用户声明"激光回调到障碍物入图最多 200ms"，ROS-Llama 自动配线程预算。

Baidu Apollo 自己从 ROS 切到 CyberRT（基于 task-graph 的调度器）也是同一思路。ROS2 用 DDS 做传输，能在通信层配 deadline QoS，但应用层 deadline 还要自己实现。

# PREEMPT_RT 内核
sudo apt install linux-image-rt

# 绑核 + 实时优先级
taskset -c 2-3 ros2 run ...
chrt -f 80 ros2 run ...        # SCHED_FIFO 优先级 80
ROS2 上车后延迟不可控的根因是 OS 调度，不是模型本身。判断力：看到一个 onboard 延迟 bug，先问"是 CFS / 优先级问题还是模型 inference 慢"——而不是先让算法 team 改模型。这是 PM 转"机器人 / 具身"方向时的底层 OS 判断力，也是和嵌入式团队对话的共同语言。反事实：默认认为是模型慢，让算法改了三轮模型，结果根因是某个 ROS callback 没绑核被网卡中断抢了。

5.8 Onboard 算力 + 功耗 + 散热：三重硬约束

  • 整车功耗红线 < 1.2kW（MIT 2023）：否则全球 AV 部署的碳排放失控。
  • NVIDIA DRIVE Orin SoC：254 TOPS（INT8），TDP 10-60W（汽车配置常见 ~72W），Arm Cortex 12 核 + Ampere GPU 2048 CUDA 核，Samsung/TSMC 8nm。
  • NIO Adam 平台用 4×Orin（48 CPU 核、8192 CUDA 核）。
  • EV 续航损失可达 ~30%（Liu 2021 综述，被引 658）：EV 上自驾计算功耗可让续航降 30%。
选模型不是只看精度，必须看"每 TOPS / 每 W 的精度"——这是车规量产 PM 与 demo PM 的本质区别。onboard 不是"算力无上限"，而是功耗预算 + 散热预算共同决定的硬约束。这个 30% 续航损失直接关联用户感知和产品定价。mAP/W、mAP/TOPS 才是车规量产的真实指标。反事实：只追 mAP，上了车发现夏天热降频 + 续航腰斩，产品完蛋。
信息可信度分级（PM 转架构师的核心素养）：NVIDIA 官方 blog 多为宣传口径（缺硬数字，例如 2019 那篇 DRIVE AGX + CUDA + TensorRT 没有 ms / FPS / TensorRT 优化百分比的硬数字）；Berkeley 技术报告 / Apollo 实测 / Pony.ai 案例 / 学术 paper 才有可引用的实测 ms 数字。看源说话——这种习惯让你在评审里不被"宣传口径"带偏。

  3. 第二遍（上工具）：读 BPF Performance Tools 对应章节，掌握"用 BPF 怎么测"。
  4. BPF（Ch.15 / 全书）：长期进阶方向，对想深入自研观测平台的团队。
  5. Ch.16 案例研究：把方法学串起来的范本，最后读。
这给 PM 一张"读这本 800 页书的导航图"：不用全读，但 Ch.2 方法学必须吃透——它提供可迁移的思维骨架。两本书 + 一个仓库（github.com/brendangregg/bpf-perf-tools-book）构成完整工具链学习闭环。注意：《性能之巅》本身没有官方 GitHub 仓，只有 brendangregg.com/sysperfbook.html 作为官网；bpf-perf-tools-book 是它的"eBPF 版实践手册"。

⑨ 关键 rationale + 反事实

R1：为什么方法先于工具？

反事实：不学方法论直接上 perf record，90% 概率盯错热点。因为采样只覆盖 on-CPU 时间，IO / 锁 / 网络等待根本看不见。Gregg 反复强调反方法论是"先有工具再瞎试"——Blame-Someone-Else（甩锅）、Ad-Hoc（凭直觉乱试）、Google-Search（搜到啥试啥）是三大陷阱。方法学先行让"看什么、怎么解读"有纪律，工具只是执行手段。

R2：为什么 USE 必须配 RED？

反事实：用 USE 监控数据回流服务，会把注意力错放在机器 CPU / 内存上，而真实瓶颈可能是上游队列或慢 SQL。USE 是资源 / 机器视角（这辆车 / CPU / GPU / 磁盘扛得住吗），RED 是服务 / 用户视角（这个请求 / 服务的用户体验爽吗）。AD 平台既有车端硬件资源又有云端请求驱动服务，两套必须合用——和嵌入式团队聊 USE，和 SRE 团队聊 RED。

R3：为什么 on-CPU 必须配 off-CPU？

反事实：只给 on-CPU 火焰图，永远看不到 DataLoader 阻塞 GPU 的真相——训练吞吐上不去但 GPU 利用率不高，根因在 off-CPU（IO / 锁 / 网络等待）。Gregg 给的经验：off-CPU 分析能解决约 40% 问题，加上 wakeup 升到约 70%。on-CPU + off-CPU 一起 = 完整 wall-clock 画面。

R4：为什么延迟必须看分布不看均值？

反事实：只看 iostat 的平均 await，会把 P99 = 200ms 的尾延迟误判为"磁盘平均 5ms 没问题"。AV 在线推理延迟（感知 → 规划 → 控制）是安全红线，平均值 99ms 但 P99 = 300ms 是不可接受的。WCET（最坏情况执行时间）比平均执行时间重要——Apollo 实测控制均值 10ms 但偶尔 1s+ 不输出。Heat Map / 直方图思维直接迁移到"端到端延迟预算分解"。

R5：为什么性能箴言按"消除→缓存→减少→异步→预计算→并发→更便宜"排序？

反事实：每次性能问题都跳到"加机器 / 加卡"——这是最贵方案，运维成本爆炸且没解决软件层面的低效。性能箴言七诀是优化方案的 brainstorming 框架，越靠前越优先（成本越低）。PM 提需求 / 写 RFC 时用它穷举改进方向（不回流 / 缓存 / 批处理 / 车端预标注 / 异步并发 / 下推 ClickHouse），直接影响成本与架构决策。

R6：为什么 GPU 利用率 ≠ 算力利用率？

反事实：把 GPU_UTIL=100% 当成"GPU 算力被充分利用"，会错过所有 stall 优化机会。DCGM 的 GPU_UTIL 定义是"采样周期内至少一个 kernel 在执行的时间百分比"——可能 util=100% 但 stall 严重（SM 在等显存、在等 PCIe、在等同步）。要配合 Nsight / Tensor Core 利用率一起看。

R7：为什么 ROS2 上车延迟不可控的根因是 OS 调度而非模型？

反事实：默认认为是模型慢，让算法改了三轮模型，结果根因是某个 ROS callback 没绑核被网卡中断抢了。ROS2 / ROS 默认走 Linux best-effort CFS，不区分实时线程。看到 onboard 延迟 bug，先问"是 CFS / 优先级问题还是模型 inference 慢"——三套解法是 PREEMPT_RT 内核 + SCHED_FIFO 绑核 + ROS-Llama / CyberRT 自动延迟管理。

⑨' 三个最深的性能认知

认知 1：性能问题不可解，根因往往是"看了错的东西"——方法学是"避免盲区"的纪律

USE / RED / 60s / 负载画像 / 延迟拆解，本质都是"强制把你的注意力铺到对的切片上"。前者扫资源、后者扫服务、60s 扫高阶信号、画像扫负载形态、拆解扫延迟构成。Gregg 自评 USE 用 5% 努力解决 80% 问题——因为它把"你也测不到什么"明文化了（known-unknowns 练习）。这条认知的杠杆点：你日常的"看仪表盘找瓶颈"本质就是性能分析，方法学把它形式化为可复用模板——这是从执行型 PM 跨入架构师最稀缺的"抽象 + 迁移"能力。

认知 2：on-CPU 只讲一半的故事，off-CPU 才是 AD 数据闭环的隐性瓶颈所在

AD 数据闭环里大量是 IO / 锁 / 网络等待（回灌、序列加载、序列化、卡 GPU），on-CPU 火焰图完全看不到。off-CPU 分析解决约 40% 问题，加上 wakeup 升到约 70%。这条直接决定你能不能解释"为什么训练吞吐上不去但 GPU 利用率不高"——on-CPU 看模型计算，off-CPU 看 DataLoader / 锁 / 网络等待。offwaketime 是定位这类"CPU 不忙但端到端慢"的最终武器。这条认知的杠杆点：理解"采样 vs 追踪""on-CPU vs off-CPU"的开销分水岭，你才知道什么能在车端常开、什么只能诊断时短开——这是把性能工具落到 AD 工程实践的边界感。

认知 3：100ms 是 AD 性能的硬约束信仰，WCET 比均值重要，延迟必须按 P99/P999 分配预算

Berkeley EECS-2019-39：高速公路上每多 100ms 延迟 = 刹车距离多 3 米。这个 100ms 是感知 → 规划 → 控制的整条链预算，不是单环节预算。Apollo 实测：感知均值 125ms 但常常超 250ms；控制均值 10ms 但偶尔 1s+。模型推理时间方差极大：同环境不同帧差 50%，不同环境差 10%，换模型差 100%。AV 是 hard RTES，只看平均会被尾巴杀死。这条认知的杠杆点：PM 用 100ms 当评审否决门槛，每加一个 head / 一层 transformer 都要回答"多花了多少 ms，撞没撞 100ms 预算"；用 P99/P999 而非均值分配预算——这是从"实现熟练度"到"判断力领先"（认知契约第 4 条）的关键跃迁。

这三个认知合起来，就是从"数据闭环 PM"到"综合架构师"的关键一跳：方法学先行（认知 1）让你能跨域沟通；on-CPU + off-CPU 双视角（认知 2）让你能与算法 / 平台工程师在同一张图上对话；100ms + WCET 信仰（认知 3）让你能在架构评审中独立判断、不被"宣传口径"带偏。这正是系统级性能诊断语言的核心——掌握它意味着能独立判断性能根因、能与 SRE / 内核团队对等对话、能在平台架构评审中提出有据可查的优化方向。
