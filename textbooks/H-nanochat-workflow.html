① 定位：nanochat 是什么、为什么极简、与 G 的承接

1.1 它是 Karpathy 亲手铺的因果链上"补齐全栈"的最后一环

你在 Zero-to-Hero 里走过的因果链：micrograd（反向传播）→ makemore（语言建模）→ nanoGPT（最小可跑预训练）。这条链的终点是"能读懂预训练代码"。nanochat 在这条链上补齐的，是 nn-zero-to-hero 没有教的工程闭环——把分词训练、SFT、RL、评测、推理全部接上，让你第一次拥有"我亲手训过一个能聊天的 ChatGPT"的体验。

定位句很直接：README.md:6 —— "nanochat is the simplest experimental harness for training LLMs. It is designed to run on a single GPU node, the code is minimal/hackable, and it covers all major LLM stages including tokenization, pretraining, finetuning, evaluation, and inference." pyproject.toml:4 更直白："the minimal full-stack ChatGPT clone"。

能力锚点：README.md:6,24 —— 在 8xH100 上 ~1.5 小时、~48 美元复现 GPT-2 级能力（2019 年成本约 43000 美元，7 年降本约 1000 倍）。这是可验证的能力锚点，不是吹的。

README.md:207-208 给出明确血统："The name (nanochat) derives from my earlier project nanoGPT, which only covered pretraining ... nanochat is also inspired by modded-nanoGPT."

如果 nanochat 像 nn-zero-to-hero 那样停留在"单阶段教学"（只讲预训练），读者毕业后会卡在"我懂 attention，但怎么把原始模型变成能聊天的 ChatGPT"。nanochat 的价值恰在于把 nn-zero-to-hero 教过的每个零件（attention、优化器、反向传播）重新组装成一条端到端流水线。不读这句定位，会把 nanochat 当成又一个 nanoGPT 而错过它的全栈教学意图。
你已经"在脑子里"跑过 micrograd 的反向传播和 makemore 的语言建模——这里不要重新学 attention，要把注意力放在"同一段 forward+backward 怎么被组装进 tokenizer → pretrain → SFT → eval → inference 的工业流水线"。模型先行：先在脑中画出这条流水线，再去读每一站的代码。

1.3 为什么极简：单一复杂度旋钮 --depth

传统做法是同时面对 n_layer / n_embd / n_head / lr / batch / weight_decay / 步数 等十几个互相耦合的超参。nanochat 的设计决定：用户只暴露一个整数 --depth（Transformer 层数），其余全部由 scaling laws + muP 式外推自动算出（README.md:108）。这 60 行代码（scripts/base_train.py:260-304）是全 repo 最值得反复读的部分。

因果链：depth → model_dim=depth×64（base_train.py:51）→ num_heads=model_dim//head_dim（base_train.py:129-143）→ target_tokens=ratio×scaling_params（Chinchilla，base_train.py:269）→ batch=Bopt∝D^0.383（Power Lines，base_train.py:277-283）→ lr∝√(B/B_ref)（base_train.py:286-294）→ weight_decay=λ_ref·√(B/B_ref)·(D_ref/D)（T_epoch，base_train.py:296-304）。全部以 d12 为参考基准（base_train.py:271-274）。

如果像 HuggingFace transformers 那样给每个超参一个独立旋钮，读者立刻被配置对象淹没、读不下去，更无法审计"这个 lr 为什么是这个值"。单一旋钮的因果是：少暴露耦合超参 → 读者能审计每一行推导 → 理解现代训练理论为什么这么设参 → 反过来能改、能 fork。这就是 Karpathy 把"认知复杂度"和"美元成本"并列当成 accessibility 的原因（README.md:201）。

1.4 极简不等于简陋：与"框架"的对抗性定位

README.md:201 原话："nanochat is not an exhaustively configurable LLM 'framework'; there are no giant configuration objects, model factories, or if-then-else monsters ... It is a single, cohesive, minimal, readable, hackable, maximally-forkable 'strong baseline' codebase."

极简哲学的微观证据无处不在：

  • nanochat/__init__.py 是 0 字节空文件——一个 package 但不预导入任何东西，没有魔法。
  • nanochat/common.py:216-223 的 DummyWandb 类——"Useful if we wish to not use wandb but have all the same signatures"。连"可选依赖"都用同签名的空对象实现，而不是 if-wandb-else。
  • tasks/common.py:21-42 的 HubDataset——"Minimal stand-in for a HuggingFace datasets Dataset"，宁可自己写 60 行 wrapper 也不引 datasets 库。

整个 repo 核心库 nanochat/ 14 个 .py 文件约 3800 行，入口脚本 scripts/ 9 个约 3000 行，加 tests/tasks/runs 合计约 7000 行 Python+shell——真的可以通读。

读 nanochat 时克制住"这工程上不够工程"的评判欲——它的目标不是生产级框架，而是让你能 hold 住整个系统的心智模型。先通读、建模型，再谈工程化。Function Owner 视角会注意到这正是"认知复杂度也是成本"的产品判断。

② 环境搭建：uv / GPU / CUDA 命令级

2.1 硬件自检：跑命令前先回答两件事

在敲任何 uv sync 之前，先回答：(1) 有没有 CUDA？(2) SM 算力是多少？这两件事决定 dtype、是否走 FP8、是否走 FA3、是否需要 GradScaler。nanochat 的设计：模型权重始终 fp32（为优化器精度），但 Linear 在 forward 时把权重 cast 到全局 COMPUTE_DTYPE（nanochat/common.py:16-32），由硬件自动决定：

硬件默认 dtype为什么
CUDA SM 80+（A100/H100/4090/L4...）bfloat16原生 bf16 tensor cores
CUDA SM < 80（V100/T4...）float32无 bf16；可手动 NANOCHAT_DTYPE=float16+GradScaler
CPU / MPSfloat32安全默认；新版 macOS MPS 可手动开 bf16 省 ~25% 显存

覆盖：NANOCHAT_DTYPE=float32|bfloat16|float16 环境变量（README.md:124-129）。

nvidia-smi                         # 看 driver/CUDA 版本
python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_capability())"
# 输出例：True (9, 0) → H100 (sm90)，自动 bf16，可用 fp8/FA3
# 输出例：True (8, 9) → 4090 (sm89)，自动 bf16，FA3 Ada kernel
# 输出例：True (7, 5) → V100 (sm75)，自动 fp32，建议 NANOCHAT_DTYPE=float16
# 输出例：False → CPU/MPS 路径，用 runcpu.sh

2.2 uv + torch + CUDA 版本对齐（最容易卡住的一步）

nanochat 用 uv（Astral 的极快 Python 包/虚拟环境管理器）替代 pip+venv+requirements.txt 三件套。Python 要求 >=3.10。关键在 pyproject.toml:36-51 的 [tool.uv.sources] 把 torch 路由到两个 PyTorch 官方 index：--extra gpu 拉 torch==2.9.1+cu128，--extra cpu 拉 +cpu。两者互斥（pyproject.toml:62-69 conflicts 声明），装错 extra 会得到错误的后端。

反事实陷阱：忘了带 --extra gpu，或系统已有 CPU torch，会出现 torch.cuda.is_available()=False 而 nvidia-smi 一切正常。根因是 PyPI 上的 torch 默认是 CPU 版。pyproject.toml:37-41 的 dual-index 把 torch 通过 extra 精准切到 download.pytorch.org/whl/cu128——这是 uv 的 index 选择机制。
# GPU 用户（A100/H100/4090 等）
curl -LsSf https://astral.sh/uv/install.sh | sh   # 装 uv（如果还没装）
uv sync --extra gpu                                # 拉 torch 2.9.1+cu128
source .venv/bin/activate

# CPU / MPS 用户（MacBook 等）
uv sync --extra cpu
source .venv/bin/activate

# 开发依赖（pytest/matplotlib/transformers 等）
uv sync --extra gpu --group dev

运行时依赖只有 9 个（pyproject.toml:7-17）：filelock / kernels / numpy / psutil / pyarrow / rustbpe / tiktoken / torch==2.9.1 / wandb——刻意最小。CUDA 12.8 是 cu128 wheel 的目标运行时，你的驱动要支持 CUDA 12.8+。

2.3 dtype 决策的代码落点

nanochat/common.py:16-32 的 _detect_compute_dtype 实现"NANOCHAT_DTYPE 优先；否则按 CUDA capability 选 bf16/fp32"。README.md:114-133 给出三档硬件默认表。dev/LOG.md:72-103 记录 2026-03-04 去 autocast、改显式 dtype、加 fp16 GradScaler 的决策因果：autocast 只在 Linear 上有用，显式化获得细粒度控制。

nanochat 主动放弃了 torch.amp.autocast。模型权重存 fp32，Linear.forward 把权重 cast 到 x.dtype（nanochat/gpt.py:45-50），embedding 直接存 COMPUTE_DTYPE 省一半显存。fp16 因 GradScaler 不能 unscale fp16 梯度，embedding 例外保 fp32（dev/LOG.md:85-87）。

③ 模型架构速览（对照 G 的 GPT）

你在 nn-zero-to-hero 第 8 讲见过的 nanoGPT 风格代码，nanochat 把每个细节换成了 2024-2026 年的 SOTA 选择：rotary 位置编码（替代 learned positional embedding）+ RMSNorm 无参数（替代 LayerNorm）+ QK norm + GQA + logit softcap + untied embedding + relu² MLP + sliding window attention + Flash Attention 3。

3.1 GPTConfig 默认值（nanochat/gpt.py:28-39）

flowchart LR
  A["token id (B,T)"] --> B["wte 查表 (B,T,n_embd)"]
  B --> C["norm (RMSNorm 无参)"]
  C --> D["smear 门控混入上一 token"]
  D --> E["Block × N: pre-norm 残差"]
  E --> F["attn: RoPE+QK norm+GQA+滑窗+FA3"]
  E --> G["mlp: relu^2"]
  F --> H["backout 减中间层残差"]
  G --> H
  H --> I["norm + lm_head (untied)"]
  I --> J["logit softcap tanh ×15"]
  J --> K["cross_entropy(ignore_index=-1)"]

GPTConfig 默认 sequence_len=2048, vocab_size=32768, n_layer=12, n_head=n_kv_head=6（GQA 退化为 MHA）, n_embd=768, window_pattern='SSSL'。这些默认值只在 --depth 没指定时生效；实际训练时 build_model_meta（base_train.py:129-143）会按 depth 重算 n_embd = depth×64、n_head = model_dim // head_dim。

3.2 五个非标准 trick（Karpathy 风格的精华）

这是 nanochat 区别于 vanilla nanoGPT 的核心创新，全部塞在 GPT 里：

  • smear（gpt.py:185, 476-492）：把上一个 token 的嵌入按门控混入当前 token，提供便宜的 bigram 信息。训练时切片，推理时从 KV cache 取。
  • resid_lambdas / x0_lambdas（gpt.py:181-188, 234-241）：每层残差的可学缩放系数，让网络自己决定"残差传多强"和"把初始嵌入混回多少"。早层强、深层弱。
  • value_embeds（ResFormer 风格）（gpt.py:53-55, 82, 94-97）：隔层再查一次 token embedding 加到 value 上，由 ve_gate 门控，gate=3·sigmoid(...)，范围 (0,3)。
  • backout（gpt.py:188, 497, 506-507）：在最后一层前减掉中间层的残差，去掉低层特征。backout_layer = n_layer//2。
  • logit softcap=15（gpt.py:511-515）：用 tanh 把 logits 压进 [-15,15]，平滑掉训练末期 logit 漂移。
这 5 个 trick 在任何 Transformer 教材里都不会一起出现，它们是"读源码才能学到的当代经验"。建议对每个 trick 单独画一张"数据怎么流"的图，并问：如果把这个 lambda 设成常数 0 或 1，forward 退化成什么？这是检验自己真懂的方式。gpt.py:103-104 的 QK norm ×1.2 锐化是一个 magic number，作者自己标了 TODO——它在补偿 RMSNorm 把方差压成 1 带来的 scale 损失。

3.3 代码地图（别去错地方找训练循环）

  • 训练循环：在 scripts/base_train.py:416-543（while True 事件驱动：eval/core/sample/checkpoint/单步）。不在 nanochat/engine.py ——那个 engine 是推理引擎。
  • 模型定义：nanochat/gpt.py（555 行）。GPT.forward(idx, targets) 在 gpt.py:459-524：targets 非 None 时返回 cross_entropy 标量 loss（L520），否则返回 logits（L524）。
  • 优化器：nanochat/optim.py（459 行）。MuonAdamW 类 docstring 在 optim.py:184-259，明确写 "nanochat does not use DDP"。
  • 数据加载：nanochat/dataloader.py。
  • 推理/KV cache：nanochat/engine.py。
反事实：以为 engine.py 是训练循环的人，会去那里改 lr，结果推理才走那条路径，训练 loss 根本不动。知道"训练循环在 scripts/、模型在 nanochat/gpt.py、优化器在 nanochat/optim.py"，才能在三分钟内定位任何 bug。

4.2 数据准备·预训练：ClimbMix-400B parquet 分片

nanochat/dataset.py:23-27：BASE_URL 指向 karpathy/climbmix-400b-shuffle，MAX_SHARD=6542，DATA_DIR = base_data_climbmix。每个 parquet ~100MB（zstd 压缩），只有一列 text。

val 切法巧妙：dataset.py:75——train = parquet_paths[:-1]，val = parquet_paths[-1:]。最后一个 shard 永远是 val，无需手动维护 split。

下载 dataset.py:98-133：5 次重试、指数退避 2^attempt 秒、先写 .tmp 再 os.rename（原子），断点续传靠"文件存在就 skip"。

export NANOCHAT_BASE_DIR="$HOME/.cache/nanochat"
python -m nanochat.dataset -n 8      # 先下 8 个 shard（~800MB）够训 tokenizer
python -m nanochat.dataset -n 170 &  # 后台下 170 个 shard 够 GPT-2 级预训练
DATASET_DOWNLOAD_PID=$!
# ... 训 tokenizer + base_train 前先 wait $DATASET_DOWNLOAD_PID
为什么不直接用 HuggingFace datasets.load_dataset？那个库会把整个数据集 tokenize 后物化到磁盘（几小时+几十 GB），nanochat 选择"流式+行内实时 tokenize"——dataloader 名字里 tokenizing 的由来。row_group 是"数据集的随机访问单位"，理解了它你才能看懂 DDP 的 start/step sharding（每张卡按 rank, rank+world_size, rank+2·world_size, ... 跳着读 row_group）。

4.3 tokenizer·训练与推理：rustbpe + tiktoken 双引擎

因果：训练时要在 2B 字符语料合并出 vocab_size=32768 的词表，这一步很慢且需要 Rust，用 rustbpe；推理时（训练循环每秒几百万 token）要极致速度，把训练出的 mergeable_ranks 喂给 tiktoken（OpenAI 的 Rust 加速库）做编码。两步通过 pickle 保存的 tiktoken.Encoding 衔接。

nanochat/tokenizer.py:9-21 的 9 个 SPECIAL_TOKENS：<|bos|>（预训练用）+ user/assistant/python/output 的 start/end（SFT/RL 用）。它们不参与 BPE 训练，在 Encoding 构造时追加（tokenizer.py:42-61），ID 连续递增。

tokenizer.py:23-26 SPLIT_PATTERN 故意用 \p{N}{1,2} 而非 GPT-4 的 {1,3}——作者注释"为小词表省 token，验证 2 是 32K 词表的甜点区"。这是词表设计的取舍，不是抄来的。

python -m scripts.tok_train                           # 默认 vocab=32768, max-chars=2B, doc-cap=10000
python -m scripts.tok_train --max-chars=2000000000     # runcpu.sh 路径，M3 Max 约 34 秒
python -m scripts.tok_eval                             # 报告压缩率

4.4 上下文构造·预训练：BOS-aligned Best-Fit packing

nanochat/dataloader.py:1-17 模块 docstring 直白："BOS-aligned loses ~35% of tokens to cropping, but ensures every token can attend back to the BOS token"。每一行强制以 BOS 开头，best-fit 算法挑"能整段放进去的最大文档"，放不下就裁一段补满。代价是丢 35% token，换来"每个 token 都能 attend 回 BOS"——上下文质量更高。

核心算法在 dataloader.py:122-152。row_capacity = T+1（dataloader.py:98）：多一位让 targets = inputs[1:] 对齐。这就是"下一个 token 预测"的物化。

反事实：如果用 nanoGPT 旧式"拼接+硬裁"（不强制 BOS 对齐），T=2048 时一行有 5-6 个文档，第 2-6 个文档的 token 看不到 BOS，bpb 会明显变差。best-fit（挑最大能放的）比 first-fit（顺序放）能减少裁剪次数——这是 bin-packing 经典启发式。35% 听起来多，但 Karpathy 实验证明"质量换数量"在这个尺度值得。

4.5 batching：单次 HtoD 传输 + state_dict 断点续训

每生成一个 batch 要把 B 行 × row_capacity 的 Python int 装进 tensor 再搬 GPU。nanochat 预分配三块连续 buffer（dataloader.py:111-120）：row_buffer（CPU 组装）、cpu_buffer（pinned memory，2·B·T 一维）、gpu_buffer（GPU 上 2·B·T 一维），.view() 切 inputs/targets 视图。最终只有一次 gpu_buffer.copy_(cpu_buffer, non_blocking=True)，和 GPU 计算重叠。

每个 batch 附带 state_dict(pq_idx, rg_idx, epoch)，写进 checkpoint 后能精确续训（dataloader.py:40-71）。

base_train.py:518 x, y, dataloader_state_dict = next(train_loader) 出现在 backward 之后——这是"异步预取"的关键位置，GPU 还在算 backward 时 CPU 已在准备下个 batch。这就是为什么 dataloader 要 yield 而不是 return——让控制权在 CPU 装填和 GPU 计算之间交替。也是为什么 nanochat 不用 PyTorch DataLoader（它的 num_workers 抽象会破坏这种细粒度重叠控制）。

4.6 SFT 数据：Task 抽象 + bestfit-PAD packing（绝不裁）

SFT 数据是对话，来自 SmolTalk/MMLU/GSM8K，统一抽象成 Task（tasks/common.py:85-123）。TaskMixture（tasks/common.py:129-161）展开 (task_idx, local_idx)，用 random.Random(42).shuffle 打散——同一 task 传多次就过采样。

SFT packing 跟预训练本质差异：不能裁剪——一条对话被裁了，loss mask 就错位，监督信号全乱。所以 SFT 用 best-fit + 填充：能整段放就放，放不下就 pad 到行尾，pad 位置 target 设 -1（cross_entropy 的 ignore_index，chat_sft.py:280-296）。

tokenizer.py:140-224 的 render_conversation：user 段全 mask=0；assistant 文本/python_call 段 mask=1；python_output 段 mask=0（因为是解释器生成的，不该监督模型去"生成"）；system message 被"缝合"进下一条 user message（tokenizer.py:156-165）。

mask 的设计就是 SFT 区别于预训练的本质——"不是每个 token 都该被预测"。mask=0 的 token 仍然在前向里被 attention 使用（提供上下文），但反向时不产生梯度。看 tests/test_tokenizer.py:73-75 的断言把规则记死。

4.7 bits-per-byte (bpb)：tokenizer 词表无关的 loss 归一化

朴素 mean cross-entropy 依赖 vocab size——词表越大每个 token 携带信息越多，loss 看起来越低，但模型实际能力没变。bpb 解决：不除以 token 数，除以这些 token 对应的字节数。

nanochat/loss_eval.py:9-65：loss2d = model(x, y, loss_reduction='none') 拿逐 token loss；num_bytes2d = token_bytes[y_safe]；total_nats += (loss2d × (num_bytes2d > 0)).sum()（同时屏蔽特殊 token，它们 num_bytes=0）；bpb = total_nats / (log(2) × total_bytes)（L64）。

token_bytes.pt 在 scripts/tok_train.py:76-91 训完 tokenizer 立刻构建：每个 id 用 decode_single_token_bytes 拿原始字节数（不能用 decode 成字符串，否则非 UTF-8 token 会损坏），特殊 token 记 0。

反事实：如果只用 mean loss，把词表从 32K 扩到 128K，loss 看起来降 30%，但模型没变好——你会被误导继续扩大词表。bpb 是 perplexity 的"去 vocab 化版本"，让跨 tokenizer 实验可比。这就是为什么 README 排行榜主指标是 val_bpb 而不是 val_loss。

5.3 scaling laws 怎么自动算出 batch / lr / wd / 步数

scripts/base_train.py:260-304 是全 repo 最值得反复读的 44 行，把四套现代训练理论压缩成可审计的数学：

  • Chinchilla（L261-269）：target_tokens = ratio × scaling_params。
  • Power Lines（L277-283）：B ∝ D^0.383，round 到最近的 2 的幂。
  • AdamW sqrt scaling（L286-294）：η ∝ √(B/B_ref)。Muon 盲跟 AdamW 理论（L292 注释承认）。
  • T_epoch 框架（L296-304）：λ = λ_ref · √(B/B_ref) · (D_ref/D)，引 arxiv 2405.13698。
  • 全部以 d12 为参考基准（B_REF = 2^19 = 524288，L274），muP 思路。
换 batch size 不是独立操作，必须同时按 √(B/B_ref) 调 lr、按 √(B/B_ref)·(D_ref/D) 调 weight decay。你以后看任何训练框架，先问它"换 batch 时 lr/wd 怎么跟着变"——没有这套连锁缩放的框架都是不严肃的。

5.4 Muon + AdamW 混合优化器（nanochat 不用 DDP 的关键）

因果：纯 AdamW 在大模型上慢且占内存（每个参数要存一阶+二阶矩）。KellerJordan 的 Muon（MomentUm Orthogonalized by Newton-schulz）对 2D 矩阵参数做"动量+正交化"，收敛快、效果稳。但 Muon 不能用在 embedding/lm_head/scalar（必须 2D）。所以 nanochat 用混合：矩阵参数走 Muon，其余走 AdamW。

更进一步：nanochat 干脆不用 PyTorch DDP，把"梯度同步 + ZeRO-2 分片"直接写进 MuonAdamW.step()（nanochat/optim.py:184-259）。step() 三阶段（optim.py:428-459）：(1) 异步 reduce（_reduce_adamw/_reduce_muon，L274-318），(2) 等待 reduce 完成、算更新、异步 gather（_compute_adamw/_compute_muon），(3) 等 gather 完成拷回（_finish_gathers）。world_size==1 时所有通信短路，退化为单卡。

Muon 的四个 2025 年微创新全在 muon_step_fused（optim.py:111-180）：MuonEq 行均衡、Polar Express 正交 5 次迭代、NorMuon 方差归约、cautious weight decay（只对 update 和参数同号的维度衰减）。

这是 nanochat 工程上最反直觉、最值得学的一块。90% 的 PyTorch 教程教你 model = DDP(model)，nanochat 说"不，我把同步塞进 optimizer"，这样能精细控制通信-计算 overlap，还能 ZeRO-2 分片省显存。反事实：用 DDP 每张卡存全量 optimizer state，8 卡 d20 显存翻 8 倍可能 OOM；用纯 AdamW 不用 Muon，矩阵参数收敛慢 30-50%。
不要被 ZeRO-1/2/3 的术语吓到。先在 world_size==1 路径下读懂 optimizer.step，再去读 reduce_scatter/all_gather。关键洞察：nanochat 的"分布式"只在 optimizer 里，model forward/backward 完全不知道分布式——这跟 DDP（每层 hook 同步）是两种截然不同的哲学。debug 多卡问题时，先确认 world_size、再确认 shape[0] % world_size == 0（optim.py:288 的 assert）。

5.5 SFT 命令：继承 pretrain 超参 + 三数据 mixture

# speedrun.sh SFT
torchrun --standalone --nproc_per_node=8 -m scripts.chat_sft -- --run=$WANDB_RUN

# CPU / MacBook SFT（~10 分钟）
python -m scripts.chat_sft -- \
    --eval-every=200 --eval-tokens=524288 --num-iterations=1500 --run=$WANDB_RUN

关键设计（scripts/chat_sft.py:96-115）：SFT 默认从 base checkpoint 继承 max_seq_len/device_batch_size/total_batch_size/三个 lr（CLI 不传就用 checkpoint meta 里的值），并 warm-start 优化器（load-optimizer=1，只取 momentum buffer，LR 重置，chat_sft.py:139-149）。数据 mixture：chat_sft.py:162-173——SmolTalk（~460K 通用对话）+ MMLU × mmlu-epochs（默认 3）+ GSM8K × gsm8k-epochs（默认 4）。

LR 调度用 progress（0→1）而非绝对 step，因为 SFT 数据驱动停止、事先不知 num_iterations。lr 先乘 init_lr_frac（默认 0.8）再走 warmup/constant/warmdown。SFT 把 weight decay 设为 0（pretrain 末段已 warmdown 到 0）。

两个工程点容易踩：(1) 优化器 warm-start 只继承 momentum 不继承 LR——因为 pretrain 的 warmdown 已把 LR 压到 ~0，直接继承会让 SFT 一开始学不动；(2) 数据用 bestfit-pad 打包，padding 位 target 置 -1，保证不丢 token 也不在 padding 上算 loss。反事实：用全新优化器或继承全部 state 含 LR，SFT 前 100 步 loss 几乎不动，会误以为数据有问题。

5.6 RL 命令：GRPO 简化成 REINFORCE，在 GSM8K 上跑

# 单卡
python -m scripts.chat_rl -- --run=default

# 8 卡
torchrun --standalone --nproc_per_node=8 -m scripts.chat_rl -- --run=default

RL 从 sft checkpoint 加载（phase=eval），用 Engine 做 rollout 采样。流程（scripts/chat_rl.py:96-146）：①render_for_completion（tokenizer.py:241-259）把对话的 user 部分渲染成 token，去掉最后一条 assistant，末尾补 <|assistant_start|>"点火"；②engine.generate_batch（num_samples=16, max_new_tokens=256, temp=1.0, top_k=50）采样，同时返回 mask（forced token=0，采样 token=1）；③用 GSM8K 的 reward 函数给每个采样打分；④reward 减均值变 advantage（不用 z-score，作者注释说简化成 REINFORCE，chat_rl.py:1-17）；⑤loss = -sum(logp × advantage)（chat_rl.py:262-273）。

这是整章最难的部分。RL 的 inputs/targets 不是从磁盘读的，是模型 forward 两次——第一次采样（eval 模式 no_grad），第二次算 logp（train 模式）。mask 在这两次之间传递"哪些 token 是模型选的，哪些是环境强制的"。建议先读 engine.py:238-270 的 mask 逻辑，再回头看 chat_rl.py 的 loss。RL 当前不支持 fp16（README.md:133）。

⑥ 评测与生成

6.1 评测一分为二：概率侧 vs 序列侧

两个不同问题：(1)"这个模型对真实文本感到多意外？"（训练监控，越小越好）；(2)"这个模型能解多少道题？"（能力体检，越准越好）。回答方式根本不同——前者不采样、只算概率读数；后者要么看选项 logits 选答案（categorical），要么真采样生成再判对错（generative）。

"不采样"是为了可复现——采样引入随机性，bpb/CORE 想要确定性概率读数。证据：scripts/base_eval.py:130 --eval 默认 core,bpb,sample 三连；chat_eval.py:28 run_generative_eval（采样）vs chat_eval.py:87 run_categorical_eval（不采样、只 argmax）。

  T1 -->|yes| K["topk 取 k 个, vals/temperature, softmax over k, multinomial"]
  T1 -->|no| F["logits/temperature, softmax 全词表, multinomial"]

6.2 bpb：训练监控的"标准化量尺"

已在 §4.7 详述。loss_eval.py:64 bpb = total_nats / (log(2) × total_bytes)。这个公式里 nats 是以 e 为底的 loss，除以 log(2) 转成 bits，再除以字节数——本质是"平均猜对一个字节需要多少比特"。perplexity 在 nanochat 里几乎不出现，因为 Karpathy 认为它依赖 vocab size，直接用 bpb 替代。

6.3 CORE / ChatCORE：centered accuracy 去随机基线

裸准确率没法跨任务比——ARC 4 选 1 随机 25%，GSM8K 随机 0%。Karpathy 用 centered accuracy：(acc - random_baseline) / (1 - random_baseline)（base_eval.py:112），把随机基线映射成 0、完美映射成 1，再对所有任务求平均（base_eval.py:117）。

base 模型这套叫 CORE（DCLM 论文 ICL 基准），三类任务（nanochat/core_eval.py:232-237）：(1) multiple_choice（如 ARC）上下文相同、选项是不同续写，找平均 loss 最低；(2) schema 上下文变、续写相同；(3) language_modeling 上下文是续写前缀，看 argmax 能否逐 token 命中。三类都不采样，全靠 forward_model（core_eval.py:144-164）拿逐 token loss + argmax 判定。这是 logits-based scoring——base 模型还没 SFT，不能用"生成一个字母"评。

chat 模型这套叫 ChatCORE（chat_eval.py:203-208, 235-237）。GPT-2 的 CORE 分是 0.256525（README.md:24），整个 speedrun 就是冲这个数。

6.4 生成/sampling：temperature 和 top-k 改了什么

nanochat/engine.py:141-156 sample_next_token 全部逻辑：temperature=0 直接 argmax（确定性，等同于 greedy）；temperature>0 先除以温度再 softmax；top-k 先取 logits 最大的 k 个、其余置 -inf 再 softmax，强制只在 top-k 候选里采。两者可叠加。

对照阅读：chat_cli.py:18-19 默认 temperature=0.6, top_k=50（Karpathy 给 chat 的"甜点区"）；base_eval.py:184 conditioned sample 用 temperature=0（确定性看模型"最想说"什么）；base_eval.py:192 unconditioned sample 用 temperature=1.0 + num_samples=8（看模型"自由发挥"分布广不广）。

采样用独立 torch.Generator(device=device) + 固定 seed=42（engine.py:182-183），保证同 prompt 可复现。

6.5 评测/生成的工程胶水

  • KV cache（engine.py:82-138）：prefill + decode 二段式，KVCache.prefill() 把 batch=1 的 cache 复制到 batch=num_samples（L123-137）。没有 KV cache，生成慢几十倍。
  • 分布式聚合（core_eval.py:249-261，loss_eval.py:54-58）：for idx in range(rank, len(data), world_size) 按 stride 切片，dist.all_reduce(SUM) 汇总。
  • 安全沙箱（nanochat/execution.py:47-71, 74-134）：HumanEval 要执行模型生成的 Python，用 subprocess + rlimit + 把 os.system/shutil.rmtree/subprocess.Popen 等危险 builtin 置 None。注意文档第 20-22 行自承 "not safe against malicious adversarial code"。

⑦ 调优与常见报错（显存 / lr / batch）

7.1 显存（VRAM）：OOM 第一时间调 --device-batch-size

OOM 几乎都来自 device-batch-size 太大（它决定单次 forward 的激活显存）。官方降档顺序：32 → 16 → 8 → 4 → 2 → 1（README.md:83）。三处脚本都按 depth 分档：miniseries/scaling 里 d>=28 用 8、d>=20 用 16、否则 32（runs/miniseries.sh:60-67）；speedrun 因 d24+fp8 直接用 16（runs/speedrun.sh:67）。

# 报错：CUDA out of memory. Tried to allocate ... GB
# 第一时间动作：
torchrun ... -m scripts.base_train -- \
    --depth=24 --device-batch-size=16 ...   # 从 32 降到 16
# 还 OOM：
... --device-batch-size=8 ...
# 还 OOM 且 depth 太大：
... --depth=20 ...   # 或降 max-seq-len

底层两个省显存机制：

  • base_train.py:15 PYTORCH_ALLOC_CONF=expandable_segments:True（让显存分配器复用碎片）。
  • embedding 直接存 COMPUTE_DTYPE 省一半显存；fp16 例外保 fp32（GradScaler 不能 unscale fp16 梯度，dev/LOG.md:85-87）。FP8 还能再省 ~9GB 激活（dev/LOG.md:358）。
  • 最后一道防线：gc.freeze()+gc.disable()（base_train.py:591-592），避免 Python GC 周期性扫几百毫秒。
降 device-batch-size 时盯住 base_train.py:409 的 assert：total_batch_size % world_tokens_per_fwdbwd == 0。world_tokens_per_fwdbwd = device_batch_size × max_seq_len × world_size。如果你让 total_batch_size 不能整除它，会直接 assert 崩。

7.2 学习率与调度：warmup / constant / warmdown 三段式

nanochat 用三套 lr：embedding_lr（Adam，默认 0.3）、unembedding_lr（Adam，默认 0.008）、matrix_lr（Muon，默认 0.02），外加 scalar_lr=0.5 和 weight_decay=0.28（仅 Muon）。调度是 linear warmup（warmup-steps 默认 40）→ constant → linear warmdown（warmdown-ratio 默认 0.65，即后 65% 线性降到 final-lr-frac=0.05）（base_train.py:360-369）。

Muon 还有独立动量调度（base_train.py:372-382）：前 400 步从 0.85 升到 0.97，warmdown 段再从 0.97 降到 0.90。weight decay 走 cosine 到 0（base_train.py:384-386）。batch 变化时所有 lr 乘 batch_lr_scale=√(B/B_ref)，weight_decay 额外乘 (D_ref/D)。

fp16 训练自动启用 GradScaler（base_train.py:324-326）。SFT 支持 fp16，RL 暂不支持 fp16（README.md:133）。

"warmdown 占 65%"是一个很激进的选择（传统 cosine 是全程衰减），来自 modded-nanogpt 经验。不要问"为什么是 0.65"，而要问"warmdown 期 lr 降到 5% 配合 momentum 降到 0.90 是在做什么"——答案：让训练末期进入"精细微调"模式，动量小、步长小，把 loss 压到最低。

7.3 batch size 与梯度累积：单卡自动等价多卡

total_batch_size 是每步全局 token 数；device_batch_size 是每卡每次 forward 的样本数。两者通过 grad_accum_steps 桥接（base_train.py:406-413）：grad_accum_steps = total_batch_size // (device_batch_size × max_seq_len × world_size)。

8 卡 device-batch-size=32 一步出 8×32×2048=524288 token（=2^19，正是 d12 最优 batch），单卡 device-batch-size=32 自动累积 8 步达到同样的 524288。所以 README 说"omit torchrun 自动切梯度累积，结果几乎一致，但慢 8 倍"。

Flash Attention 3 not available, using SDPA fallback非 Hopper 卡或非 bf16（正常）若 window_pattern≠L 会警告；建议 --window-pattern L
训练 loss 不降/发散warmup 太短 / batch 变了 lr 没缩放 / fp16 没 GradScaler查 warmup-steps、batch_lr_scale、COMPUTE_DTYPE
SFT 前 100 步 loss 不动用了全新优化器或继承了 LR确保 load-optimizer=1（只继承 momentum）
RL 报 fp16 相关错RL 暂不支持 fp16用 bf16 或 fp32
eval 时形状变化触发 recompile 慢torch.compile dynamic=Falseeval 用 orig_model（未 compile），见 base_train.py:246

延伸阅读

  • Karpathy nn-zero-to-hero（教材 G）：本教材的前置。nanochat 假设你已懂 micrograd / makemore / nanoGPT。
  • Chinchilla scaling laws（Hoffmann et al. 2022）：tokens:params ≈ 20:1 是 compute-optimal。nanochat 默认 ratio=12 略欠训换更快收敛。
  • Power Lines paper（arxiv 2505.13738）：Bopt ∝ D^0.383 给最优 batch size 外推公式。
  • T_epoch framework（arxiv 2405.13698）：T_epoch = B/(η·λ·D) 恒定 → weight decay 缩放公式。
  • muP / modded-nanoGPT：小模型调超参迁移到大模型；nanochat 的 d12 参考基准即此思路。
  • Muon optimizer（KellerJordan）：2D 矩阵参数的动量+正交化优化器。
  • DCLM CORE benchmark：base 模型综合能力评测，GPT-2 CORE=0.256525。
  • Flash Attention 3（varunneal kernel for Hopper，kernels-community for Ada/Ampere）：长上下文 attention 的内存优化。
  • uv 官方文档（docs.astral.sh/uv）：替代 pip+venv+requirements.txt 的极快包管理器。
  • nanochat 仓库 dev/LOG.md + dev/LEADERBOARD.md：Karpathy 的实验日志和 speedrun 排行榜，研究 repo 而非纯教学 repo 的二次定位。

本教材基于 nanochat 仓库的代码与文档整理。所有 file:line 证据均可在仓库内 grep 验证。读者按 §9 学习路径依次精读，配合 §8 命令序列在本地跑通，即可完成从 zero-to-hero 毕业到"亲手训出一个能聊天的模型"的闭环。
