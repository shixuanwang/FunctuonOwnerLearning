CH 01项目定位与本质：JoyDriver 在 E2E AD 里的位置

一句话定位：JoyDriver 是一个「以轨迹预测/规划为出口」的端到端自动驾驶模型 —— 单次前向（single forward）把多模态历史观测（向量化的 agent/ego/map + 相机图像 + 时序记忆）一次性映射成 ego 与周围 agent 的未来 6s 轨迹，工程上覆盖训练 → 评测 → 可视化 → ONNX 部署全闭环。
它在 E2E AD 里的位置不是「纯规划器」，而是 「感知（相机 BEV / 时序融合 StreamPETR）+ 预测（agents 多模态轨迹）+ 规划（ego 轨迹 + refline + refine head）」三段合一的统一网络，最末输出可以直接喂给下游控制器。

1.2 它到底输出什么：ego + agents 的未来 6s 轨迹（核心是规划，不是检测）

数据流的终点（JoyDriverV0.forward 的 Stage 4 _generate_predictions）产出的是：自车未来 60 步（60×0.1s=6s）的位置 / 速度 / 加速度 / 偏航角速率 / 模态概率，加上周围 agent 同样的 6s 轨迹，再加一条 80 步的参考线（refline）和可选的 refine 后 ego 轨迹。

configs/joydriver_v0_cfg.py:243-249 trajectory_conf: n_step=60, dt=0.1（→6s）, acc_min/max=-8/8；:250-253 refline_conf n_step=80。
src/models/joydriver_v0.py:907-968 _generate_predictions 输出 agents_traj_pred / ego_traj_pred / ego_traj_refined 等；traj_head 输出 acc/omega 后积分（:253-271 interpolate + 积分）。
src/models/joydriver_v0.py:1020-1027 Stage5 refine_ego_traj：用 map_tokens 对 ego 初轨迹做 cross-attn 残差修正。

关键洞察：head 不是在预测检测框，而是在直接回归控制层关心的运动量（acc/omega），然后内部积分成 vel/pos。所以这个模型的「产品价值」是：给定当前帧的多源观测，直接吐出可执行的未来轨迹 —— 轨迹再经下游控制器转方向盘/油门。

这定义了整个数据闭环要喂什么标签 —— 训练数据必须有「未来 6s 的 ego 真值轨迹」和「agent 真值轨迹」，不是检测框标注。模型评估用的也是 brier_fde_k（轨迹预测指标，见 run.py:83），不是 mAP。反事实：若误以为是感知模型，会去准备 3D 框标注；但实际上 loss_cfg（cfg:295-315）的全是轨迹回归 loss + 转向角约束（ego_steer_limit_deg=35），这跟检测完全不同。
端到端模型本质（必读）：传统 AD 把「感知(detector) → 预测(predictor) → 规划(planner)」拆成三个独立模型，每个有自己的 loss。JoyDriver 把三段合进一个 transformer：相机分支做 BEV 感知（但不显式出框），时序 transformer 把感知特征和 agent/ego 向量融合，最后一个 TrajectoryHead 直接出轨迹。所谓「端到端」= 一次反向传播同时优化感知+预测+规划，避免了级联误差累积。输出 acc/omega（而非直接出 pos）的好处是：物理约束（速度/加速度上限）可以硬 clamp，避免模型预测出物理上不可能的轨迹。

CH 02端到端模型本质：为什么 E2E，IL/RL，三段合一

核心问题：为什么要把感知/预测/规划焊成一张可导图？「端到端」的「端」到底从哪到哪？这一章把 E2E 的范式、训练范式（IL vs RL）、以及 JoyDriver 的 StreamPETR 时序融合机制讲透，为第 3 章的逐层架构打认知地基。

把感知（3D 检测/特征提取）和规划（轨迹预测）焊成一张可导图，梯度能从「轨迹 L2/碰撞 loss」一路回传到 RegNet 卷积核，让骨干为规划目标（而非检测 mAP）做联合优化。

常见误解纠正：读者可能以为「端到端」=「没有中间层」。更准确的说法是：中间层很多（backbone/neck/transformer/head 全在），但全部可导、全部联合训练，没有不可导的「人工缝合点」。另一个常见误解：E2E 不是「感知也输出轨迹」，而是感知和规划共享一份特征，规划 loss 倒逼感知学对。

2.2 训练范式：行为克隆（IL）而非 RL

JoyDriver 走的是模仿学习（Imitation Learning, IL），更具体是行为克隆（Behavior Cloning, BC）：训练数据是「人类驾驶员的真实未来轨迹」作为 GT，loss 是预测轨迹与 GT 轨迹的 L2 / brier-fde 等回归 loss，让模型直接模仿人类。这跟强化学习（RL）有本质区别：

维度IL / 行为克隆（JoyDriver 走的路）RL（如 UniAD/AD-MLP 之外的研究）
GT 来源人类驾驶的未来轨迹（离线、确定）环境奖励（在线、需仿真器）
训练成本低（监督学习，8 卡数百万 iter）极高（需闭环仿真，采样效率瓶颈）
分布偏移有（covariate shift：训练见过的状态 vs 部署自己陷入的状态）无（自己探索过）
可解释性低更低

JoyDriver 缓解 covariate shift 的两个工程手段（在数据侧而非算法侧）：

  1. mask_ego_history（joydriver_v0.py:731-735）：训练时随机遮蔽自车历史最后几步，逼模型从图像补全 —— 防止模型只依赖历史位置外推（容易在遮挡时崩，是捷径学习的典型）。
  2. BEV 旋转增广（augmentations.py:21-108）：同步旋转轨迹 + BEV，让模型见到更多朝向组合，缓解直行多、急弯少的数据不平衡。
给 PM 转 PM/架构师：IL 的最大软肋是 covariate shift —— 训练时模型看到的状态分布 = 人类驾驶的状态分布，但部署时模型自己犯错进入的状态不在训练分布里，错误会滚雪球。JoyDriver 用「数据闭环 + 分桶评测」缓解：每次发现失败场景 → 用规则从海量原始数据里 recall 类似帧 → 加进 manifest 重训。这本质上是用数据工程绕开 RL 的算力难题，是工业界的务实选择。

2.3 StreamPETR 时序融合：把「上一帧的检测记忆」喂给这一帧

单帧检测无法判断「这辆车会不会动、往哪动」，而轨迹规划必须知道运动历史。StreamPETR 的核心创新是把 DETR 类检测器改成「流式」：每帧不再独立做检测，而是带一份「上一帧的 object query 记忆」进入这一帧。head.py 把这件事拆成三步纯函数：

步骤方法职责
(a) 运动补偿_compute_updated_memory_pre（head.py:167-221）用 ego_pose_inv 把上一帧记忆里的 reference point 和 egopose 变换到当前坐标系，旧记忆在空间和时间上对齐到「现在」
(b) 时序对齐_temporal_alignment（head.py:223-316）把当前帧 query + 前 N 个 propagated 旧 query 拼成 tgt；剩余旧记忆作为 temporal_memory；用 ego_pose_pe (MLN) 和时间 embedding 调制
(c) 入队_compute_updated_memory_post（head.py:318-371）当前帧 decoder 最后一层输出 detach 后 FIFO 入队，截到 memory_len，并记录新 reference point/egopose/timestamp 供下一帧用

整条记忆链包含 6 个张量（embedding / reference_point / timestamp / egopose / velo / valid_flag），由调用方显式传入传出。decoder 的 self-attention 让当前 query 同时看到「自己 + 旧 query + 旧记忆」，cross-attention 看图像特征。

src/models/streampetr/decoder.py:252-272：temp_key = cat([query, temp_memory]) —— self-attn 的 K/V 是「当前 query + 历史记忆」拼接。
src/models/streampetr/utils.py:250-274：transform_reference_points 用 egopose 矩阵把 reference point 在帧间坐标变换。
StreamPETR 通过把上一帧的 query 当作这一帧的「先验」，让网络隐式学到速度 / 遮挡恢复 / ID 一致性，且无需显式做数据关联（DETR 的匈牙利匹配天然处理）。运动补偿（ego_pose_inv 变换）保证记忆在自车移动后仍指向同一物理点 —— 这是 cfg 里 ego_pose/ego_pose_inv/timestamp_interval 必须作为输入的原因（forward:1001-1006）。
如果不做时序融合（纯单帧 PETR，no_img_transformer=True 分支，forward:999），被遮挡车辆每帧都得重新检测、速度估计噪声极大，规划端会看到「跳变」的他车轨迹，cut-in/变道这类需要历史信息的场景会大面积失败 —— 这正是为什么 cfg 里 mem_len 设得很大（1024 = max_agents×8）。如果不做运动补偿，自车一转弯旧记忆就指向错误的世界点，时序融合反而有害。
三个对 PM 最关键的概念：
(1) memory_len 必须是 num_query 的整数倍（head.py:59 assert），因为记忆按「每帧 N 个 query」成块管理，propagated 取前 N 个当 query、剩下的当 temporal_memory；
(2) detach() 是关键 —— _compute_updated_memory_post 里 outs_dec[-1][:, :self.num_query].detach()，这意味着记忆只在「当前帧」参与梯度，不会让反向传播沿时间无限回溯（否则显存爆炸，类似 truncated BPTT）；
(3) clip_length=8 是另一个工程阀门：每 8 帧强制清零记忆，防止长序列漂移。

2.4 感知 → 预测 → 规划如何「打通」：共享 transformer backbone

很多人理解的 E2E 是「三个 head 共用一个 backbone」，但 JoyDriver 更激进：三者共用同一份 token 序列和注意力。具体地，进 StreamPETR transformer 之前，AgentEncoder 把每个 agent 的历史向量压成 query embedding（joydriver_v0.py:69-171），同时建两个 encoder：self.agent_encoder 编他车、self.ego_encoder 编自车，然后 cat 成 [ego; agents] 序列，第 0 个永远是自车 —— 这是后面所有「只取 ego token」操作的隐含约定。

src/models/joydriver_v0.py:505-514：JoyDriverV0 建两个 AgentEncoder；
:710-753 _encode_agent_ego_features：cat([ego_feature, agent_feature], dim=1)，ego 在 index 0。

之后：

  • 感知：这份 query 在 StreamPETR transformer 里通过 cross-attn 看图像特征，从像素里「读出」每个 agent 的 3D 状态 —— 但不显式出框，状态融在 token 里。
  • 预测：每个 agent token 通过 self-attn 互相看（包括历史记忆），隐式建模交互。
  • 规划：TrajectoryHead 从 ego token（index 0）解出 ego 的未来轨迹；6 层 agent_self_attns 让 ego 看到所有他车再决策。
用 agent 历史向量作为 query 初始化，相当于给 transformer 一个强先验 ——「请围绕这些已知 agent 去融合图像信息」，而不是从零学一组匿名 query。如果 query 用纯可学习 anchor（原版 StreamPETR），规划 head 无法区分「这是 ego 还是他车」，也无法利用速度/朝向历史，轨迹预测精度会大幅下降。
ego 放 index 0 这个约定如果被破坏，后面 trajectory_head 输出的 ego_traj_pred 就会取错 token，整个规划输出错位 —— 这是代码里最脆弱的隐式约定之一。

2.5 多模态轨迹输出：为什么是 6 条而不是 1 条

TrajectoryHead 输出每个 mode、每个 coarse_step 的 (加速度 acc, 偏航角速度 omega)，cls_head 用 softmax 输出 n_modal=6 个模式的概率。多模态对应「未来本质上是不确定的」这一建模假设 —— 路口可左转可直行，模型必须输出分布而非单点。下游 planner 从 6 条候选里选最优或做加权。

对 PM 转 PM/架构师最关键的洞察：head 的设计直接决定「模型误差能不能被 loss 解释」。acc/omega 积分意味着 loss 是定义在「控制量」上的，长时程位置误差会被 cumsum 放大，所以训练时往往要对早期步加大权重。coarse_steps = n_step//5 是降参技巧 —— 只预测 12 个粗步再插值到 60 步，参数量降 5 倍且防过拟合。autocast(enabled=False)（line 231）说明积分这步要 fp32 做数值稳定，AMP 训练时这是常见坑点。

CH 03模型架构：从像素到轨迹的「端」到「端」

本章逐层拆解架构。读者建立的总图：像素 → RegNet 骨干 → CPFPN 颈 → 3D 位置编码 → StreamPETR 时序 transformer → map 交叉注意力 + agent 自注意力 → TrajectoryHead 积分出轨迹 → RefineHead 精修。最后讲 ONNX 部署形态（有状态训练 / 无状态部署）。

3.1 骨干（RegNet）+ 颈（CPFPN）：把像素压成 256 维多尺度特征

图像进入模型的第一件事是被 RegNet 残差骨干逐级降采样、加宽通道：3×3 stem 卷积 stride=2 起步，再走 4 个 stage（layer1-4），每个 stage 由若干 Bottleneck（1×1→3×3→1×1，带残差）组成，stage 之间 stride=2，最终在 out_indices=[2,3] 取出两个分辨率最低、语义最抽象的特征图（regnetx_800mf 是 288 通道和 672 通道）。

CPFPN（颈）再把这两张图通过 1×1 lateral conv 投到统一 256 通道、用 top-down 把高层特征上采样加到低层（让低层也带高层语义），最后只在 level 0 过一个 3×3 fpn_conv，输出 2 张统一通道、不同分辨率的特征金字塔给下游。这两步合起来就是「骨干+颈」：骨干负责提语义，颈负责统一通道/尺度。

src/models/backbones/regnet.py:271-282 RegNet.forward：stem→逐 stage res_layer→按 out_indices 收集输出；
:197-206 _make_stem_layer：3×3 stride=2 stem，第一次降采样；
:91-100 arch_settings：regnetx_800mf 的 w0/wa/wm/group_w/depth，决定每 stage 宽度；
:22-69 Bottleneck：1×1→3×3→1×1 + 残差；
src/models/necks/cp_fpn.py:143-170 CPFPN.forward：laterals=1×1 conv → top-down 上采样相加 → level 0 过 3×3 fpn_conv；
src/models/streampetr/img_encoder.py:40-46 ImgEncoder.extract_img_feat：先 backbone 再 neck，img_feats[self.position_level] 才是给 transformer 用的。
图像原始像素 512×1024×3 太大、太冗余、且高度相关，直接喂 transformer 会把注意力矩阵爆掉且学不到抽象。骨干把空间分辨率压低、把通道语义抬高，颈把多尺度信息统一到一个 transformer 能消化的 256 维序列。反事实：如果跳过骨干直接用原图，token 数会是 H×W≈50 万，注意力 O(N²) 直接内存溢出；如果跳过颈只用单尺度，小目标（远车）和大目标（近车）的信息无法在同通道下被 query 共享，远车召回会塌。
为什么 backbone 输出 [2,3] 而不是 [0,1,2,3]？因为深层（2,3）语义强、分辨率小，token 数少、注意力便宜；浅层（0,1）细节多但语义弱且贵。CPFPN 只取 2 层 + position_level=0（即选第 0 个输出，对应 backbone 的 layer3）就是「够用且便宜」的工程取舍。regnetx_800mf 这个选型本身是精度/速度折中（约 0.8G FLOPs），对车端实时性是硬约束。
PM 视角：backbone 选型直接决定车端推理时延和远距检测召回，是 BOM/算力预算的核心变量。

3.2 3D 位置编码 PositionEmbedding3D：2D 图像特征如何长出「深度」

PETR 家族的关键 trick：transformer 的 cross-attention 本身不知道哪个像素对应 3D 空间的哪个点，必须在 key 上注入「这个像素在 3D 世界的位置」信息。PositionEmbedding3D 在每个图像特征像素上构造一束「假设深度」（LID 采样的 64 个深度 bin），用相机内参与 img2lidar 矩阵把 (像素 u, 像素 v, 深度 d) 投到自车坐标系 (x,y,z)，归一化后过 inverse_sigmoid + 一个 MLP，得到该像素的 3D 位置编码。同时把内参 fx/fy 和 3D 坐标拼成 cone（视锥参数），后续给 spatial_alignment（MLN）调制图像特征用。这样每个图像 token 都同时携带「我长什么样（CNN 特征）」和「我在 3D 世界哪个位置（PE）」两条信息。

src/models/streampetr/position_embedding_3d.py:19-29 LID 深度采样：bin_size 按二次函数分布，近处密、远处疏；
:53-63 coords3d = img2lidars @ coords，把 (u,v,d) 网格投到 3D；
:65-67 按 position_range 归一化到 [0,1]；
:73-76 inverse_sigmoid 后过 position_encoder MLP，并拼出 cone 给 MLN 调制；
:31-35 position_encoder：Linear(position_dim=192) → 4*256 → 256。
单目图像本身丢了一维（深度），网络无法从纯 2D 卷积特征里恢复「这辆车离我多远」。PETR 的解法是用一组假设深度把每个像素反投影成一束 3D 候选点，让 transformer 的 query（带 3D 位置）通过注意力去「挑」正确的深度 —— 等价于把深度估计隐式写进了注意力权重。
如果不注入 3D PE（纯 2D DETR），cross-attention 只能学到「图像里有车」，无法学到「车在 3D 哪里」，3D 检测/轨迹预测都会失败。这是 PETR 比 2D DETR 多出来的核心一环，也是「图像→3D 检测」这步因果链的物理基础。
LID（Linear Increasing Discretization）采样为什么是二次函数 bin_size = depth_start + bin_size * index * index_1？因为远处深度不确定性大、需要更疏的 bin，否则 64 个 bin 全堆在近处浪费容量 —— 等价于「按距离做对数式分桶」。cone 这个名字来自 cone-of-vision（视锥），它把「相机的焦距 + 像素的 3D 投影」编码进特征调制，让同一张图在不同相机参数下能被对齐处理。

3.3 感知 query 从哪来：AgentEncoder 把历史向量序列压成 query embedding

进 StreamPETR transformer 之前，模型需要一份「这一帧有哪些 agent、各自历史运动如何」的初始 query。AgentEncoder 干这件事：输入是每个 agent 过去 T 步的向量特征 (B,N,T,Fin)（含位置、速度、朝向、类别等），先线性投到 hidden_dim，加上「正弦 PE + 可学习时间 PE」标注时间步，过 2 层 1D 卷积（kernel=3，捕捉局部时序模式）+ 残差，再按 mask 做 masked mean-pool 压成单步，最后过 MLP head 得到 (B,N,C) 的 agent embedding。

src/models/joydriver_v0.py:69-171 AgentEncoder：proj → time PE → 1D conv×2 → masked mean pool → MLP head；
:505-514 JoyDriverV0 建两个 AgentEncoder：self.agent_encoder（他车）+ self.ego_encoder（自车，obs_len 可不同）。
为什么用 1D conv 而不是 LSTM/Transformer 编时序？conv 便宜、可并行、对短序列（obs_len=50）够用；而且后面还有 StreamPETR 的全局 self-attn 做二次融合，conv 只负责提「局部运动斜率」即可。mask_ego_history（:731-735）这个 trick 值得记：它强迫模型不要只依赖「自车历史位置」外推（容易在遮挡时崩），而要学会从图像找自车位置 —— 这是典型的数据增广防捷径学习，PM 视角看就是「防止模型学到伪相关」。

读者常困惑：为什么感知 transformer 用 (N,B,C) 顺序、规划 transformer 用 (B,N,C)？这是历史包袱 —— PETR 脱胎于 mmdet 的 nn.MultiheadAttention（默认 seq-first），nanoGPT 风格用 batch-first。decoder.py 里大量 transpose 就是在两种格式间倒腾。flash_attn（attention.py:52-129）是另一层优化 —— 把 attention 的 O(N²) 显存压成 O(N)，训练大 batch 时必开。

3.5 轨迹/规划 head：从加速度积分到多模态未来轨迹

TrajectoryHead 不直接回归位置，而是回归「控制量」：traj_head 输出每个 mode、每个 coarse_step 的 (加速度 acc, 偏航角速度 omega)，线性插值上采样到 n_step，然后做运动学积分：

speed = cumsum(acc) * dt + init_speed angle = cumsum(omega) * dt heading = (cos(angle), sin(angle)) vel = speed * heading pos = cumsum(vel) * dt # 这就是 ego/agents 的未来 60 步轨迹

同时 cls_head 用 softmax 输出 n_modal 个模式的概率。这是「自行车模型」（bicycle model）的可微实现：acc/omega 是受约束的物理量（可 clamp 到 acc_min/acc_max），积分保证轨迹运动学合法（不会出现侧滑、瞬移）。

src/models/joydriver_v0.py:216-229 traj_head 回归 acc/omega，cls_head softmax 出 mode 概率；
:249-273 forward：积分链 acc→speed→angle→heading→vel→pos，典型 bicycle model；
:255-258 acc/omega 可 clamp 到物理可行区间；
:275-283 _interpolate_steps：coarse_step 线性插值到 n_step，降维减参；
:174-175 docstring 明确："Predict per-step acc/yaw-rate, integrate to vel/pos"。
直接回归 xy 位置有两个病 —— (a) 不满足运动学约束（车不能横向平移），网络可能学到非法轨迹；(b) 误差随时间累积放大，长程预测漂移。回归 acc/omega 再积分，等价于把「自行车模型」作为硬先验嵌入网络，输出的轨迹天然可执行，且误差结构更合理（速度对了，位置就跟得上）。多模态则是为规划服务的：planner 可以从 6 条候选里选最优/做加权。
如果直接回归位置，下游控制器（转向/油门）无法直接执行，还得反解 acc/omega，引入数值误差；如果单模态输出，遇到「路口可左转可直行」这种本质多解场景，模型会被迫取平均，输出一条直穿绿化带的「平均轨迹」。

ONNX 导出陷阱（必读）：三个对 PM 最关键的部署概念：
(1) clip_length=8 + force_reset 是「工程化时序」 —— 训练时按 8 帧一个片段 BPTT，部署时也每 8 帧清零，保证两边状态机一致；如果不一致会出现「训练精度高、上车就崩」的诡异 bug；
(2) ONNXModelAdapter._to_numpy（line 130-149）把 float64→float32、int64→int32，是因为 ONNX/TensorRT 对 dtype 极敏感，dataloader 默认 dtype 经常和导出时不符 —— 这是典型的「模型上线第一类 bug」；
(3) JoyDriverV0.forward 里特意把 NHWC→NCHW 的 permute 放进 forward 而不是 pre_process（:987-992），就是为了让 ONNX 能 trace 这一步 —— 否则 trace 出来的图会缺这个算子，车端结果会错。这种「为部署服务的代码结构」是端到端工程的关键。

4.2 DDP（DistributedDataParallel）8 卡并行：梯度怎么同步

训练一个端到端模型要 8 卡跑数百万 iter，单机跑不完。DDP（DistributedDataParallel）是把模型在 8 张卡上各放一份、各跑一个 batch、反向传播时用 NCCL 同步梯度的并行方案。具体流程：

flowchart TB
  M["模型 (8 份副本, 各 GPU 一份)"] --> G1["GPU0: batch0 → forward → loss"]
  M --> G2["GPU1: batch1 → forward → loss"]
  M --> G8["GPU7: batch7 → forward → loss"]
  G1 --> NCCL["NCCL all-reduce
(经 InfiniBand)"]
  G2 --> NCCL
  G8 --> NCCL
  NCCL --> AVG["梯度平均 (÷8)"]
  AVG --> OPT["各卡 optimizer.step()
(同步更新)"]
  OPT --> NEXT["下一 iter, 所有卡权重一致"]

DDP 在 train/run.py:27 import、:324 wrap。每个 batch：每张卡前向算 loss、反向算梯度，NCCL 经 InfiniBand 同步梯度平均，然后各卡独立 optimizer.step()（因为梯度相同，权重更新也相同）。

RDMA / NCCL / InfiniBand 多卡训练（重点）：
InfiniBand 是一种专用高速网络（带宽 100-400 Gbps，延迟 μs 级），比普通以太网快 1-2 个数量级。det.yaml:7-24 挂载了 uverbs0-5 设备 —— 这就是 InfiniBand 的用户态访问设备。
NCCL（NVIDIA Collective Communications Library）是 NVIDIA 写的集合通信库，专门优化 GPU 间通信，自动用 RDMA（Remote Direct Memory Access，远程直接内存访问，CPU 不参与）走 InfiniBand。
为什么需要 RDMA-NCCL-InfiniBand：训练时 8 卡要 all-reduce 梯度（每卡 ~1GB 梯度），如果走普通以太网 + TCP，每 iter 通信要几百 ms，训练吞吐崩塌；走 RDMA，CPU 不参与拷贝，延迟降到 μs 级。这就是为什么 det.yaml 要显式挂载 uverbs 设备 —— 没有它 NCCL 退化成 TCP，训练慢 10 倍。

4.3 AMP + GradScaler：混合精度训练的数值稳定

run.py 用 AMP（Automatic Mixed Precision）训练：use_amp=True 时，前向用 fp16（省显存、快），反向算梯度时 GradScaler 动态放大 loss 防止小梯度下溢。train_one_epoch（run.py:681 起）的核心循环大致是：

# 伪代码 (run.py:681 起 train_one_epoch) scaler = GradScaler() for batch in dataloader: optimizer.zero_grad() with autocast(enabled=use_amp): out = model.forward(batch) loss = compute_loss(out, batch) scaler.scale(loss).backward() # 放大梯度 scaler.unscale_(optimizer) clip_grad_norm_(...) # 梯度裁剪 scaler.step(optimizer) # 缩放回去再 step scaler.update()
AMP 的关键坑点：TrajectoryHead 的积分步骤必须 autocast(enabled=False)（joydriver_v0.py:231），即 fp32 做数值稳定。因为 cumsum 在 fp16 下误差会被放大，6 秒位置预测可能漂几米。这是为什么模型代码里要在关键算子前显式禁用 autocast。
异常 loss skip：训练中偶尔会出现 NaN/Inf loss（数据异常 / 梯度爆炸），run.py 实现了 skip 逻辑 —— 检测到异常 loss 直接 optimizer.zero_grad() 跳过这 iter，不更新权重。这是百万 iter 训练能跑完的关键防线。

4.4 loss 设计：轨迹回归 + 转向角约束 + 多模态

loss_cfg（cfg:295-315）的全是轨迹回归 loss + 转向角约束，跟检测完全不同。核心组件：

  • 轨迹 L2 loss：预测轨迹 vs GT 轨迹的位置误差（每个未来步加权，早期步权重大）
  • 速度 / 加速度 loss：约束控制量预测准确
  • 转向角约束（ego_steer_limit_deg=35）：惩罚预测轨迹的转向角超出物理可行范围
  • 多模态 loss：从 6 条候选轨迹里挑与 GT 最近的那条算 loss（winner-takes-all），同时 cls_head 学把最高概率分给最准的那条
  • 碰撞 loss（可选）：约束 ego 轨迹不与他车 GT 轨迹相交
acc/omega 积分意味着 loss 是定义在「控制量」上的，长时程位置误差会被 cumsum 放大，所以训练时往往要对早期步加大权重。ego_steer_limit_deg=35 这个值对应车辆物理极限（方向盘打死约 35°），超出说明模型预测了物理上不可能的轨迹，要惩罚。

4.5 max_restarts + checkpoint：训练失败怎么恢复

百万 iter 训练跨数天，中途必然遇到 GPU 故障 / 网络抖动 / 节点重启。Determined 提供 max_restarts（det.yaml）机制：trial 异常退出时自动从最近 checkpoint 重启。train/run.py 的 checkpoint 保存逻辑：每隔 N iter 存一次（含模型权重 + optimizer 状态 + lr scheduler 状态 + 当前 iter），重启时从最新 checkpoint 恢复，训练无缝续接。

checkpoint 要存什么？不只是模型权重 state_dict，还要存 optimizer.state_dict()（Adam 的一阶/二阶动量）、lr_scheduler.state_dict()（当前 lr）、iter_count、rng_state（随机数状态，保证数据增广可复现）。漏存任何一个，重启后训练会「跳跃」（lr 突变、动量丢失、增广不可复现），可能导致 loss 突然爆炸。
load_state_dict 的兼容性坑：joydriver_v0.py:570-639 那堆兼容性代码（剥 _orig_mod. 前缀、加 core. 前缀、删旧 map_encoder key）就是为这个 —— 模型架构改过几次，旧 checkpoint 的 key 名和新代码对不上，要手动映射。这是模型迭代管理的真实成本，PM 要理解：改架构 = 老 checkpoint 失效 = 要么写兼容代码、要么从头训。

CH 05数据管线与挖掘闭环：manifest / 采样 / 挖掘回链

本章强调三条因果主线：(1) manifest = 文件名清单（非数据）；(2) target_area 是模型看的导航指令；(3) 数据挖掘是给文件名贴标签后再剪枝/召回清单。这是数据闭环 PM 最能直接对号入座的章节。

5.1 数据形态：一个 .zst 就是一帧，manifest 只存文件名不存数据

训练消费的最小单元是一个 zst 压缩的 pickle 帧，文件名形如 {seq_name}_{timestamp_ns}.zst，落在 {seq_dir}/e2e_data/ 下。manifest 不是数据本身，而是一个 list[str]，每条就是一个 zst 文件名（相对路径即文件名）。build_manifest 扫描目录把所有 zst basename 收集进 pickle，这样训练启动时只需加载一个轻量清单，按需再去磁盘解压具体帧。

src/dataset/build_manifest.py:15-52 _filter_zst / scan_zsts_fast：只收 .zst basename；check_img 用 img_ts_set 过滤缺图样本；
:55-92 _process_seq_dir / build_manifest：扫 data_root/<seq_dir>/e2e_data/*.zst，pickle.dump(entries) 存的是文件名清单；
src/dataset/dataset.py:1148-1166 load_data：zlib 解出文件名后拼 data_root/<clip_name>/e2e_data/<file>.zst，zstd 流式解压读 pickle。
把「清单」和「数据」分离是数据闭环的根基：清单小（百 MB 级）可频繁增删改、做挖掘筛选、断点续训，而数据大（TB 级）始终只读。反事实：若 manifest 把整帧内联进 pkl，每次挖掘筛选都要重写 TB 数据，闭环迭代周期会从小时级退化到天级，长尾场景根本迭代不动。
PM 闭环思维里「数据」常被当成一个整体概念；这里要补的点：训练侧的「数据加载」其实是两层 —— 清单层（决定喂哪些帧、喂的顺序）+ 物理帧层（决定每帧长什么样）。挖掘改的是清单层，preprocess 改的是物理帧层，两者解耦。

5.2 帧的内部结构：TARGET_AREA / ROUTING / REFER_PATH 是「导航三件套」

每一帧 pickle 解开后是按 header 排列的字典序列：SEQ_ID（场景唯一键）、EGO_TRAJ（自车历史 + 未来轨迹）、AGENT_TRAJS（他车轨迹）、REFER_PATH（参考线）、TARGET_AREA（240×120 二值栅格，模型看的「可行驶目标区域」）、ROUTING（导航折线，回退用）、CALIB_INFO（lidar2cam 等标定）、IMAGE_INFO（前视相机图像路径 + 内外参）、RMP/RMP_V2（栅格化地图）。

TARGET_AREA 和 ROUTING 不是原始传感器，是 preprocess 阶段用地图 + 参考线算出来的「导航指令栅格」，模型把它当 BEV 图看。

src/preprocess/steps/feature_generator.py:402-404 headers 序列：["SEQ_ID","CITY_NAME","EGO_TRAJ","REFER_PATH","AGENT_TRAJS","STATIC_MAP","BEV_MAP","CALIB_INFO","IMAGE_INFO","TARGET_POINT","OCC",rmp_header,"TARGET_AREA","ROUTING","EGO_TRAJ_PRED"]；
:370-392 target_area 由 build_offboard / build_onboard_target_area_result 生成，240×120 uint8；
src/dataset/dataset.py:1309-1320 __getitem__ 读 TARGET_AREA 和 ROUTING(target_area_centerline)。
TARGET_AREA 是端到端模型实际「读懂导航」的载体：它把高精地图的车道面 + 参考线 + 路口识别压缩成一张「车该往哪片区域开」的二值图。反事实：若没有 TARGET_AREA，模型只能从 REFER_PATH 这种连续坐标学导航，跨城市/路口泛化差，且无法表达「这一片都可走」的柔性约束 —— 这正是 StreamPETR 类端到端模型要 BEV 表征的原因。
对 ML 实现生疏的读者：可以把 TARGET_AREA 理解成「给模型看的导航缩略图」—— 它不是语义分割 GT，而是 preprocess 用地图拓扑算出来的「驾驶意图栅格」。240×120 = 0.5m 分辨率对应 x∈[-40, 80]m、y∈[-30, 30]m 的车前区域。

5.3 采样：clip_len 把连续帧绑成时序片段，DistClipSampler 保证同 batch 同 clip

_split_clip（dataset.py:969-1118）把同一序列里时间戳连续（相邻间隔 < 0.15s）的帧切成 clip_len 长的片段。DistClipSampler（sampler.py:48-75）在分布式训练里按 rank 分配 clip，每个 batch 取 batch_size 个 clip，按 clip 内帧序逐帧 yield，保证一个 batch 内同一时刻所有 rank 拿到的是同一批 clip 的连续帧 —— 这是时序模型训练的硬约束。

src/dataset/sampler.py:48-75 __iter__：先 randperm clips，再 indices[rank::world] 分片，再按 f_idx→clip_idx 双重循环 yield clip_idx*clip_len + f_idx。
时序端到端模型（如 StreamPETR）需要连续帧来维护时序 memory，clip 是最小可训练单元。反事实：若用普通随机采样打乱时序，模型每帧都从零初始化 memory，相当于退化成单帧模型，时序增益归零；若 batch 内 clip 不对齐，多卡训练时梯度聚合会混入不同 clip 的 memory 状态，训练发散。
数据闭环 PM 看到「采样」常想到「分层抽样/场景配比」；但这里 sampler 解决的是「工程对齐」问题（多卡时序一致），而「场景配比」是 manifest 层用挖掘脚本做的（见后文 clean_*/recall_*）。两者在管线里位置不同：sampler 在训练运行时，manifest 配比在数据准备时。

5.4 增广：BEV 旋转 + 图像色彩抖动，两条独立通路

增广分两路：

  1. RandomRotationAugmentor（augmentations.py:21-108）对 BEV map（target_area_centerline）和 agent/ego 轨迹同步绕 ego 原点随机旋转 —— 必须同步否则轨迹和地图错位。
  2. ImageAugmentor（img_augmentations.py:8-50）对前视图像做 brightness/contrast/HSV/Gamma/Blur/Noise 六类像素级抖动，全局概率 0.5，多视角时 consistent_view=True 保证同帧多相机用同一组参数。
旋转增广解决路口转弯数据不平衡（直行多、急弯少）；色彩抖动解决光照/相机差异泛化。但 BEV 旋转必须同步轨迹，否则等于给模型喂错标签 —— 这是「增广正确性」比「增广丰富度」更重要的典型例子。

预处理是数据闭环的「生产侧」：每条新采集 record 走完管线变成可训练 zst，状态回调到 data-pipeline.jd.com 触发下游。反事实：没有标准化的 step 链，每个工程师各写各的预处理，会导致同一场景不同版本特征不一致，模型回归无法定位是数据变了还是模型变了 —— 这是闭环里「特征版本一致性」的命门。

5.6 TARGET_AREA 生成算法：参考线找目标点 → 沿车道面回溯 → 拓扑连通出可行驶走廊

build_target_area_from_rmp_and_refer 的因果链：

  1. 从 REFER_PATH 取第 target_point_index_m=80m 处的点作为目标点；
  2. 从目标点沿参考线向后回溯 refer_range_m=80m 得到 backward_path；
  3. 在 RMP 地图上把 backward_path 光栅化成 corridor，与 lane_mask / drivable_mask 求交，用连通域分析挑出包含目标点的车道连通块；
  4. 若连通块不够长，用 bridge 在车道间断处补线（connect_lane_path_with_bridge）；
  5. 叠加 intersection_mask（路口斑马线连通域）处理路口放宽。

最终产出 240×120 的 target_area + centerline + boundary。

src/preprocess/target_area/offboard_core.py:908-998 build_target_area / build_target_area_from_rmp_and_refer：取 80m 目标点，调 generate_lane_target_masks；
:737-868 generate_lane_target_masks：连通域 pick_best_component + corridor 光栅化 + intersection_mask 叠加；
:546-636 connect_lane_path_with_bridge：Dijkstra + bridge 在车道间断处补连。
这一步是把「人类导航意图（参考线）」翻译成「模型能消化的空间分布（栅格）」。反事实：若只给模型一个目标点坐标，模型无法表达「这条车道整个都能走」的柔性，会在车道边界处抖动；TARGET_AREA 把「一片连续可走区域」显式画出，模型轨迹预测更稳。连通域 + bridge 处理是为了应对地图车道面断裂（如遮挡、地图缺漏），保证 target_area 连续不破。
对 ML 不熟的读者：这一段全是经典 CV 几何/形态学操作（dilate/erode/connectedComponents/floodFill/convexHull/Dijkstra），不是神经网络。它是「数据工程」而非「模型」，理解这点能帮 PM 划清「模型问题 vs 数据问题」的边界 —— 轨迹在路口偏，先查 target_area 的 intersection_mask 算对没，而不是先调模型。

5.7 数据挖掘本质：给 zst 文件名贴场景标签，产出 allinfo 清单供剪枝

5.10 内存优化：MMapSamples 让千万级清单零内存常驻

manifest 膨胀到千万级帧时，把文件名清单全加载进内存（每帧约 100B）会占 GB 级 RAM。create_mmap.py 把所有 zlib 压缩后的文件名拼成一个 filenames.bin，再用 offsets.npy 记录每帧起止偏移，运行时用 mmap 把 bin 映射到虚拟地址，按需 OS 调页 —— 清单本身零 RAM 占用，访问时只读需要的 4KB 页。配套 clip_info_{clip_len}.npy 预算好 clip 切分，避免每次启动重算 _split_clip（千万帧要十几分钟）。

CH 06评测 + ONNX 导出 + onboard 部署

本章从「训练态模型」走到「可上车推理」，每一步都在解决一个「对齐」问题：训练态 ↔ 部署态对齐、PyTorch ↔ ONNX 输出对齐、离线 ↔ 车端 tensor 对齐。理解这一章就理解了「为什么模型上线不是调个 API」。

6.1 评测的两层结构：训练内 ADE/FDE vs. 离线闭环 benchmark

JoyDriver 的「评测」不是一个东西，而是两套互补的指标：

ADE/FDE 是「数学上贴近」，benchmark 是「行为上贴近」。只看 ADE 会被骗：一个 ADE 很低的模型可能在 cutin 场景总是急刹（舒适度差）或总是偏左（压线）。反事实：如果砍掉 benchmark 层只留 ADE，你会迭代出一个「指标好看但不敢上车」的模型；如果砍掉 ADE 只留 benchmark，每个 epoch 都要等几小时离线算，迭代速度崩塌。两层缺一不可。

6.2 多模态轨迹的评测：minADE_k / minFDE_k 与概率排序

JoyDriver 的预测头输出不是一条轨迹而是 M 条候选（多模态，ego 默认 6 条），每条带一个概率。评测时要先按概率从高到低排序，再算两个版本的指标：

  • minADE_1 / minFDE_1：「概率最高的那条」和真值的误差 —— 反映「模型最信的那条有多准」（决策质量）
  • minADE_k / minFDE_k：「K 条里挑最贴近真值的那条的误差」—— 反映「模型的可能性空间里有没有覆盖真值」（覆盖率）
src/eval/evaluator.py:73-100 _prob_ordered_metrics：order = np.argsort(-probs) 按概率降序，top1 = top[0] 算 ade1/fde1，top_k = top[:k] 取 min 得 adek/fdek。
多模态是端到端预测的核心设计 —— 未来本就不确定（车可能左转也可能直行），模型必须输出分布而非单点。minADE_k 衡量「覆盖率」，minADE_1 衡量「决策质量」。反事实：如果只看 minADE_k，模型可以输出 6 条覆盖所有可能的「撒胡椒面」轨迹拿低分，但下游 planner 选哪条？所以必须同时盯 minADE_1。这也是为什么 run.py:83 把 rank_metric 默认设成 brier_fde_k（带概率惩罚的 FDE，进一步逼模型把概率分给最准的那条）。

6.3 评测的有效样本筛选：为什么不能对所有 agent 平均

评测前要先过滤「有效 agent」。_valid_agent_indices 要求：最后一帧未来真值有效（has_last_future）、非 padding、agent_weight > 0。只有同时满足的 (batch_idx, agent_idx) 对才进入 ADE/FDE 计算。原因是数据里有大量 padding 出来的「假车」（max_agents=128 但实际场景可能只有 5 辆车）。

如果不做这个过滤，一个全 padding 的 batch 会让 ADE 看起来极低，模型会「学会」少预测真车多预测 padding 来刷分，整个训练目标被污染。这是数据闭环里「指标定义错 → 模型学错」的经典案例。

6.4 训练态模型 vs. 部署态模型：stateful wrapper 与 stateless core 的分叉

同一个模型 JoyDriverV0 有两种「跑法」：

形态调用状态用途
训练态forward(batch)有状态：模型自己持有 _temporal_state（6 个 memory 张量），每个 batch 后 update_temporal_state(out) 写回（detach().clone()）训练 / PyTorch 验证
部署态forward_with_core(batch, prev_memory_*)无状态：6 个 memory 张量显式变成输入和输出ONNX/TensorRT 导出
src/models/joydriver_v0.py:685-708 update_temporal_state：训练态从 out 取 _temporal_new_memory_* 写回 self._temporal_state；
:1144-1205 forward_with_core：把 prev_memory_* 作为入参、new memory 作为返回值的一部分，专给 ONNX/TensorRT 用。
ONNX/TensorRT 是「一次推理一个确定输入 → 一个确定输出」的计算图，图里不能有跨调用的 python 成员变量。所以任何跨帧状态都必须拍扁成图的输入输出。反事实：如果硬要用 stateful wrapper 导出（代码保留了 --export_stateful 选项），ONNX 图里会固化导出那一刻的 memory，每一帧推理都用同一份初始 memory，相当于「失忆」 —— 时序 transformer 直接退化成单帧模型，精度暴跌。这就是注释里反复警告 stateful "may not be suitable for all deployment scenarios" 的原因。
这是本视角最核心、也最反直觉的点。PM 容易把「模型」当成一个静态对象，但带时序的 transformer 本质是「把历史压缩进 memory 的循环系统」。训练时这个循环由 python 对象托管，部署时必须由 C++ 宿主托管 —— 同一份权重，两种「活法」。理解了这个，就理解了为什么导出 ONNX 不是「调个 API」而是「重新设计接口契约」。

6.5 ONNX 导出工程：dummy inputs、opset、layout 转换、常量折叠

导出的真实流程：构造一份 dummy_inputs（build_dummy_inputs 里 map_feature=zeros[1,1,240,120]、agent_feature=zeros[1,127,9,20]、img=zeros[1,540,960,3] 等，shape 来自 cfg），包进 JoyDriverCoreOnnxWrapper，调 torch.onnx.export(opset_version=20, do_constant_folding=True)。两个工程细节：

  1. img 输入是 NHWC，在 forward 里 permute(0,3,1,2) 转 NCHW。这个 permute故意写在 forward 内部而不是 pre_process，目的是让 ONNX trace 能记录这个算子（C++ 端喂 NHWC，图内自己转）；
  2. dummy_inputs 的具体数值（全 0/全 1）只影响 trace 的 shape 推导，不影响权重。
scripts/export_joydriver_v0_onnx.py:427-436 torch.onnx.export: opset_version=20, do_constant_folding=True, external_data=False；
:197-303 build_dummy_inputs：所有 shape 从 net_cfg/dataset_cfg 读，img 显式写成 NHWC（:249 torch.zeros(batch_size,540,960,3)）；
src/models/joydriver_v0.py:987-992 forward 内部做 img.permute(0,3,1,2)，注释明说 "done in forward() so ONNX can trace this operation"；
scripts/export_onnx.sh:4-7 生产实际调的是 export_joydriver_v0_onnx.py，不是 src/cli/export.py。
ONNX 导出的本质是「把动态 python 计算描成一张静态计算图」，dummy input 决定图的形状，opset 决定能用哪些算子（opset 20 才支持较新的 transformer 算子）。把 layout 转换放进图里，是为了让 C++ 端的图像 buffer（天然 NHWC，因为相机驱动吐的就是 NHWC）能直接喂进来，省一次宿主侧拷贝。反事实：如果 layout 转换放在 pre_process（python 侧），ONNX 图就假设输入是 NCHW，C++ 端必须先 permute 再喂，多一次拷贝且容易写错维度顺序 —— 这是经典的「训练用 NCHW、部署相机吐 NHWC」的坑。

6.6 ONNX 简化（onnxsim）的两副面孔：生产没用，但理解它有用

onnxsim 做的事是「常量折叠 + 冗余算子消除」：把图里能用 initializers 算出来的部分提前算掉，把 reshape/transpose 链合并。src/cli/export.py 里调了 simplify(args.onnx_path) 并 assert check，再把简化后的存成 _sim.onnx。但生产脚本 export_joydriver_v0_onnx.py 根本没调 onnxsim —— 它直接在 export 时开 do_constant_folding=True，已经做了大部分常量折叠。

onnxsim 在老链路（HiVT 那套，含 python list 输入、dynamic batch）里很有用，因为 torch.onnx 对 list 输入会生成一堆 Identity/SequenceAt 冗余节点，onnxsim 能清掉。但 JoyDriverV0 导出是固定 batch=1、纯 tensor 输入，图本来就比较干净。盲目套 onnxsim 反而可能触发 check=False（简化后数值不等），debug 成本高于收益。这是一条「别抄老脚本」的教训。
PM 转 architect 要建立的不是「onnxsim 是个好工具」，而是「每个工程动作都有适用条件」。

6.7 ONNX 验证：ONNXModelAdapter 怎么接进训练验证流水线

导出后要验证「ONNX 模型和 PyTorch 模型输出一致」。做法不是单独写个 diff 脚本，而是把 ONNX 包成 ONNXModelAdapter，伪装成 JoyDriverV0 的接口（pre_process / forward / post_process），直接塞进 run.py 的 val 流程跑同样的验证集，看指标是否对齐。关键设计：

  1. pre_process / post_process 直接复用 PyTorch 模型的方法（保证前处理完全一致）；
  2. forward 内部把 batch dict 拆成 ONNX 的 input dict、调 onnxruntime、再把输出拼回 dict；
  3. memory 状态由 adapter 自己托管（_init_memory / _reset_memory），在 clip 边界自动重置。

loader.py 在 use_onnx=True 时强制 val_batch_size=1、禁止多卡 DDP。

src/models/onnx_adapter.py:280-332 pre_process / post_process 直接 return self.pytorch_model.pre_process / post_process；
:291-321 forward：prepare_onnx_inputs → session.run → _convert_outputs，其中 _convert_outputs 把后 6 个输出存回 self.memory_state（:269-276）；

复用 val 流水线验证 = 零额外代码就能拿到「ONNX 模型在整个 val 集上的 ADE/FDE」，和 PyTorch 跑出来的直接比。这是「对齐」最硬的证据，比单样本数值 diff 强得多。反事实：如果只用几个 dummy 样本数值 diff，可能因为 dummy 样本刚好覆盖不到 memory 跨帧累积的差异，上车后才发现精度漂移 —— 而跑全 val 集会暴露任何系统性偏差。强制 batch=1 是因为 ONNX 导出时 batch 维被固化。
PM 要理解的关键因果：「验证」不是「功能验证」（能不能跑），而是「等价性验证」（ONNX 输出和 PyTorch 是否在统计上不可区分）。前者过不了上不了车，后者过不了上车会出事。ONNXModelAdapter 的精妙在于它让「等价性验证」复用了「功能验证」的全部基建。

6.8 训练态 memory 管理的细节陷阱：force_reset、clip_length、temporal_iter

训练态 memory 不是一直累积的，要在 clip 边界重置。重置信号有两个来源：

  1. full_seq_mode 时由数据侧的 clip_start 标志位显式给出（pre_process 里把 clip_start 转成 force_reset bool）；
  2. 非 full_seq 时用计数器 self._temporal_iter % temporal_clip_length == 0 自动判断。

_get_temporal_memory_inputs 收到 force_reset=True 就调 _init_temporal_state 把 6 个 memory 张量清零/置单位阵。注意 config 里 clip_len=1，意味着实际训练时每个 batch 都重置 memory（单帧训练），只有部署时序列推理才需要跨帧 memory 续接。

src/models/joydriver_v0.py:1113-1121 pre_process 里 force_reset 的两套来源：有 clip_start 用 clip_start.any()，没有则用 _temporal_iter % temporal_clip_length == 0；
:665-683 _get_temporal_memory_inputs：force_reset=True 时调 _init_temporal_state 清零；
configs/joydriver_v0_cfg.py:15 clip_len=1，:284 'clip_length': clip_len 传给 temporal_transformer；
src/models/onnx_adapter.py:303-308 ONNX 侧也复刻了这个逻辑：优先 force_reset，否则 batch_count % clip_length 重置。
如果重置逻辑写错（比如导出 ONNX 时 clip_length 配成 0 或忘记重置），ONNX 会在第一帧后永远带着第 0 帧的 memory 跑，时序 transformer 退化，且这种 bug 在单样本验证时看不出来（单样本 memory 影响小），只有长序列 val 才暴露。clip_len=1 这个配置点说明：训练用单帧（数据是打散的），部署用序列 —— 训练和部署的时序语义本就不同，重置逻辑必须在两条链路上都正确。
这是最容易被忽略、上车必爆的坑。PM 直觉上「训练准确 = 部署准确」，但时序模型在「训练打散单帧」和「部署连续序列」两种模式下，memory 的语义完全不同。force_reset 就是连接两种模式的「离合器」。

6.9 onboard 部署链路：从 ONNX 到 TensorRT engine，再到 tensor 录制回放

真正上车的是 TensorRT engine（不是 ONNX 本身 —— ONNX 只是中间格式，TensorRT 把它编译成针对具体 GPU 优化的引擎）。链路：ONNX → trtexec/编译 → .engine → C++ 推理服务消费。Joy Driver 仓库里 onboard 的对应物是 src/cli/tensor_recorder.py：它的 TensorRTEngine 类直接 load .engine 文件、用 context.execute_async_v3 + cuda stream 跑推理，模拟 C++ 车端的调用方式。

两个核心用途：

  1. cal_offboard_tensor：用 offboard 真值数据跑 PyTorch 模型，把 pre_process 输入和 post_process 输出都录成 JSON；
  2. replay_onboard_tensor：把车端 C++ 录的 pre_process tensor 喂进模型（PyTorch 或 TRT），输出 post_process tensor，用来 diff 车端和离线的中间 tensor 是否一致。
src/cli/tensor_recorder.py:23-83 TensorRTEngine：deserialize_cuda_engine、create_execution_context、set_tensor_address、execute_async_v3，车端 C++ 的 python 复刻；
:266-323 cal_offboard_tensor：net.pre_process(data) → 存 JSON；net(data_in) → net.post_process → 存 JSON；
:344-410 replay_onboard_tensor：load_preprocess_tensor 读车端录的 JSON，喂模型，存 post_process_onboard；
:195-240 replace_key 把 ONBOARD_* 前缀的键名（车端命名）映射成模型输入键名 —— 车端/离线键名对齐的桥。
车端 C++ pipeline 和离线 PyTorch pipeline 是两套独立实现，任何一处的预处理差异（图像归一化常数、坐标系约定、dtype、padding 顺序）都会让 ONNX 输入不一致，导致车端输出和离线对不上。tensor 录制回放是「端到端对齐」的唯一可靠手段：把两边的中间 tensor 都落盘，逐帧 diff。反事实：如果不做这个对齐，可能出现「离线 ADE 很好、上车就跑偏」的幽灵 bug，且无法定位 —— 因为你看不到车端到底喂了什么进模型。TensorRTEngine 类存在的意义就是「用 python 复刻车端推理路径」，让 diff 可执行。
PM 要建立的核心因果：「端到端模型上车」不是把 .onnx 扔给车端就完事，而是一条「预处理对齐 → 中间 tensor 对齐 → 输出对齐」的三段式验证链。tensor_recorder.py 就是这条链的工具化。replace_key 那段（ONBOARD_AGENT_FEATURE → agent_feature 等）揭示了车端和离线的键名都不一样 —— 细节多到必须用工具系统化对齐。

6.10 预测结果落盘与可视化调试

evaluator.save_pred=True 时，JoyDriverEvaluator.evaluate 会把每个 seq 的完整预测 + 真值 + record_info 序列化成 dict，经 _compress_numpy_to_float32（float64 → float32、保留 2 位小数）压缩，再 zstandard level=3 压缩成 .zst 落盘到 eval_res/。这些 .zst 同时是 benchmark.py 的输入（开闭环指标）和 visualize.py 的输入（画图调试）。落盘前有个关键变换 local_coordinate_transform：把模型输出的「局部坐标轨迹」经旋转矩阵转回全局坐标。

9.4 三个最深的设计决策（详细讲解）

决策一：为什么是「stateful 训练 / stateless 部署」的双形态，而不是统一一种

这是整个 JoyDriver 工程里最深、也最反直觉的设计。表面看，维护两套 forward（forward 走 wrapper、forward_with_core 走 core）是重复代码，为什么不统一？

根因在于训练框架和部署框架的表达能力不对称：PyTorch 是动态图，能写任意 Python 对象状态（self._temporal_state 跨 batch 持有），训练时 wrapper 模式让代码简洁（update_temporal_state 一个调用就更新记忆）。但 ONNX/TensorRT 是静态计算图，一次推理一个确定输入 → 一个确定输出，图里不能有跨调用的成员变量 —— 任何跨帧状态都必须拍扁成图的输入输出。

所以双形态的真正价值是：让训练代码的简洁性和部署的可行性各得其所。如果只保留 stateless core，训练时每个 batch 都要手动传 6 个 memory 张量、手动写回，代码冗长易错；如果只保留 stateful wrapper，导不出 ONNX（stateful 部分无法 trace），上不了车。StreamPETRHeadCore 是无状态纯函数（head.py:26-46），StreamPETRHead 是有状态 wrapper（:479-496）调 .core，ONNXModelAdapter 在车端用 numpy 维护 6 个记忆张量（onnx_adapter.py:100-128）。同一份权重，三种「活法」，分别对应「训练便利」「ONNX 可导」「车端可执行」三个互相冲突的目标。

这套设计还把「何时 reset 记忆」这个产品决策留给了部署侧（force_reset 由数据集 clip_start 决定），训练和部署解耦。ONNX 输出后 6 个张量是新记忆而非在模型内原地更新，是因为 ONNX 计算图没有「副作用」语义。

决策二：为什么用 TARGET_AREA 反向量自车（target_area_distance_allinfo），而不是单独标注居中真值

这是数据闭环里最巧妙的「自洽」设计。表面看，要衡量「自车是否居中」，最直觉的做法是让人工标注车道中心线作为真值。但 JoyDriver 偏偏用训练时模型看的同一个 TARGET_AREA反过来当尺子量自车偏移。

根因是分布自洽：模型训练时见到的 TARGET_AREA 是 preprocess 用地图 + 参考线算出来的「驾驶意图栅格」，模型学到的「居中」概念是相对这个栅格的中心线。如果挖掘时用另一套真值（人工标注的车道中心），就会出现「挖掘说这帧不居中、模型说它居中」的矛盾 —— 因为两者用的「中心」不是同一个。用 TARGET_AREA 反向量，等于用模型的世界观筛模型的数据，挖掘的判据和模型的优化目标完全对齐。

具体算法（target_area_distance.py:196-301）：对 target_area 做连通域分析提取中心线，在自车当前 x 处插值出中心线 y 作为 anchor_center_y，算 signed_lateral_distance_60 = 未来 60 帧自车 y 减 anchor_center_y 的序列。这 60 个数刻画「未来 6 秒自车会偏离目标车道中心多少」，既是挖掘的指标，也是 clean_*/recall_* 脚本剪枝/召回的依据。配合 start_frame=25、recovery_ratio=0.70、median 0.20 这些从数据分布调出来的超参（不是模型超参），整个闭环的判据都和模型训练目标对齐。

决策三：为什么 TrajectoryHead 输出 acc/omega 再积分，而不是直接回归 xy 位置

这是端到端模型里影响最大的设计决策之一。表面看，模型的最终输出是轨迹（xy 位置序列），为什么不直接回归 xy，反而绕一圈回归 acc/omega 再积分？

根因有两个。第一，运动学合法性：车辆是 nonholonomic 系统（不能横向平移），直接回归 xy 网络可能学到物理上不可能的轨迹（侧滑、瞬移）。回归 acc（加速度）和 omega（偏航角速度）再积分，等价于把「自行车模型」作为硬先验嵌入网络 —— 输出的轨迹天然满足运动学约束。而且 acc/omega 是受约束的物理量（可 clamp 到 acc_min/acc_max），网络不会预测出物理不可能的控制量。

第二，误差结构：直接回归 xy，长程误差随时间累积放大（未来第 6 秒的位置误差远大于第 1 秒），loss 被末期误差主导，训练困难。回归 acc/omega 后，loss 是定义在「控制量」上的，速度对了，位置就跟得上，误差结构更合理。代价是 cumsum 在 fp16 下数值不稳定，所以 joydriver_v0.py:231 显式 autocast(enabled=False) 用 fp32 积分。

这个设计还有个下游红利：输出 acc/omega 可以直接喂给下游控制器（转向/油门），不需要反解。如果直接回归 xy，控制器还得反解 acc/omega，引入数值误差。多模态输出 6 条候选 + 概率，则对应「未来本质上不确定」的建模假设 —— planner 从 6 条里选最优或加权。
