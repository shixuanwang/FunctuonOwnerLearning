DDD + 状态机：产品架构 × aicoding 的杠杆

一份写给"4 年数据闭环 PM、判断力领先、目标 Function Owner"读者的单文件教材。核心论点：主动加白（design-time 把合法状态/转移/边界/契约先设计好，约束 AI 只在合法路径上生成）vs 事后加黑（post-hoc 让 AI 自由膨胀再 review/blocklist 收敛）。前者把"防住所有坏情况"换成"只放行已知好情况"。

读者：cheche · 状态机 practiced（doc02 状态清单） · 治理结构（变更单/契约/审计）introduced（最关键短板） · 工程化 PRD practiced（doc17 单点爆发未模板化） · 编写日期：2026-07-26 · 认知契约：模型先行/先因果后术语/两遍法

① 定位：为什么 DDD + 状态机是产品架构 × aicoding 的杠杆

产品架构最痛的不是写不出功能，而是"隐性规则被绕过"——已归档项目还被改配额、已停用用户还能审批、已废弃数据集还参与训练、状态机的某个不变式被某段 service 代码偷偷绕过。把规则写在 README 或 PM 脑子里，等于没写。

本教材的因果骨架是三句话：

  1. 结构问题用结构解法。AI 生成的代码"看起来合理、只在碰巧对齐训练分布时才正确"（plausible by construction, correct only where aligned with training distribution）——这是结构性问题，不是 prompt engineering 问题，code review 抓不到。解法是把信任预算花在确定性层：限界上下文（圈 scope）+ 状态机（显式合法转移）+ 聚合边界（局部化变更）+ 契约（验证 gate）。
  2. 主动加白把默认值翻成 DENY。黑名单默认 ALLOW（只能拦已知坏、对零日威胁慢半拍）；白名单默认 DENY（问"这是不是已知好"而非"是不是已知坏"）。加白把不可能的"防住所有坏情况"换成可能且可验证的"只放行已知好情况"。
  3. 治理结构（变更单/契约/审计）就是加白的工程化产物。读者最缺的治理结构，恰好就是 aicoding 时代让 AI 不漂移的结构性护栏——契约是状态机的对外承诺，变更单是穿过唯一入口的放行记录，审计是执行日志。
读者作为 PM 已有"状态清单 + 工程化 PRD 单点爆发"的判断力，缺的是把它们形式化成"边界句 + 状态机 + 变更单 + 契约 + 审计"五位一体治理制品的纪律。这教材把 doc02/doc17 的判断力固化成可被开发直接落地的规格，让你从"能说概念"跨到"能决定代价/故障模式/验收信号"。
为什么 DDD 和状态机必须配对讲：DDD 给"边界与一致性"（限界上下文、聚合、不变量、事件），状态机给"在边界内让规则可执行"（合法转移表、guard、effect）。只讲 DDD 容易停在哲学，只讲状态机容易切碎边界。两者结合才能回答"AI 生成的代码改了这个对象的这个字段，会不会违反业务规则"。

② DDD 第一性原理

2.1 统一语言（Ubiquitous Language）：把业务词汇焊进代码，不是停留在文档

先讲因果再讲术语。软件项目失败的根因常常不是技术选型，而是开发者与业务专家对同一个词有不同隐含模型。Lehtinen et al.（Information and Software Technology 2014，被引 292 次）把"stakeholder 之间缺乏沟通"列为软件项目失败主因之一；多个援引 Standish CHAOS 的二手来源一致：约 50% 失败源于需求/对齐问题，约 7% 才是编码错误。Eric Evans 在《DDD》第 2 章"Communication and the Use of Language"用"conceptual translation map"描述两套模型间的翻译，并明确写"loss of shared language will reduce communication"——把翻译和共享语言流失当作失败机制本身。

Evans 创造的术语 Ubiquitous Language 指：开发者和领域专家共同建设、持续演进、并以代码里的领域模型为锚点的一套严格词汇。三件事已被权威逐字确证：

  • (1) Pervasively 贯穿对话/图/文档/代码：Fowler 引用 Evans 原话"using the model-based language pervasively and not being satisfied until it flows"（Fowler bliki）。Agile Alliance 词条补充"applying it consistently across all communications, code, and documentation"。注：Fowler 页面未逐字说"类名/方法名 = 业务名词/动词"，这是 Evans《DDD》第 2 章 / DDD Reference PDF 的标准推论，溯源应回到 Evans 而非挂在 Fowler 名下。
  • (2) 对话是模型的测试机制：Fowler 原文"using the ubiquitous language in conversations with domain experts is an important part of testing it"；Evans 原话"Domain experts should object to terms or structures that are awkward"+"developers should watch for ambiguity or inconsistency"。
  • (3) 活的、随理解演进：Fowler 原文"the language (and model) should evolve as the team's understanding of the domain grows"。

代价视角：没有统一语言，每次需求评审 / PR review 都在重新翻译，翻译损耗随系统规模显著放大（VMware Tanzu 博文"Translation and context sharing has a cost that should not be ignored"——注意：权威资料只说"不可忽略"，未给出 O(n) 的定量结论，"线性放大"是修辞，不是已证的复杂度量级）。Yuri Melo（Substack）反面提醒：维护不当会引入官僚开销，即代价不是单调收益。

独立验证修正（重要）：调研初稿把"贫血模型"归因为"统一语言失配的代价"，这条因果链在权威文献里找不到直接依据，已被收窄。Fowler《AnemicDomainModel》原文把贫血模型的病因归为"(a) 过程式编程习惯 / 数据背景思维；(b) 框架诱导（如早期 J2EE Entity Beans）"，Evans 关注的也是"行为没落到合适的对象上"。正确表述：对齐失败带来翻译税 + 隐性 bug；过程式思维带来贫血模型；两者常共生但来源不同，不是单向因果。教材第 ⑤ 节会按这个修正版本展开。
契约 = 用统一语言固化下来。读者治理短板（变更单/契约/审计 introduced）的技术对偶就在这里：契约/Schema/变更单本质是把跨团队共享词汇固化可执行，与统一语言"消除翻译层"的目标同构。这是 introduced → practiced 的逻辑入口。

2.2 限界上下文（Bounded Context）：按"语言在哪里分叉"切边界，不是按页面

因果链：系统越大，单一统一模型越不可能且越不划算（里手都为同一词吵不完）。Evans 经典论述——Fowler 引用："total unification of the domain model for a large system will not be feasible or cost-effective"（Fowler bliki）。Bounded Context 是 DDD 战略设计的中心模式：给一个"在这个边界内模型与语言必须内部一致（no contradictions）"的明确范围。边界常由人类文化/语言切换决定——Fowler 原文"Usually the dominant one is human culture, since models act as Ubiquitous Language, you need a different model when the language changes"。

同一词在不同上下文里有不同定义，就该是两个上下文。强行统一 = 制造半成品字段。JoyDrive 真实样本（一手实证，doc/organization-prd.md）：边界句"组织管人、项目、角色权限、GPU 总配额和授权关系；资源管资源对象和调度策略；监控管运行状态和告警诊断"——一句话把"项目"在三个上下文的不同定义钉死。

  • "项目"在组织域 = 授权关系 + 配额；在资源域 = 可调度资源；在监控域 = 告警对象。三义分叉属实。
  • "配额"在组织域 = 总量授权（只暴露剩余量）；在资源域 = 实时扣减（D2 划归业务/资源域，组织 PRD 只暴露剩余量）。
  • D5 把 NamespaceBinding 的 Error 态归资源域写入、组织页只读展示——跨上下文事实归属的精确切分。

"语言在哪里分叉"是判断边界的第一性原理。看到任何一个写操作先问"这个词在另一个域里有不同定义吗"——如果答"是"，就该切出独立上下文。读者做 doc12"数据闭环场景矩阵 + 7 共性能力"已经识别了能力，缺的是把能力映射到限界上下文边界 + 上下文映射（谁是上游下游、谁是 ACL、谁是共享内核）。

2.3 Core / Supporting / Generic 子域：把最贵的工程注意力投向唯一不可替代的部分

三分类决定资源投向（读者作为 PM → Function Owner 最该懂的战略杠杆）：

  • Core Domain（核心域） = 业务之所以能赢、不可替代、必须用最优秀的人自研放最大投入（例：推荐排序、定价引擎、自动驾驶数据闭环）。
  • Supporting Subdomain（支撑域） = 重要但非差异化、可定制可外包（例：订单履转、数据标注工具）。
  • Generic Subdomain（通用域） = 所有人做法相同、直接买/SaaS（认证、日志、推送、看板）。

Vlad Khononov 指出："In the Blue Book (Evans), the terms domain and subdomain are used interchangeably"。Vernon 红皮书将三类（核心/支撑/通用）细化为核心战略投资框架。这是 introduced → can-decide 的判断题：把哪些算 core 直接决定团队生死投入分配。最常见资源浪费：把通用域（认证、看板）当核心域自研。

对应读者场景：数据闭环里的"采集 → 上传 → 解算 → 落仓 → 标注 → 训练 → 评测 → 交付"链路，"数据资产血缘账本""可复现实验冻结"是核心域（自研重投入），"数据标注工具链""告警看板"是支撑/通用域（可定制或买 SaaS）。读者做资源决策时按这个分类排优先级。

2.4 战略 DDD vs 战术 DDD：先画地图，再盖房子（顺序错了全盘皆输）

战略（strategic）决定"系统边界与业务对齐"——bounded context、上下文映射、子域划分，是地图/蓝图。战术（tactical）决定"在某个 context 内如何建模"——entity / value object / aggregate / domain event / repository / factory / domain service，是砌砖。Fowler 明说战略设计处理大模型大团队问题；微软文档明说"design a microservice to be no smaller than an aggregate and no larger than a bounded context"。

读者校准：判断力领先但治理是短板——战略层（boundary、context map、契约面）正是最该补的那一层，战术层已在 doc02 状态机里 practiced（状态转移 = 实体行为）。常见误区：跳过战略直接玩战术模式，结果聚合边界划错、微服务切碎——这正是 Function Owner 必须拦下的架构债。

2.5 实体 / 值对象 / 聚合根 / 领域事件：四个战术原语

实体 vs 值对象：身份决定一切建模默认值

因果问题："这个概念要不要被跟踪身份？" Entity 有唯一身份、跨时间延续，两个同 ID 实例即使属性变了也是同一个东西（如账户、客户）。Value Object 无身份、只由属性值定义、不可变、可互换（如地址、金额、坐标）。微软文档的默认值："Prefer value objects as your default modeling choice. Only promote a concept to an entity when you need to track its identity over time"。示例：Address 通常值对象，但若需审计跟踪某地址记录历史则升为实体。

这条规则对抗"万物皆实体 + 一堆 getter/setter"的本能，是技术层面避免贫血模型的第一道闸。

聚合根：事务一致性边界（不是数据容器）

因果链：真实世界关系复杂（订单含商品、商品有供应商），但跨多个对象改数据时要保持一致性（invariants）。分布式系统里数据库事务跨不了边界，于是 DDD 用聚合把"必须在单个事务内一致"的对象圈起来。Vernon《Effective Aggregate Design》核心原则——一个设计良好的限界上下文"modifies only one aggregate instance per transaction in all cases"（Vernon 2011）。

三条设计规则：

  1. 设计小聚合，只圈必须在单事务一致的数据；
  2. 跨聚合只引用 ID 不引用对象（reference other aggregates by identity）；
  3. 跨聚合用最终一致性 + 领域事件。

"聚合可以只含一个实体"——使它成为聚合的是事务边界，不是大小。聚合根是"一致性守卫（consistency guardian）"：外部不能直接改内部实体，所有变更必须穿过根的方法，根在里面重算/校验/确认集群仍然一致才放行。不变量（invariant）是"对象存活期间必须永远为真的业务规则"（如"一个 order 的 total 必须等于所有 line item 之和"）。

聚合 vs 实体是 DDD 最反直觉的区分。每个聚合根是实体，但不是每个实体都是聚合根。聚合根的判据：它是外部访问内部对象的唯一入口。JoyDrive 的 DataArtifact（doc/data-artifact-registry-design.md L29-61）就是聚合根——artifact_id 是聚合根、total_packages / total_frames 是聚合根内的不变量计数、Package 是聚合内实体（由聚合根管控）、Location / Event 是独立聚合。

领域事件：跨聚合 / 跨上下文的解耦主轴

因果：聚合内部用事务保一致性，但业务流程常跨多个聚合（下单 → 扣库存 → 生成账单）。在聚合外不能锁事务，于是用领域事件——聚合改完状态后 raise 一个"领域内有意义的变更"（如 DeliveryCompleted 而非"inserted a row"），其他聚合 / 上下文异步反应。区分两类：内部领域事件留在一个 bounded context 内；集成事件（integration event）在源事务提交后经消息中间件跨微服务异步发布。

2.6 Context Mapping 与 ACL：上下文之间的关系契约（直击读者治理短板）

Context Mapping 是战略 DDD 里画"多个 bounded context 之间关系"的活动——这正是治理结构的技术本体。常见关系模式（Vernon 红皮书 ch.13 / dddcommunity 体系）：

关系语义何时用
Shared Kernel（共享内核）两边共担一小块代码/模型紧密协作、共担改造成本
Customer-Supplier（客户-供方）下游客户、上游供方，谈判两团队都有话语权
Conformist（顺从）下游完全顺从上游模型上游不可控且强势
ACL / Anticorruption Layer（反腐层）下游建翻译层自我保护上游模型污染不可控
Open Host Service + Published Language对外开放标准协议对多个下游提供标准接口
Partnership（对等合作）两团队同步演化短期紧密协作

ACL 是其中最关键的一个：当下游不得不消费一个你不可控的（遗留 / 外部）模型时，你在边界上建一层翻译 / 适配层，把外部模型翻译成你自己 context 内的干净模型，使外部模型的污染（pollution）进不来（Vernon 红皮书 ch.13）。Vernon 演示下游 context 用 ACL 把上游 IAM 的 JSON 翻译成自己的模型。

ACL 就是软件版的"变更单 + 审计隔离"——它定义了"我的契约边界在哪、外部变更如何被审校后才允许穿透"。这是读者治理结构（introduced）短板要补的那一跳：从"能说 ACL 是什么"到"能决定哪个集成面必须上 ACL、代价（翻译层维护成本）vs 收益（隔离外部变化）"。

何时该上 ACL（判断题）：(1) 上游模型不可控（外部供应商、遗留系统）；(2) 上游变更频繁且不通知；(3) 上游语义与你核心域冲突（同一词多义）。三者满足任一即应上 ACL。代价：翻译层有维护成本、有性能开销。读者做这个决策时按"故障成本 vs 维护成本"权衡——若外部模型变更穿透进来一次的故障成本 > 翻译层全生命周期维护成本，就上 ACL。

③ 状态机：state / transition / guard / effect

2.1 状态机五要素因果链（先因果后术语）

先建因果骨架：一个对象某时刻只能处于一个状态（state）；外部来了一个事件（trigger/event）；系统先问"当前状态 + 这个事件"是否允许转换，允许才走，这个判断就是 guard；通过则执行动作并产生对外可见的副作用（side-effect / effect）（发消息、写审计、扣额度）；最终对象进入新状态（target）。UML 2.x 标准定义一次完整转移必须有四部分：trigger + guard + effect + target，缺一就不是状态机。

UML 标准执行顺序（Sparx Systems UML 2 Tutorial、UCC 课件）：

  1. 触发事件到达，guard 求值前必须为 true 且无副作用（uml-diagrams.org）；
  2. Exit action（源状态）——释放资源、停止计时器（Moore 风格）；
  3. Transition effect——绑事件、绑副作用（Mealy 风格，发消息/扣额度/写审计）；
  4. Entry action（目标状态）——初始化资源、启动计时器（Moore 风格）；
  5. 对象进入新状态。
Mealy vs Moore 不是选择题，是观察视角。Moore 把输出绑在状态上（进入某状态恒定输出，用于 guaranteed initialization / cleanup）；Mealy 把输出绑在转换上（转换时由事件决定输出）。领域建模里 Mealy 更常见，因为业务副作用（发消息 / 扣额度 / 写审计）通常由"事件触发"而非"状态驻留"决定。Kevin Webber 论证："the Mealy model is the one to keep in mind for event-driven systems"。注意：UML state machine 是 Mealy + Moore 混合体——entry/exit 是 Moore 面、transition effect 是 Mealy 面。不要把 entry/exit action 当 Mealy。

2.2 状态机的核心价值：用"唯一状态"消灭非法组合（不变量编码载体）

不用状态机时业务常靠一堆 bool 标志位（isPending / isApproved / isExecuting）描述对象，但 n 个 bool 会组合出 2^n 个具体状态，其中只有少数在业务上合法。若用平铺的 bool 字段（而非判别联合）建模，类型系统阻止不了写出非法组合，bug 藏在"非法组合被某段代码处理了"的地方。

状态机用单一 status 字段 + 受控转换路径，在结构上保证"同一时刻只有一个状态"，非法组合直接不存在。这是状态机作为"不变量编码工具"的根本机理：把"哪些状态合法、谁能跳到谁"从散落 if/else 提升为一张可审查的表。

独立验证修正（重要精度提示）：调研初稿说"编译器/类型系统阻止不了写出这种组合"——这是错误泛化。bool 字段确实阻止不了，但类型系统（判别联合 / sum type / discriminated union）恰恰可以在编译期让非法组合不可表示（F# for Fun and Profit "Designing with Types"）。问题出在用错类型（bool），而非类型系统本身无能为力。同样，"单一 status 字段"是状态机的最低限度形式，只保证状态名互斥，并不保证状态特定附带数据的合法性（如 status=APPROVED 时 approvedAt 是否填、status=PENDING 时是否误填执行结果）。状态机作为不变量编码工具的最强形态是"状态 + 转换表 + 每状态类型化数据"（State 模式，下一节）。

make illegal states unrepresentable——这是 Yaron Minsky（Jane Street，2010《Effective ML》）的经典口号，源头是 OCaml（不是 elm；Kent C. Dodds 的"make impossible states impossible"是后端传播变体）。"Making illegal states unrepresentable is all about statically proving that all runtime values (without exception) correspond to valid objects in the business domain"。对比 Transaction Script 的致命缺陷：'What is stopping a new developer from just doing new User({...})? nothing'——校验只在一个方法里，绕过它直接 new 一个对象就失效了。加白做法是私有构造 + 静态工厂方法：让"创建对象的唯一路径"必须经过校验，编译器替你强制。

2.3 State 模式：把每个状态的"行为 + 数据"封装成一个对象

当某状态需携带专属数据（如"蹲下"状态才有 chargeTime，"审批中"才有 approverID + deadline），堆在主对象上会造成"这个字段何时有意义"的混乱。State 模式（GoF 设计模式）给每个状态一个类，状态专属数据跟着状态类走；主对象只持 state_ 指针，"改变状态"= 指针指向新状态对象（Game Programming Patterns）。新增状态 = 加一个类，不动其他状态代码。

SSENSE 用 TypeScript 实现 Ready / Locked / Abandoned 三态，每个状态类携带 back-reference 到 domain model（SSENSE Tech）。把状态机五要素直接映射成 API 的最干净对照是 Stateless（C#）：

2.4 Event Sourcing 里聚合本质就是状态机

ES 因果链：事件流是对象所有变化的有序记录；回放事件重建当前状态。所以 ES 中实体天然是状态机——状态 = 回放事件栈后的快照，转换 = 追加新事件。Oskar Dudycz 实践："They're usually state machines. Each state is actually a different aggregate"。酒店预订例：'there is a distinct set of operations you can do on the initiated, confirmed and completed reservation'。

更深一层：同一实体在不同状态下可做的操作和应有数据结构都不同（initiated 能 confirm、confirmed 能 complete、completed 只读），故"每个状态其实是不同的聚合"。Dudycz 用"数据 + 函数"（Decider 模式）组合，而非单一 OOP 类硬塞所有状态方法，因为'用一套方法覆盖所有状态反而增加认知负担'。这把状态机、聚合、不变量钉死在同一机制上：不变量在每个状态的函数内自然成立（不可变数据创建时已验证、每个状态只暴露允许操作）。

2.5 跨聚合不变量：不能用强一致，要用 Saga / 状态机协调最终一致

当一个不变量跨多个聚合边界（如"转账两端金额必须对等"），强一致方案 = 嵌套锁多个聚合，结果是死锁和低吞吐。Zilverline 实测：嵌套锁死锁后吞吐仅 1.24 req/s，改 Saga 后 48 req/s（高并发达 90）。

解法是 Saga 模式：把跨聚合操作拆成 reserve → deposit → commit/cancel 三步，每步只锁一个聚合，用 reference UUID 贯穿，协调流程本身就是一个状态机（reserved → deposited → committed / cancelled）。状态机让系统在任何中断点都能审查预留状态判断事务进展，从而支持补偿操作。这是"状态机治理长流程"的典型落地：用状态序列 + 事件记录替代分布式锁。

读者场景对应：若要做"同一批数据不能同时被两个训练任务独占"这类跨聚合不变量，警惕强一致陷阱。参考 Zilverline 的 Saga：把跨聚合操作拆成 reserve→commit/cancel 三步，用状态机协调，不要用嵌套锁。这对应数仓血源 / 版本化场景里"跨表 / 跨任务一致性"的盲区。

2.6 层级（hierarchical）与并行（parallel）：把"状态机"变"状态图"

当状态数变多、出现正交关注点（如订单"支付状态"和"物流状态"可独立演进），扁平状态机会状态爆炸（状态数 = 各维度笛卡尔积）。Harel 状态图引入两层：

  • 层级——子状态嵌套在父状态内，继承父状态转换，"退出父状态"自动退出所有子状态；
  • 并行——多个 region 同时活跃，事件广播到所有 region，各 region 独立消费。

W3C SCXML 把 Harel 状态图标准化为 XML（W3C SCXML），并有 run-to-completion（RTC）语义：一个事件的处理不被打断。判断标准：状态数 > 8 或存在正交维度就该考虑层级 / 并行，否则扁平机就够。HN 社区共识："A statechart without hierarchy is just a state machine. It is the composition and hierarchy that turns a state machine into a statechart."

何时上状态机框架的阈值：状态少且转换简单 → 手写 enum + switch 或 Go 类型校验即可（如 JoyDrive internal/platform/state.go）；状态多 / 需可视化 / 需跨语言共享 → 上 Stateless / XState / Akka FSM。框架的价值是 PermitIf / guard 互斥校验、Mermaid 导出、外部状态存储这些工程化能力。读者领域（数据闭环 ~25 状态、有并行管线如公有 / 私有 pipeline、有正交维度如采集状态 vs 处理状态）已超过扁平机的舒适区（> 8 状态）。考虑用层级状态把"采集/回传/上传"和"解算/落仓/应用"分成两个 region，避免状态爆炸。但不要一上来就上 XState/SCXML 重框架——先用 mermaid stateDiagram-v2 画清楚转移表，验证业务规则对了再考虑代码化。

3.1 聚合根 = 确定性状态机：命令先校验不变量才产事件迁状态

把 DDD 和状态机焊起来的核心论断：聚合根是确定性状态机。命令进来先校验不变量（"执行后是否仍成立"），成立才产事件、才迁移状态。Vernon 红皮书核心原则：聚合设计围绕 true invariants，在单事务内完全一致（InformIT）。t-pl.io 用自动机理论把 Command/Behavior/Event 映射到 FST 的 (S,C,E,δ,ω)："FSMs process a stream of Commands, enforcing invariants and changing state"。MS 官方："validation rules = invariants, aggregate main responsibility is enforce invariants across state changes"。

两个关键边界：

  1. 不变量校验 ≠ 输入校验。前者管业务规则（如"order total = Σ line items"），后者管数据健全性（必填、长度、格式）。Enterprise Craftsmanship 明确："DDD says it's the responsibility of the aggregate to protect the invariants"，并区分 input validation（上游）vs invariant validation（聚合内）。
  2. 状态迁移逻辑只能活在聚合根内部一处。这是把"哪段代码能改对象状态"显式收敛的设计原则。

3.4 事件驱动状态转移：Outbox + workflow-service 编排跨上下文流程

因果链：单聚合内的状态迁移用同步事务；跨聚合（如"实验创建"要触发 metadata 写血缘 + cluster 提交训练 + dataset 回写）必须异步、可重试、最终一致。JoyDrive 的做法（doc/architecture-design.html）：

  • 业务表与 Outbox 表在同一事务提交（保证事件至少产生一次）；
  • PG NOTIFY 唤醒 worker 投递；
  • Reconciler 周期扫描未处理事件兜底；
  • 目标服务按 event_id 和 business_key 去重（幂等）；
  • POST 接口要求 idempotency_key。

状态转移由"事件"驱动而非"直接调用"，这让多个上下文能独立演进而不耦合。例：cluster-service 收到 ExperimentCreated 事件后调 metadata 血缘回写 + cluster 提交训练 + dataset 回写（state.go L733-741 RequestTraining 注释明确"on receipt of an ExperimentCreated event"）。

3.5 CQRS 读写分离 + event sourcing 的轻量化形态：审计即事件日志

JoyDrive 没有上重型 event sourcing（不存全量事件流重建状态），但抓住了 ES 的本质价值——审计可追溯。做法：

  • web-service 只做读侧聚合（BFF），不持久化领域对象、不写业务事实（architecture-design.html L459）；写侧落单一权威服务。
  • 审计记录（AuditRecord / OpsAuditRecord）只追加不修改（L607），导出动作本身也写审计——这是"事件溯源"的精神落地，用审计表代替全量事件流，成本可控且满足治理需求。

这给读者的判断：是否上完整 ES，取决于"是否需要回放重建任意历史状态"；治理场景只需要"有据可查 + 不可篡改"，轻量审计足够。

④ 避免贫血模型（富模型 vs 贫血模型的真实代价）

4.1 本质区别一句话：行为该放在哪

把第 ② 节修正后的版本展开：贫血模型 = 对象只是 getter/setter 的数据袋，所有业务逻辑住在 Service 层，整体退化成过程式 Transaction Script。富模型 = 数据和行为同居于同一对象，用 OO 技巧组织复杂规则。Fowler 的判决："incur all of the costs of a domain model, without yielding any of the benefits"——你照样付了 O/R 映射层、照样建了对象、照样维护模型，但因为它"contrary to the basic idea of object-oriented design"，你拿不到 OO 该给的封装 / 多态 / 规则内聚收益。

4.2 代价拆解（不是翻译税，是行为外溢）

  1. 业务规则散落在 N 个 service 里，改一处规则要追多个文件；
  2. 实体可被任意外部 service 改坏状态（无封装保护），状态机不变式被绕过；
  3. 测试只能测 service 不能测领域规则的内聚性。

关键诊断信号（Fowler 原话）："the more behavior you find in the services, the more likely you are to be robbing yourself of the benefits of a domain model." Application Service 厚 = 贫血信号。

再次强调独立验证修正：调研初稿把贫血模型归因为"统一语言失配的代价"已被收窄。贫血模型的病因：(1) 过程式编程习惯（许多人没真正用过 domain model，尤其是数据背景出身的开发者）；(2) 框架诱导（如早期 J2EE Entity Beans）；(3) 团队对 OO 设计放弃太早——Evans 关注的正是"giving up too easily on fitting the behavior into an appropriate object, gradually slipping toward procedural programming"。不是术语对齐失败导致贫血。两者常同现（一个团队语言失配，往往模型也贫血），但是相关而非因果。
读者 doc02 状态机（practiced）的镜像：状态机要真正有效就必须住进实体里（富），否则一旦规则外泄到 service，状态不变式就是个纸面约定。读者做一次贫血模型体检：在练习仓里 grep 出所有只有 getter/setter 的实体类，统计它们的业务规则被分散在多少个 service 文件里——把规则收回实体（状态机住进 Delivery/Order 实体）作为一次可量化的重构实验，对比改动半径。

⑤ 核心论点：主动加白 vs 事后加黑

5.1 第一性原理：默认值翻转是核心杠杆

白名单 / 黑名单的本质区别不在"列什么"，而在"默认值"。

  • 黑名单默认 ALLOW：未在表中出现的就放行。所以它只能拦住"已知的坏"，对新出现的、零日威胁永远慢半拍，必须"constant updates to address emerging threats"。
  • 白名单默认 DENY：未在表中出现的一律拒绝。所以它不依赖穷举坏样本，问的不是"这是不是已知坏"而是"这是不是已知好"。

多源一致（Packetlabs、Adaptist、BCS365、Huntress）——"Default allow opens up your system to vulnerabilities because unclassified activity is assumed safe until proven harmful... With default deny in place, even new and unknown exploits are blocked unless pre-approved"。NIST SP 800-167 是官方背书的应用白名单指南。Cybereason 直引："Every time new malware is discovered, antivirus vendors add its signature to a blacklist"。

这一句就是整本教材的因果锚点：主动加白 = 把默认值从"放行"翻成"拦截"，于是 AI 生成时不可能走到"没设计过的合法状态"之外。把"防住所有坏情况"（不可能）换成"只放行已知好情况"（可能且可验证）。读者要做 Function Owner，最该懂的就是这个默认值翻转的杠杆。

独立验证修正（关键 nuance）：调研初稿最后一句"AI 生成时不可能走到没设计过的合法状态之外"过强，混淆了两个层次：
  • 句法 / 结构层：确实"不可能"。Constrained decoding 通过 token masking 让非法 token literally 不可采样——"manipulates a generative model's token generation process to constrain its next-token predictions to only tokens that do not violate the required output structure"。
  • 语义层：不"不可能"，且是白名单的真正失败模式。Cooper 用案例证明：regex 约束下模型可输出"Donald Duck"作为美国总统——结构合法、语义全错；小写约束下把 Paris 对到"spain"而非"France"。原文结论："constrained decoding eliminates structural errors but cannot prevent semantically wrong, unhelpful, or harmful content that happens to fit the required schema"。
正确表述：加白把默认值从放行翻成拦截后，AI 生成时不可能走到"语法/结构/schema 层面没设计过的合法状态"之外——非法 token 在解码时被 mask 掉、literal 不可采样。但"语义层面"仍可能出问题：合规 JSON / 合规工具签名 / 合规 SQL 形状的输出，仍可能是错误答案、越权动作或幻觉。Function Owner 的杠杆：加白封死了"形态错误"，但"语义/业务正确性"必须靠契约的另一翼（可验证的断言、测试、回滚、人在环路）来补。"好形态" ≠ "好语义"。

5.2 poka-yoke（防错）：检测 < 修正 < 预防

防错的因果链是：检测 < 修正 < 预防。New England Lean Consulting《The 3 Levels of Lean Mistake-Proofing》给出三层级：Level 3 Prevention（Cannot Produce，最高）、Level 2（Cannot Process）、Level 1（Cannot Pass）。Quality-One、ASQ《Mistake-Proofing》口径一致。

把这套直觉搬到软件：两个 boolean（引擎状态 / 飞行状态）会产生隐性非法状态（引擎关但人在空中），加白做法是折叠成一个枚举 plane_status: taxiing | flying | stopped，让非法组合在类型系统里根本表达不出来（dontbuildsoftware Substack）。

这是"加白 vs 加黑"的人话版定义：加黑 = 给错误装报警器（检测到错误），加白 = 把错误从物理结构上消除（让错误不可能发生）。状态的非法组合连"写出来"都做不到，AI 自然只能走在合法路径上。

独立验证修正（类比精度）：调研初稿用了澳洲插头"针脚角度让反向插入不可能"和 Roborock 弹簧片两个物理类比，验证发现两处不精确：
  • 澳洲插头：反插"不可能"主要靠"不对称几何 + 接地针更长先接通 + 接地针位置偏移"，而非单凭"针脚角度"。且并非绝对不可能——阿根廷 IRAM 2073 用同款几何但极性相反，说明物理结构只挡得住"上下颠倒"，挡不住接线错误造成的 live/neutral 极性反转。
  • Roborock 弹簧片：仅有 Reddit 用户经验帖 r/Roborock，非官方机械设计文档，且帖里明确说"部分型号不行"。不能当 Roborock 官方工程事实引用。
建议：澳洲插头类比改为"不对称几何 + 接地针更长先接通共同使上下颠倒插入物理不可能，但接线错误仍可导致极性反转"，避免把"结构性不可能"讲过头；Roborock 类比标注"用户经验非官方"，或换一个有官方工程背书的 poka-yoke 案例（如 3.5mm 耳机插头、USB-C 对称可盲插、SIM 卡托缺角防反插）。
伪引文修正：调研初稿引文 'It is impossible to assign an unexpected state' 多轮精确/模糊搜索均无任何出处匹配。这是伪引文风险，应删除引号或改为转述真实口号：Yaron Minsky（Jane Street, 2010《Effective ML》）的"make illegal states unrepresentable"——源头是 OCaml，不是 elm。

5.4 反事实·成本侧：只加黑（验证 + 重试）会怎样

用具体算术给读者"只加黑"的反事实兜底。设成功率 98.4%、平均重试 3 次：成功请求 1× token、失败请求 4× token，加权 = 0.98×1 + 0.02×4 = 1.06×，看似只贵 6%。但这是地板不是天花板（tianpan.co）。真实消耗 12-18% 来自两个放大器：

  1. 重试 prompt 更长，input token 是原请求的 1.5-2×（wrapper 把坏输出 + 修复指令都塞回去）；
  2. 失败与难度正相关，难样本让模型输出更长。

更致命的是"无单调收敛"：每次重试修一个缺陷却引入另一个（Attempt 2 补了缺字段却把另一个字段挪出父对象，Attempt 3 出了一个合法 enum 的 typo）。wrapper 收下第一个 schema-valid 输出，但"可能仍然语义错误（一字段修正、另一字段被静默截断）"。结论：重试是在跟"模型自己的解码分布"对抗。constrained decoding 把失败率压到"in-distribution < 1%"。

5.5 反事实·语义侧：加白的设计成本与正确边界（关键 nuance）

给加白划"正确用法"。CRANE（Banerjee et al., arXiv:2502.09061）指出严格约束有时反而"降低推理正确性"（prior works empirically observed strict constraints can hurt correctness）——因为约束太死会切断模型"绕路思考"的能力。但 CRANE 同时证明：设计得当的约束可以比无约束还好（最高 +10pp）。

给读者的教益：加白要加在"结构正确性"（状态 / 转移 / 字段 / 边界）上，而不是"语义最优"上。你加的白名单是"合法状态集合"和"合法转移图"——这层约束是净正收益；但你不要试图用约束去规定"最优答案"，那是另一回事。加白的哲学是"让非法不可能，把合法空间留给模型/AI 自由发挥"。

这条 nuance 给读者最重要的判断框架：加白不是无止境做制品，越过"AI 能可靠 draft"的拐点就是成本膨胀而非节省。codecentric 拐点论："The pivot from the strategic to the tactical level is the moment when the actor playing primary Drafter changes from a human to an AI." 拐点前制品在建，拐点后制品"富到 AI 能可靠 draft"。拐点即止，否则自身成为 cost-drift 源。这是读者 doc17 单点爆发但要规模化的关键停损判据。

⑥ 在 aicoding 里省设计/开发/调研成本

本节是教材的核心 facet——回答"在 aicoding 时代，DDD + 状态机怎么省设计/开发/调研成本"。读者对外汇报的口径应是这样一句话：aicoding 省成本的本质 = 把信任预算从 model confidence 转移到 deterministic 结构层。

6.1 避免贫血模型：富领域模型 / 契约给 AI 明确靶子，减少 interpretation drift

因果链：AI 输出"plausible by construction, correct only where aligned with training distribution"（codecentric）。若不给 AI 一个结构化靶子，它只会回退到训练分布默认值（generic CRUD / boilerplate），这种 drift 最贵——是返工级失败，不是修 bug 级失败。机制：在人介入 AI 之前先做富领域制品（Domain Story / Visual Glossary / API Product Canvas / OpenAPI），每个制品都是精度 prompt。

关键拐点：codecentric 原文"The pivot from the strategic to the tactical level is the moment when the actor playing primary Drafter changes from a human to an AI"——拐点前制品在建，拐点后制品"富到 AI 能可靠 draft"。契约把"创造发现"（creative discovery）转成"结构化输入"（formalized input）："Hand AI the formalized work and it is a force multiplier. Ask it to originate the creative work and you will be disappointed."

独立验证修正（三处需收窄）：(A) 跨源拼接冒充单源——codecentric 两篇自身从未用"generic CRUD / boilerplate"描述失败模式，调研初稿把 dev.to / levelup 的 CRUD 回退观察嫁接到 codecentric 的 plausible-by-construction 论证上。方向自洽，但应标注为"综合多家观察的推论"。(B) "最贵的 drift / 返工级 vs bug-fix 级"是修辞级强调而非已证实成本量级——AgileCaddie 与 LinkedIn 帖是断言，没有返工工时 / 缺陷密度的量化对照。论点用于成本决策需补量化证据。(C) 单边因果，未承认反证成本：重型 upfront 制品本身有过度工程风险（dev.to "The Over-Engineering Trap"、Heroku）。净结论：plausible-by-construction + artifacts-are-prompts + 拐点切换三件事已 confirmed；"CRUD 回退=最贵返工"为 partial（机制存在，成本量级未量化）；并补一条上限：制品富化在拐点即止。

6.2 避免细节膨胀：限界上下文圈定 scope，agent 不 sprawl（含 token 量化证据）

因果链：单个 agent 处理跨领域任务时，token 大量耗在"调和无关关注点"上，错误率随歧义上升。机制：限界上下文 = agent 天然工作单元，"a bounded context is a natural unit of work for an agent"（LearnInternetGrow），"agents thrive within clear boundaries but hallucinate across incompatible domains"。

量化案例：一个"guard agent"同时做 code review + security + testing，每次超过 3000 tokens，多花在调和无关事；按领域切分（quality context / security context）后，"each agent's complexity dropped from thousands of tokens to hundreds"——同样工作量，成本降一个数量级。歧义消除案例：Finance context 里 booking = 收入信号，Risk context 里 booking = 负债信号；给每个 agent 自己的 context，"结构性消除歧义，不是靠改模型"。

6.3 AGENTS.md / CLAUDE.md 即 strategic DDD 给 agent 的载体

因果链：agent 每次会话开局自动加载 AGENTS.md / CLAUDE.md，所以这里放的应是"战略决策"而非"战术笔记"。把 strategic DDD 决策（限界上下文归属、统一语言、聚合边界、不变量、集成模式）编码进 AGENTS.md，等于把这些决策从"人脑/会议纪要"升级为"agent 每次必读的可执行指令"。

James Croft 把 bounded context 直接映射为 agent ownership boundary："One or more agents represent a bounded context. This means an agent encapsulates the knowledge and rules of its specific domain." 统一语言也在此固化："Within a bounded context, use consistent terminology that a human domain expert would understand."

AGENTS.md 模板（每个限界上下文一段）：(1) 归属 agent / 责任边界；(2) 统一语言 glossary（"a cheap, high-leverage hallucination reducer"）；(3) 聚合边界 + 不变量；(4) 集成模式（ACL / Conformist / Customer-Supplier）。读者用 HilPerformancePlatform 的 onboard + 数仓两个上下文做试点，验证 "each agent's complexity dropped from thousands of tokens to hundreds" 在自己场景是否成立。

6.4 避免主线偏移：状态机显式合法转移，AI 不能引入非法流

因果链：AI 提议（probabilistic），状态机裁决（deterministic）——两者必须分离，否则 probabilistic 决策会污染 deterministic 执行。机制：runtime 硬阻断任何非显式允许的转移。例（buildmvpfast）："If approve_payment is illegal from planning, the runtime should reject it." 失败时状态机用"具体确定性原因"拒绝，而不是 prompt loop 的含糊偏离。显式终止条件防 runaway（Brightlume）：rather than letting the LLM decide when to stop, you define the boundaries—preventing runaway or off-track flows。

调研箴言：先设计 states，再列 tools（design states before listing tools）。缺失显式 state 会导致 safety drift（arXiv 2607.18366 实证）。Hugging Face Explicit State Loop："probabilistic decision-making and deterministic execution coexist without corrupting each other"。

6.5 避免成本膨胀：聚合边界把变更局部化（blast radius 控制）

因果链：变更越能局部化，rework / 重生成 / 回归测试的 token 与人工成本越小。机制：聚合 = 一致性边界，所有不变量在一个聚合内强制、跨聚合只走领域事件 / 最终一致。落到 aicoding：一个 agent 改动若被聚合边界约束，重生成 / 测试只发生在该聚合内，不会级联扩散到无关代码（即"AI 修一个 bug 破坏三个文件"的 context drift 根因之一是无边界）。

配合"不变量作硬门（hard gate）"（LearnInternetGrow）："Confidence is probabilistic; an invariant is a hard gate"——失败确定性在边界被抓，不到生产。领域模型是双向过滤器："The domain model creates a two-way filter: it shapes context going into the agent and validates results coming out"+"you catch it deterministically at the boundary, not in production"。

6.6 SDD / spec-as-contract：spec 是 source of truth，drift 被设计性消除（含承诺级别防 sprawl）

因果链：当代码从 spec 重生成而非手改时，spec 与 code 始终对齐——drift 被设计性消除。但 spec 必须达到"机器可读、边界冻结"（如 OpenAPI）才配当 source of truth；模糊 / in-flux 的 spec 作生成 prompt 会放大每个缺口（codecentric："when a spec is ambiguous, incomplete, or in flux, using it as a generation prompt amplifies every gap"）。

codecentric 给三级承诺度护栏防 sprawl：

承诺度含义风险
spec-first一次性探索，可丢低（探索性质）
spec-anchored随 code 共同演进，活契约中（需同步维护）
spec-as-sourcespec 即真理，code 由其生成高（须谨慎，spec 必须机器可读且边界冻结）

验证是 continuous 不是 one-time gate（codecentric）："It is not a one-time gate but a continuous activity." Augment Code："Spec-driven development turns specifications into executable contracts that constrain what AI agents generate."

工程化 PRD 模板化（doc17 单点爆发未模板化）的杠杆：直接套用 codecentric 三级 spec 承诺度作为 PRD 的承诺度字段，强制写明"这份 PRD 是探索 / 活契约 / source-of-truth"，从结构上防"in-flux spec 被当生成 prompt 放大每个缺口"。

6.7 约束 AI 的范式：prose 告诉 AI 想要什么，确定性检查决定它能交付什么

bitbytebit 点破读者在 aicoding 时代的核心痛点："An LLM will produce code that looks correct yet quietly violates a rule you assumed was safe"，因为它对系统依赖的约束没有固有记忆。解决方案不是写更多 prompt，而是把不变量编码到 AI 无法忽略的地方：

  • ADR（Architecture Decision Record）+ scope 文件路径 glob，Stop hook 检查"被改的文件对应的 ADR 是否被读过，没读过则非零退出"；
  • RFC 2119 关键词（MUST / SHALL / MUST NOT）+ Gherkin given/when/then 把"建议"变"可测规则"。

"Prose tells an agent what you would like, a check decides what it can ship." 读者 doc17 的 Hook + 三把锁 + Edge Cases（校准第 25-26 行）本质就是给 AI 立的 guard，但停留在单篇 PRD 没有沉淀成 hook / ADR / 契约。读者已经会的"状态机+Hook+守卫"配上 ADR+契约+确定性检查，就是从"人盯 AI"到"系统约束 AI"的跃迁。

独立验证修正（重要位置混淆）：调研初稿用 Newcomb (2025)《Preconditions and Postconditions as Design Constraints for LLM Code Generation》的实测结果背书"治理结构是关键短板"——这存在位置混淆。Newcomb 证明的是设计期把契约写进 prompt 提升生成准确率（Python pass@1 显著提升 +23.67pp, p=0.0402；Java 未达显著 p=0.066，C++ 仅 pass@1 显著 p=0.0417, pass@10 不显著；样本为单一井字棋系统、15 个类、6 模型，结论外推性有限）。但 Wasowski 主张的是审计期 / 运行期 checkable contract。读者"治理结构（变更单 + 审计）"在 Newcomb 实证里无任何数据支撑。净结论：契约部分有 pilot 支持（生成期），但"变更单+审计整套治理结构是关键短板"这一具体断言目前仍是推断而非已证。读者做这个判断时用"结构性护栏优于纯 prompt 调优、契约能压住 interpretation drift"的方向表述（有 pilot + 论证 + 直觉支撑），但不要冒充"已被实证大幅提升"。

7.1 大厂 DDD 落地路径：事件风暴 → 统一语言 → 限界上下文 → 上下文映射 → 聚合

7.4 Vernon 红皮书 vs Evans 蓝皮书：两本书的分工（读者阅读路径）

Evans《Domain-Driven Design》（蓝皮书, 2003）是开创性理论：定 ubiquitous language、bounded context、aggregates、战略 / 战术框架，偏哲学与建模思想。Vernon《Implementing Domain-Driven Design》（红皮书）是落地工程指南：把蓝皮书的抽象转成可编码的样板（聚合设计规则、Sagas、ACL 实现成 REST client adapter、CQRS、事件源），附大量 Java/Spring 代码。

两遍法适用：第一遍读蓝皮书建因果骨架（为什么这么建模），第二遍读红皮书补实现细节（怎么落地）。读者判断力领先于实现熟练度——蓝皮书对齐她的强项（判断 / 建模），红皮书补她的弱项（工程化模板），doc17 工程化 PRD 单点爆发的模板化正好对应红皮书的样板。建议阅读路径：先速读 Evans 蓝皮书第 1/2/14 章建因果骨架，再精读 Vernon 红皮书聚合设计那一章补工程模板；不要一上来啃全部战术模式。

⑧ 读者应用水平映射（practiced → can-decide）

8.1 当前水平校准（基于实测 doc02）

直接读了读者的 doc02（joyspace-cache/02-jpLBIKqy086mEqQQSVRq.txt）。它有约 25 个状态（初始态 / 数据产生 / 数据邮寄 / 数据上传 / 云端解算 / 解算通过 / 解算失败 / 处理完成 / 处理异常 / 数据资产落仓 / 数据废弃...），每个状态点挂了埋点字段（落盘时间戳、盘号、车辆 id、错误码、ncu 等）——这部分是 practiced 水准。但缺三样：

  1. 没有 from→to 的状态转移矩阵（谁能跳到哪、触发条件、guard）；
  2. 没有 side-effect 契约（进入某状态除埋点还要发什么事件、扣什么额度、通知谁）；

8.4 反共识练习：判断"加概念 vs 删概念"

JoyDrive 真实演进痕迹：domain-model.html（旧版）仍写"User、Team、RoleTemplate"（L226, L301），而 organization-prd.md 修订记录（2026-05-21）明确"采用项目制，不再把 Team 作为一等概念，User 表不保留 team 字段（D6）"。这不是矛盾，是模型演进的正常现象——Team 这个概念在组织上下文里被证明是半成品标签、被显式删除。这示范了 DDD 的反共识教训："放弃一个看似天然的概念比'加一个概念'更需要判断力，且必须落在迁移里"（organization-prd.md L58：现有 schema 的 team 字段在迁移中删除，避免半成品标签）。对 cheche：判断'加白名单 vs 加黑名单'时，能删的概念往往是更优解。
