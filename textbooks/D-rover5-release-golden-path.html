①现状诊断：四条线在代码侧基本断链

把部门四条线（无人车交付 / 需求交付 / 问题收敛 / 代码交付）落到 git 这一侧来看，代码交付是唯一有客观留痕的；其余三条线本应通过 commit message 里的关联号、MR 描述里的验收链接、tag 上的发版说明串起来，但 ROVER5.0 在代码侧的留痕只剩"模块前缀"这一根细线，且模块名不受控。下面六段是逐段证据。

1.1 合并方式：squash / 快进合并，MR 边界在主干上彻底消失

因为合并时只把代码差异压平进主干、不产生独立的 Merge branch X into devel 节点，所以从主干 git log 里看不到任何一次 MR 在何时、由谁、合了哪些 commit、关联到哪个需求或缺陷。每条 commit 像被直接 push 到 devel 上一样扁平——产物是线性历史，代价是"MR 作为评审/验收/责任单元"这个最重要的可追溯锚点不见了。

recon:1"===== 近 30 merge commit =====" 标题下完全空白，作者预期找 merge commit 实际一条都没有
git log --merges --oneline -200 | wc -l = 0本机实跑输出 0 行，独立二次确认近 200 commit 区间无任何 merge commit
recon:107-109branch -r 只有 origin/devel 一个长期分支，无 release/* hotfix/* 等并行分支，主干即一切
git config --list仅 branch.devel.merge=refs/heads/devel，无 pull.ff/merge.ff 配置，ff 是默认行为而非显式策略
无 merge commit → MR 边界丢失 → 出线上问题想倒查"这是哪次 MR、哪次评审、哪个需求带进来的"时，主干上没有任何锚点，只能靠 commit message 的人肉记忆或日期推测。这是"问题收敛"在代码侧的最大结构性 gap。
把这条讲给团队时，关键不是争论 squash 好还是 merge commit 好，而是"MR 是部门级的评审/验收/责任单元"——一旦压平，这个单元的责任人、评审记录、关联需求全部从代码史里蒸发。

commit message 里通常需要带 issue 号、Jira key、MR 号。ROVER5.0 的 200 条 commit 里一条这样的关联都没有（grep issue/jira/MR/PR/refs/#N 全部 0 真实命中，recon 里看到的 17 个匹配全是 inf/protection/prepare 这类英文词里的子串误报）。替代方案是 wangboqian1（wbq）这个人把自己的 8 条 bugfix commit 都加 _wbq 后缀，部分还带日期（_0526）和疑似需求号（_7387/_8447/_0714），形成了一套只在他脑子里能解码的追溯暗号——其他人 0 条这么做。

②根因：squash 合并 + lightweight tag + 手输 commitId 的三重失效

四条线脱钩不是四个独立问题，而是三个共用节点的三重失效。任何黄金路径设计都必须在这三个节点同时打钉子，只改其中一个（如只加 commit 规范）解决不了交叉追溯。

2.1 节点 A · 变更：squash 合并把 MR 压成一条 commit

N 个 MR 压成 1 条 commit，MR 模板里 FixJira/模块/测试结论全丢。需求线 ② 与问题线 ③ 同时失去 git 锚点。

git log --merges -200 = 0squash 全局策略，MR 边界在 git 中系统性丢失
.gitlab/merge_request_templates/merge_template.md:11-15NoTestReason/ExpectedResults 字段存在，但因 squash 未进 git，关闭信息无处沉淀
对比：模板有 FixJira 契约 vs git log body 无 Jira证明是流程执行断层而非模板缺失——契约写了但被 squash 冲掉

2.2 节点 B · 版本：lightweight tag + 多对一，tag 是产物标签不是变更标签

278 tag 全是 lightweight、不带注释；QA/HIL/daily 多个 tag 同指 b91eb4b2 一个 commit。tag 命名是"场景+日期"而非"变更集"，无人车线 ① 的"版本"与代码线 ④ 的"变更"之间是松耦合，无法做偏序。

git cat-file -t QA_20260725_daily_trt1013 = tag（lightweight）tag 全是 lightweight 且多对一，证实 tag 是产物标签而非变更标签

③MR 体系最佳实践：分支策略、合并方式、模板、门禁

这一节把"行业怎么做"摆出来，作为下一节"ROVER5.0 该怎么做"的参照系。重点是 trade-off 不是教条——每一项都标注了在车端场景下的取舍。

3.1 分支策略：Trunk-Based vs Git Flow vs Release Flow

车端栈的发布是"日级 daily build + 按 sensor_kit 分包 OTA"，这决定了分支策略不能照搬 SaaS 的 GitHub Flow（一条 main 随时部署），但也不必上重型 Git Flow（5 类分支太重）。推荐 Release Flow 的轻量版：

策略分支拓扑适用场景ROVER5.0 适用度
Trunk-Based仅 main + 短命 feature持续部署、强 CI、小团队部分 现状是 trunk 但无 release 分支
GitHub Flowmain + feature，PR 即部署SaaS、Web、可回滚不适合 车端不可秒级回滚
Git Flowmain/develop/feature/release/hotfix有明确版本发布的产品太重 5 类分支对 50 人团队过载
Release Flow（推荐）main(devel) + feature + release/* + hotfix/*有发布节奏的企业软件推荐 与日级 daily 节奏匹配

3.2 squash vs merge commit：可追溯性的核心 trade-off

这是产品负责人 own 发版流程时最容易被带偏的一个点。把它讲清楚：

squash merge（ROVER5.0 当前）

  • ✓ 历史线性、干净，git log 易读
  • ✓ 一个 MR = 一条 commit，语义集中
  • ✗ MR 标题/描述/review/CI 状态全部不进 git 图
  • ✗ 出问题无法回溯"哪次 MR、谁审的、关联哪个 issue"
  • ✗ blame 看不到评审上下文，只有最终作者

merge commit --no-ff（推荐用于关键模块）

  • ✓ MR 边界在 git 图上可见，标题即评审单元
  • ✓ 可 git log --merges 直接列出所有评审点
  • ✓ 出问题可二分定位到引入 MR
  • ✗ 历史非线性，git log 稍乱
  • ✗ 仓库作者需统一接受

行业惯例折中：feature 分支用 squash（保留 PR 内多条 commit 的可读性），但 squash 后的 commit body 强制带 Fixes: JDXAD-xxxx + 评审人 + 模块前缀。这样既保线性又保追溯。关键在于：squash 不是问题本身，"squash 之后没有任何东西替代 MR 承载追溯信息"才是问题。

evaluator 是另一个发现引擎，专门盯"行为质量"而非"健康度"。它订阅 Planning/Localization/感知/信号灯等 topic，按 11 个"指标 handler"逐项算（碰撞距离/速度加速度越界/顿挫/绕路/路口/障碍物/信号/尾灯/检测置信度），算出来不达标就标一条 LabelResult 发出去。这套标签流向 data_miner 的 save_jira_data 模块，按 priority=HIGH 保留对应时间窗口的数据，最终回传云端形成可被标注/复盘的 badcase。

evaluator/metrics/ 目录（11 个 metric handler）collision/planning/stutters/detour/intersection/obstacle/signal/taillight/detection_confidence 等行为质量指标各一个 handler
data_miner/data_dispatcher/save_jira_data/save_jira_data_dispatcher.cc:45-90Process 读 save_jira_data_table，按 HIGH priority 组装 retaining_data，DeleteOneJiraData 说明 jira_id 是问题归属键——即每个 badcase 对应一个 jira
evaluator 触发的 badcase 有 jira_id（save_jira_data_dispatcher 明确以 jira_id 为键），但修复它的 commit 从不引用这个 jira。"发现"产出了问题 ID，"修复"却不认这个 ID，闭环在这里就断了第一处。

5.3 定位：通过数据源→faultId→error_code 的映射链把问题钉到模块

问题被发现后要回答"是谁的锅"。每个数据源（system_status/module_status/latency/vehicle_motion/battery/control_cmd/gnss_imu）天然绑死一组 faultId，faultId 又绑死一组 error_code 枚举。所以一旦某个 fault 触发，归属链是"数据源→faultId→error_code 枚举名→Guardian 的 module_result.name"。

degradation_monitor/daemon/degradation_control_daemon.cc:86-114GetSourceToFaultIds 静态映射表：system_status→F001/F002/F005/F006...，module_status→F004_HZ/F004_EC...，gnss_imu→F018 碰撞——这就是'数据源→故障类别'归属
degradation_monitor/handler/detection_handler.cc:279-312,1121-1263F004_EC 四队列（warning/error/fatal/critical）把每个 error_code 映射到严重度桶
定位粒度是"故障类别/数据源/模块进程"，不是"代码行/commit/PR"。从 error_code 反查不到是哪次提交引入的回归——因为 commit 不带 issue/jira 关联。所以"定位"止步于"是 Planning 模块的 F004_HZ fatal"，无法继续收敛到"是 abc123 这个 MR 把 expect_hz 改错导致的"。
无人车行业惯例：定位要做到"问题→模块→负责人→引入版本"四级。这里第一级（模块）有，第四级（引入版本）完全缺失，因为 git 端没留 issue 关联也没留 MR 边界。

5.4 修复（断点 A）：commit 直提交无 issue 关联、无 MR 边界

定位后开发者直接在 devel 分支上提交修复。commit subject 大致遵循 <模块>:<subject>，但风格极不统一（大小写混用、有的带 fix、有的带 feat、有的纯中文如"实现禾赛ATX雷达的故障上报"）。合并方式是 squash/快进，导致近 30 条 merge commit 全部为空。最关键：300 条 commit 里 0 条带 issue/jira/refs 关联，而代码侧明明有 jira_id 概念。

_rover-recon.txt:1（近30条merge commit 标题为空）git 证据：merge commit 为空 → squash/快进合并，MR 边界丢失
git log 输出：grep -icE '#[0-9]{2,}|jira|ticket|ROVER-|refs|关联' over last 300 commits = 00 条 commit 关联 issue/jira——问题与代码零关联
git log --oneline -- degradation_monitor/ = 7; evaluator/ = 1; data_miner/ = 1问题收敛核心三模块的总 commit 数极少（共9），但 daily tag 几乎天天发版——说明这些模块的变更被压缩在极少的 commit 里，每个 commit 背后可能是多个未追溯的修复
三个根因级断点：(1) squash/快进合并 → MR 边界丢失，无法回溯"这次发版合了哪些修复、各自对应什么问题"；(2) commit 无 issue/jira 关联 → 问题（jira_id）与修复（commit）无法双向追溯；(3) 三模块 commit 被极度压缩 → 单个 commit 聚合多个变更，MR 化拆分缺位。
"近30条 merge commit 为空"不是说没有 MR，而是合并策略把 MR 信息抹掉了。换成"保留 merge commit"或"squash 时把 MR 标题/issue 写进 commit body"就能立刻恢复追溯能力，是性价比最高的改造。

5.5 验证（断点 B）：simulation2 的 71 个 validator 与 evaluator 指标双轨

修复后要验证"没引入新问题、老问题真修了"。验证手段是 simulation2 的回归体系：71 个 validator（proto 定义），覆盖闯红灯/压实线/碰撞/急刹/规划跳变/感知漏检/预测失误/路由连通性/E2E drivable area/占用栅格关键障碍物等。

simulation2/proto/validator/*.proto = 71 个覆盖 run_red_light/solid_line_violation/active_collision/unreasonable_brake/planning_decision_jumping/perception_miss_detection/prediction_key_obstacle/routing_connectivity/e2e_collision_metric 等
simulation2/component/regression/validator/*.cc + regression/metric/*.cc两层实现：regression/validator（场景级判过不过）+ regression/metric（连续指标如 TTC）
验证层最大的问题是"指标双轨"：仿真用 simulation2 的 validator（71个），实车/在线用 evaluator 的 metric handler（11个），两者定义不统一（同名概念如 collision 在两边实现不同）。结果是一个 badcase 在 evaluator 标出来了，仿真回归却可能验不到，反之亦然。"验证"无法严格闭合"发现"。
判断点：要 own 部门问题收敛，必须推动"发现指标=验证指标"统一——把 evaluator 的 11 个 metric 和 simulation2 的对应 validator 抽成共享定义（同一 proto/同一阈值源），否则回归永远是近似而非证明。

5.6 关闭（断点 C）：daily tag 不含修复问题清单

修复 commit 进了 devel，daily tag 打出来发版，但 tag 命名（QA_yyyymmdd_daily_trt1013）不含修复的问题清单，发版说明靠人记。问题关闭要么发生在 Jira（与 git 脱钩），要么干脆没有（口头关闭）。当一个 HIL tag 跑出问题，想回答"这个问题是哪次修复引入/哪次修复该解决却没解决"时，git 给不出答案。

⑧关键设计 rationale + 反事实

把每个关键决策的"为什么这么做"和"不这么做会怎样"摆出来，方便跟团队/上级讨论时有据可依。

8.1 为什么先做 commit Fixes 关联，而不是先做 CI 单测门禁？

Rationale：commit Fixes 关联的工程成本极低（一个 hook + 一个 commitlint），但能恢复"需求↔代码"双向追溯，这是所有上层 dashboard 的地基。CI 单测门禁工程成本高（要补测试用例、要修 blade test 注释、要稳定 CI 环境），且即便建好也回答不了"这个修复对应哪个工单"的问题。

反事实：如果先做 CI 单测门禁而不做 Fixes 关联，3 个月后单测通过率上去了，但部门级 dashboard 仍然算不出"问题收敛率/MTTR"，因为代码和工单还是断的。产品 own 的核心收益（让四条线对齐）落空。

8.2 为什么推荐保留 merge commit 而不是 squash + body 带 Fixes？

Rationale：merge commit --no-ff 保留 MR 作为 git 图上的独立节点，git log --merges 可直接列出所有评审点，git bisect 可二分定位引入 MR。squash + body 带 Fixes 虽然也能恢复追溯，但 MR 评审单元在 git 图上仍是隐形的，需要靠 body 解析才能恢复，工具链复杂度高。

反事实：如果继续 squash 而不带 Fixes，线上问题二分定位时只能逐条 commit 测试，每个 commit 背后可能聚合了多个未追溯的修复（degradation_monitor 仅 7 条 commit 但 daily tag 天天发，证实了这点），二分粒度太粗。如果 squash 但带 Fixes，能恢复"工单→commit"映射，但"工单→MR→评审人→评审时间"这一链路仍不全（评审信息在 GitLab UI，归档后可能丢）。

务实折中：对关键模块（degradation/control/fault.conf）保留 merge commit，对其他模块允许 squash + body 强制带 Fixes。这样既保线性又保关键模块的完整追溯。

8.3 为什么不强行上语义化版本 x.y.z？

Rationale：车端栈的发布是"日级 daily build + 按 sensor_kit 分包 OTA"，不是 SaaS 的"功能发布"。x.y.z 语义化版本对应"功能集"概念，但车端每次 daily build 都可能含上百个 MR，x.y.z 无法承载这个粒度。 annotated tag + date + audience + MR 清单的组合更贴合实际发版语义。

反事实：如果强行上 x.y.z，要么版本号增长极快（每天 +1），要么需要定义"什么时候 minor+1"的规则，对车端栈无意义。团队会很快弃用，回到 date-based 命名。

8.4 为什么把发版流程从 wiki 搬进仓库？

Rationale：仓库是代码变更的唯一起点，发版流程文档如果在 wiki，新人/产品/测试要看流程必须跨系统，且 wiki 与代码版本无绑定（wiki 改了代码没改，或反之）。把 CONTRIBUTING.md / RELEASE.md / .gitlab-ci.yml 的 MR 模板放仓库，让仓库"自解释"。

反事实：如果继续放 wiki，每次流程变更要靠邮件通知，3 个月后无人记得 wiki 在哪、内容是否最新。新成员上手时长 = 问老人时长，部门级 own 落空。

8.5 为什么推动 A/B 分区而不是继续整包替换？

Rationale：车端 OTA 失败的代价是车趴窝（升级窗口长、失败难回滚）。A/B 分区（两个 rootfs slot，OTA 写非活动 slot，重启切活动 slot，失败自动切回）是无人车/车机行业的事实标准，能把 OTA 失败的影响降到"一次重启"。

反事实：如果继续整包替换 + status.txt 状态机，一次 OTA 失败可能需要人工上车站点恢复，部门级 OTA 灰度（5%→30%→100%）几乎不可能，只能全量推、全量赌。

这条是中长期目标，不在 30/60 天计划内。但产品负责人要把它放进 own 的 roadmap，因为"OTA 可回滚"是无人车量产的前提。

8.6 为什么模块词表是产品可决定的，而不是工程可决定的？

Rationale：模块词表的本质是"部门组织架构在代码侧的投影"——每个一级模块对应一个团队/owner。这是产品负责人（Function Owner）的职责范畴：定义"我们部门有几个一级模块、各自 owner 是谁"。工程团队负责执行（commitlint、CI 卡口）。

反事实：如果不冻结词表，团队继续用 Planning/planning/3d_planning/Planning3 四种写法，部门级 dashboard 永远对不齐，"Planning 模块本月改了几次/收敛了多少问题"这种基础问题答不出。产品 own 的数据基建落空。
