这份 PRD 把 OnBoard 平台从"被动接收台架报告的看板"重定位为"无人车软件版本发布前最后一道性能质量闸口"——以发版准出 Gate 为终态倒推四阶段、五大闭环、指标体系、技术架构与数据架构。所有"现在做到什么程度"的论断都钉到 file:line，"应该做到什么程度"用 rationale + 反事实呈现。

0. 执行摘要：定位 / 价值 / 北极星指标

0.1 一句话定位

OnBoard 是一套面向自动驾驶测试 + 运维团队的"HiL 台架性能 + 实车稳定性 + 故障码分析 + 实车性能（CPU/内存/E2E/控制误差）四合一"性能监测与发版准出平台。它解决的不是"如何跑一次测试"，而是"一个算法包从研发中 → QA → 发版准出 → 实车运营的整条性能生命周期，能否在同一个平台上一路追踪、并对发版给出 PASS/FAIL 的硬结论"。

  • docs/PROJECT.html:35-36：一句话定位"面向自动驾驶测试+运维团队的 HiL 台架性能+实车稳定性+故障码分析可视化平台"。
  • docs/PROJECT.html:38-45：三条业务线 + 第四条 OnBoard 实车性能线（平台已从纯台架工具升级为台架+实车的统一性能监测平台）。
  • docs/ARCHITECTURE.html §3.3-§3.4：4 阶段（算法开发 / 准出门禁 / 集成监控 / 灰度运营）× 4 角色（算法 / QA / DRI / 车端架构）闭环矩阵。

0.3 北极星指标（North Star Metric）

北极星 = 准出报告自动覆盖率 = (某季度算法包发版中由 OnBoard 自动产出 PASS/FAIL 准出报告的数量) / (同期算法包发版总数)。当前值 ≈ 0%（无 Quality Gate 引擎），12 个月目标 ≥ 80%。该指标同时反映"平台是不是真的被研发流程采用了"，比"任务数 / 看板 PV"更接近业务本质。

选"准出报告自动覆盖率"做北极星而非"任务数"或"看板 PV"，因为前者直接对齐平台的业务存在理由（做发版的硬质量闸口），后两者会被"为了看而看"的虚荣指标污染。Function Owner 的关键判断是：北极星指标必须是业务终态的代理量，不是工具使用量。
北极星指标"准出报告自动覆盖率"暗含一个前提假设——QA / 算法 owner 真的愿意用平台给的发版结论。若管理层未把 Quality Gate 纳入合入流程的硬约束（PR 卡点），即便平台做出来也会沦为参考工具，覆盖率永远到不了 80%。这条前提必须在路线图 P0 阶段与管理层对齐。

1. 业务背景与全生命周期模型

1.1 全生命周期模型：4 阶段 × 4 角色

用"4 阶段"切而不是按"HiL / 实车 / 故障码"数据维度切，是因为真实用户的工作场景是按时间推进的算法包生命周期，不是按数据源。PRODUCT_AUDIT §7 已诊断："UI 按数据维度组织但用户按工作场景组织，导致体验割裂"（docs/PRODUCT_AUDIT.html L204-207）。本 PRD 的 IA 重排遵循 INDUSTRY_RESEARCH L266-268 的修正：任务诊断 / 全局监控 / 场景管理 / 实车 四组。

1.4 阶段 ③ 发版准出门禁（Quality Gate）最大缺口

维度定义
目标算法包发版前必须通过 OnBoard 的 Quality Gate：指标 × 场景集 × 阈值 → PASS/FAIL，FAIL 阻塞合入
核心用户QA Lead、DRI、发版负责人、Function Owner
关键场景(a) 配置 Quality Gate 规则（指标 / 场景集 / 阈值 / 阻塞或告警）(b) 发版前查看 release gate 报告 (c) MR 合入流水线对接（webhook 卡点）
关键指标Quality Gate 阻塞率、发版回归逃逸率（上线后才发现的回归数）、准出报告自动覆盖率（北极星）
现状未交付：阈值配置（perf_threshold_config）有 warn/critical 双阈值，版本对比（compare.ts）能算 baselineValue 差值，但没有任何接口把"判定结果"转成"门禁决策"——grep "quality gate/准出/阻塞合入/block merge" 在业务代码 0 命中（docs/ARCHITECTURE.html §3.3）。
核心证据backend/src/services/thresholdService.ts L13（只读阈值供看板着色，无判定逻辑）；backend/src/routes/compare.ts L186（算差值但无阈值判定）；docs/INDUSTRY_RESEARCH.html L272-279（Quality Gate vs Alert，SonarQube 式范式）
"Quality Gate 而非 Alert"是 INDUSTRY_RESEARCH 的关键修正：质控 / DRI 的真实诉求是"发版前阻塞"而非"被动告警"。SonarQube 式范式的本质是把性能阈值从"建议"升格为"流程硬约束"——这要求平台必须能对接 MR 合入流水线（GitHub webhook / 公司内部 ERP），把 PASS/FAIL 写到合入卡点上。否则即便做了判定引擎也只是"更漂亮的看板"。反事实：若只做 Alert 不做 Gate，算法包上线后才发现回归，回滚成本是发版前发现的 10-100 倍。

2. 五大闭环设计

平台由 5 个相对独立的闭环构成。每个闭环遵循 "触发 → 数据 → 判断 → 处置 → 回流" 五段式。下文逐一展开，每段标注当前状态（已有 / 部分 / 未交付）。

2.1 HiL 任务闭环（A 线最强段）已有

触发：算法工程师 / QA / DRI 在 JobNew 页面发起任务 → 落 hil_jobs（status=queued）
数据：台架 pull queue 拉取（status=dispatched）→ 台架执行（status=running）→ 台架推 HIL_PUSH_V2 报告（1 JSON + 2 Parquet）
判断：报告带 jobUuid 时反向关联到 job（UPDATE hil_jobs SET report_task_id, status='finished'）
处置：任务失败 → rerun 创建新 job 并 retried_from 指向旧 job（追溯链）；任务完成 → 在 Compare/Trends 看结果
回流：报告入库 → hil_module_metrics / hil_memory_metrics / hil_planning_stats → hil_daily_aggregation 趋势看板

2.2 实时性能数据闭环（已达生产级 launch-review 成熟度）已有

回流：reader 通过独立 PG activation 切换可见性 → 后端读 ADS 给前端

4.4 关键选型 rationale

选型 #1：ClickHouse 用 HTTP 协议 + 关闭新 analyzer + SQL 写全库前缀

rationale：升级 CK 25.3.6.56 后，新版 analyzer（默认 allow_experimental_analyzer=1）对 ReplicatedMergeTree 跨库 SELECT 解析报 Code:60 UNKNOWN_TABLE，HTTP 客户端层传 database 参数叠加 WHERE 子句稳定触发。三件事兜底：(1) 客户端强制 HTTP；(2) SQL 写 x_performance.table_name 全前缀；(3) allow_experimental_analyzer=0 回退旧 InterpreterSelectQuery。

反事实：若不绕过，dashboard 查询随机 Code:60 失败。

技术债：把 analyzer 永久关 0 是对 CK 新版能力的主动放弃，长期阻碍升级和性能优化（new analyzer 是 CK 未来方向）。应上游反馈或等待修复后解禁。

  • backend/src/config/clickhouse.ts:9-15（HTTP 根因 + Code:60 bug）；L35-44（analyzer=0）；L21-23（SQL 全前缀）。
  • docs/DECISIONS.html L214-244：ADR-013 CK 25.3 Code:60 四类根因。

选型 #2：prod-shadow 影子表双轨

rationale：实时性能链路（1Hz 全车队）切到生产风险极高，SQL/聚合口径错误会污染线上看板且不可回滚。维护 _prod_shadow_local 影子宽表，后端通过 ONBOARD_PERF_SOURCE==='prod-shadow' 切到读影子表，可在不影响生产读的前提下跑全量 percentile 验证。

反事实：若直切生产，一次口径错误 = 线上看板被污染 = 失去管理层信任。

5.6 原子发布与 generation 机制（ADS 黄金路径）

全车队百分位一旦被下游 reader 消费就必须不可变且可追溯，所以 ADS 用"stage 表 + generation 分区 + PG fence + REPLACE PARTITION"原子发布：

  1. ETL 先写 *_stage_local 表（TTL created_at+3DAY，reader 不可见）。
  2. DQ gate 全过。
  3. PG 抢占 publishing fence（onboard_full_fleet_percentile_generation_v2 唯一约束）。
  4. REPLACE PARTITION (dt,generation) FROM stage 原子替换 6 张 final 表（dag/resource/control/context/minute_state/vehicle_qc_daily）。
  5. reader 通过独立 PG activation 切换可见性。

generation 是 UUID，cohort 间用 insert_deduplication_token 保证幂等，DROP PARTITION 只允许在 PLANNED/STAGING 等发布前状态。这套机制让"部分发布、重复发布、脏发布"都成为不可能。

7.4 准出 Gate 的统计意义

Quality Gate 阻塞合入的统计意义：性能数据是重尾分布，单次 HiL 任务的结果方差大（受场景随机性 / 硬件抖动影响）。Gate 判定必须基于足够样本（多 scenario × 多 run）+ 分位而非均值。规则建议：(1) 单场景至少 N=10 runs 才参与 Gate 判定；(2) 用 P99 而非 mean；(3) FAIL 时自动 rerun 一次再判（避免单次抖动假阳性）；(4) WARN 不阻塞但写审计（治理元数据缺失这类）。反事实：若用单次 mean 判定，假阳性会逼算法 owner 反复 rerun，平台被抵制；假阴性会让回归逃逸上线。
Gate vs Alert 的本质区别：Alert 是事后告警（被动），Gate 是事前阻塞（主动）。INDUSTRY_RESEARCH L272-279 的关键修正："质控/DRI 真实诉求是 Quality Gate（发版前阻塞）而非 Alert（被动告警）"。SonarQube 范式的工业验证：把静态分析从 IDE 警告升格为合入门禁，才真正改变了代码质量。本平台要做的是同一件事——把性能阈值从"Trends 看板上的颜色"升格为"MR 合入的硬约束"。
