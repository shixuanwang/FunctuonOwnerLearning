0. 执行摘要：定位 / 价值 / 北极星指标（重定义）

0.1 一句话定位

OnBoard 是一套面向自动驾驶测试 + 运维团队的"HiL 台架性能 + 实车稳定性 + 故障码分析 + 实车性能（CPU/内存/E2E/控制误差）四合一"性能监测与发版准出平台。它解决的不是"如何跑一次测试"，而是"一个算法包从研发中 → QA → 发版准出 → 实车运营的整条性能生命周期，能否在同一个平台上一路追踪、并对发版给出 PASS/FAIL 的硬结论"。

1. 业务背景与全生命周期模型

1.1 全生命周期模型：4 阶段 × 4 角色

7.4 准出 Gate 的统计意义（A/B 分层 + rerun 区分确定性 vs 抖动）

Quality Gate 阻塞合入的统计意义：性能数据是重尾分布，单次 HiL 任务的结果方差大。Gate 判定必须基于足够样本（多 scenario × 多 run）+ 分位而非均值（A 类用 worst-case，B 类用 P99）。规则建议：(1) 单场景至少 N=10 runs 才参与 B 类 Gate 判定；(2) A 类不进 rerun、不进 N=10，任何单次超限即 FAIL；(3) FAIL 时自动 rerun 一次再判（但 rerun 不是无条件重跑同一份，而是换台架/换时间窗重跑——hil_jobs 有 bench_pool_tag 字段，rerun 强制换 pool，物理隔离硬件抖动）；(4) rerun 结果和原结果做显著性判定而非简单覆盖——两次都 FAIL = 确定性回归直接升级人工，一次 FAIL 一次 PASS = 抖动触发"补样本"模式（再跑 3-5 次取统计量），关键 scenario 第一次 FAIL 就升级人工；(5) WARN 不阻塞但写审计。反事实：若用单次 mean 判定，假阳性会逼算法 owner 反复 rerun，平台被抵制；假阴性会让回归逃逸上线。

7.6 Gate 判定输入约束与产能预算（v1 N=10 散落，终版串联）

  • P0 阶段基于现状 N≥2 做 Soft Gate（仅告警不阻塞），N≥10 为 Hard Gate 启用条件；
  • 台架工时估算：场景集数 × N × 单 run 时长 / 台架并发数 = 阻塞研发天数。P0 必须与算法 owner/DRI 开"Gate 样本共识会"出产能预算，但产能数据 PRD 当前没有；

-- quality_gate_rule: 阈值 catalog + 治理元数据
CREATE TABLE quality_gate_rule (
  rule_id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  metric             TEXT NOT NULL,             -- e.g. 'e2e_p99_ms', 'cpu_high_minutes'
  metric_class       TEXT NOT NULL CHECK (metric_class IN ('A_SAFETY','B_PERFORMANCE')),
  scenario_set       TEXT NOT NULL,
  algo_module        TEXT,                       -- NULL = 全局，否则按感知/规划等模块
  warn_threshold     DOUBLE PRECISION,
  crit_threshold     DOUBLE PRECISION NOT NULL,
  min_runs_per_scenario  INTEGER NOT NULL DEFAULT 10,
  max_rerun_per_gate     INTEGER NOT NULL DEFAULT 1,
  blocking_mode      TEXT NOT NULL CHECK (blocking_mode IN ('advisory','soft','hard')),
  source             TEXT NOT NULL CHECK (source IN ('business_signed','engineer_guess')),
  version            INTEGER NOT NULL,
  active             BOOLEAN NOT NULL DEFAULT true,
  created_by         TEXT NOT NULL,              -- actor（操作级 RBAC）
